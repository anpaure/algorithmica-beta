There is no fastest sorting algorithm in the same sense that there is no fastest vehicle.

For arbitrary objects, a comparison may be all we have. For 32-bit integers, throwing the other 31 bits away on every comparison seems wasteful. Stability, record size, input distribution, memory limits, and what happens to the sorted data afterwards can all change the answer.

This case study deliberately fixes most of those choices. We sort an array of `uint32_t` values in ascending order. There is no payload. The radix kernels are stable and use one equally large temporary array, although stability is not observable for key-only input. Allocation, input generation, and restoring the input between repetitions are excluded unless stated otherwise; histogram initialization and every pass over the keys are included.

All measurements below were made on one performance core of an Apple M4 Max with Apple Clang 17, compiling with `-O3 -mcpu=native`. The input is generated by `mt19937_64` with a fixed seed. Each headline result is the median of seven runs after two warmups; every result is checked with `std::is_sorted`. The [complete benchmark and randomized test program](../../../code/sorting.cpp), [exact CSV output](../../../code/sorting_m4_results.txt), and [Matplotlib generator](../../../code/plot_sorting.py) reproduce the numbers and figures.

## Escaping Comparisons

A comparison gives at most one bit of information. Distinguishing all $n!$ permutations therefore takes at least

$$
\log_2(n!)=n\log_2n-O(n)
$$

comparisons in the worst case. `std::sort` is a strong implementation of this model, and it is our baseline rather than a home-made quicksort.

Fixed-width integers let us use another model. Counting sort can order a small key range by counting each value, finding the beginning of every bucket, and placing the values there. A 32-bit counting array is absurdly large, but one byte has only 256 values. We can stably counting-sort the least significant byte, then the next byte, and so on. Stability preserves the order established by the earlier digits.

```c++
void radix8(vector<uint32_t> &a, vector<uint32_t> &buffer) {
    buffer.resize(a.size());

    for (int shift = 0; shift < 32; shift += 8) {
        size_t count[256] = {};
        size_t position[256];

        for (uint32_t x : a)
            count[(x >> shift) & 255]++;

        position[0] = 0;
        for (int d = 1; d < 256; d++)
            position[d] = position[d - 1] + count[d - 1];

        for (uint32_t x : a) {
            int d = (x >> shift) & 255;
            buffer[position[d]++] = x;
        }
        a.swap(buffer);
    }
}
```

The vector swap only exchanges two pointers. Four passes are even, so the final answer ends up in the original allocation.

On $2^{20}$ uniformly random keys, `std::sort` takes 43.009 ms. The direct radix implementation, including allocation and value-initialization of its temporary array, takes 3.456 ms: a 12.4-fold speedup. This is not because our loops are especially clever. We changed the problem from roughly $n\log n$ data-dependent comparisons to four streaming counting passes.

## Removing One Allocation

The first optimization is almost disappointingly small. Letting the caller retain the temporary array changes 3.456 ms to 3.300 ms, or just 4.5%. Allocation plus value-initializing the temporary storage was visible, but it was not the main problem.

The traffic is. In each pass, counting reads $4n$ bytes; scattering reads another $4n$ and writes $4n$. Ignoring the tiny histogram, the four-pass version transfers at least $48n$ bytes through the cache hierarchy. Reusing the allocation changes none of that.

This is a useful failed expectation: an obvious source-level expense need not be the bottleneck. We need to remove passes, not merely tidy up their setup.

## Eleven Bits at a Time

With $r$ bits per digit, a pass needs $2^r$ counters and we need $\lceil 32/r\rceil$ passes. Wider digits save complete reads and writes, but enlarge the hot histogram and create more independent output streams. This is a hardware-dependent choice, so we swept it instead of declaring eight or eleven to be special. The workspace allocations are outside timing; each bar is the median of five runs after one warmup on the same $2^{20}$ random keys.

![Throughput for six radix widths](../img/sorting-radix-width.svg)

Four-bit digits waste time on eight complete distributions. Ten bits look wider than eight, but both still need four passes; the 10-bit histogram merely makes each pass harder and produces a real regression from 301 to 261 million keys per second. At 16 bits we reach two passes, but the 512 KiB histogram is four times larger than L1D and the scatter has 65,536 possible output streams. Eleven bits is the measured compromise: one fewer pass than radix-8, with a 16 KiB histogram.

Eleven bits give three digits of widths 11, 11, and 10. The largest histogram has 2,048 `size_t` counters, or 16 KiB, and remains comfortably inside the M4 Max's 128 KiB L1 data cache:

```c++
constexpr int width[3] = {11, 11, 10};
constexpr int shift[3] = {0, 11, 22};
array<size_t, 1 << 11> count;

for (int pass = 0; pass < 3; pass++) {
    int buckets = 1 << width[pass];
    uint32_t mask = buckets - 1;
    fill(count.begin(), count.begin() + buckets, 0);

    for (uint32_t x : a)
        count[(x >> shift[pass]) & mask]++;

    // Prefix sums and the same stable scatter as before.
}
```

This single change reduces the lower-bound traffic from $48n$ to $36n$ bytes. The time falls from 3.300 ms to 2.465 ms, a further 25%, and the throughput reaches 425 million keys per second.

We can also time the three parts separately. For $2^{22}$ random keys, the three counting phases take 3.536 ms in total, prefix sums take 0.002 ms, and scattering takes 7.333 ms. The prefix sums are irrelevant; counting and especially data movement dominate. This is direct evidence for optimizing the number of full-array passes.

Neither hot loop has ordinary contiguous output. `count[digit]++` is a read-modify-write through an input-dependent address; a later occurrence of the same digit depends on the previous counter value. The scatter has the same dependency in `position[digit]++`, followed by a store to another input-dependent address. Wider radices create more such streams, while narrower radices repeat these loops more often. The width sweep measures precisely this conflict.

## Counting Every Byte at Once

There is another way to save scans. During one read of the input, we can fill four 256-entry histograms:

```c++
for (uint32_t x : a) {
    count[0][x & 255]++;
    count[1][(x >> 8) & 255]++;
    count[2][(x >> 16) & 255]++;
    count[3][x >> 24]++;
}
```

The four later scatters still have to happen, but their count scans disappear. On random input this takes 3.058 ms. It improves on ordinary radix-8, yet loses to radix-11 by 24%. Four dependent histogram updates per key are not free, and the implementation still writes the whole array four times. This is the regression we keep in the optimization diary: eliminating reads is not as valuable as eliminating a scatter.

The fixed-pass radix kernel is already useful for modest arrays, while the comparison baseline loses throughput as $n$ grows. Radix-11 remains faster throughout the plotted range; its throughput changes near the cache-capacity reference points but never suffers the $n\log n$ comparison term.

## The Input Still Matters

Uniform random integers are a favorable contract for radix sorting and an unfavorable one for comparison sorting. We therefore reran $2^{20}$ keys with four other distributions. “8-bit range” draws every key from $[0,255]$; “1% swaps” begins sorted and performs $n/100$ random swaps.

![Sorting speedup for five input distributions](../img/sorting-distributions.svg)

The plot is intentionally a speedup over `std::sort`, so the dashed line at one means parity. The exact medians from a separate headline run show the reversal clearly:

| Input | `std::sort` | radix-8 | radix-11 | all histograms |
|---|---:|---:|---:|---:|
| random 32-bit | 43.876 ms | 3.245 ms | **2.396 ms** | 2.978 ms |
| values in $[0,255]$ | 18.770 ms | 8.399 ms | 5.622 ms | **4.918 ms** |
| already sorted | **0.790 ms** | 3.268 ms | 2.406 ms | 4.105 ms |

On sorted input, `std::sort` is more than three times faster than our best radix kernel. Radix sort cannot notice that it is done: it always performs every pass. The small-range input is another instructive case. Three of the four bytes contain no information, but our general kernels still process them. Precounting happens to win among the radix variants because its wasted passes no longer need wasted counting scans.

## Signed Keys, Records, and Other Contracts

On the usual two's-complement representation, signed integers can be ordered by flipping the sign bit before extracting digits:

```c++
uint32_t key(int32_t x) {
    return uint32_t(x) ^ 0x80000000u;
}
```

Keep the original value as the payload; only the digit selection uses this transformed key. Floating-point keys need a related transformation and an explicit policy for NaNs and signed zero.

Records are a more serious limitation. Moving a 64-byte record three times is not the experiment above. Sorting compact indices reduces write traffic but adds indirection when the result is consumed. An in-place radix sort saves the second array but requires cycle following and usually gives up this simple stable scatter. `std::sort` is not stable either; a fair stable-record baseline would be `std::stable_sort`.

The final result is therefore conditional, as sorting results always are. For stable out-of-place sorting of full-range random 32-bit keys, widening the radix from eight to eleven bits was the decisive optimization and beat `std::sort` by 17.4 times in the headline run. Reusing an allocation barely mattered, and counting every byte at once was a real step backwards from the best kernel. Change the distribution to already sorted data, and the winner changes with it.
