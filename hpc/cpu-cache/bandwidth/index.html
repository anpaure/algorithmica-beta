Memory Bandwidth

Between the CPU registers and RAM lies a hierarchy of caches. Levels nearer a core are usually smaller and quicker; levels farther away are larger and slower. Two different quantities are hidden inside the word “quick”:

  • latency is the delay between issuing a request and receiving the value;
  • bandwidth is the amount of data the system can transfer per unit of time once enough requests are in flight.

Bandwidth is often the binding resource for loops that perform little work per element. It is also relatively easy to expose: present the machine with a long stream of independent accesses and give it enough time to reach a steady state.

For a first experiment, create an array and increment every element $K$ times:

std::vector<std::uint32_t> a(N);

for (std::size_t t = 0; t < K; ++t)
    for (std::uint32_t &x : a)
        ++x;

The real benchmark consumes a checksum afterward; otherwise the compiler may remove or simplify the work. We vary $N$ and choose $K$ so that the number of useful element updates stays roughly constant:

The transitions line up with the private and shared cache capacities on the test system. When the array is small, execution resources in the core dominate. Once the working set outgrows a cache level, moving dirty lines to and from the next level becomes increasingly important.

The vertical axis is useful updates per second, despite the historical “GFLOPS” label on some plots. An integer increment is not a floating-point operation, and an update is not a fixed amount of bus traffic. The first store miss to a line can have a very different cost from the next fifteen increments to the same resident line.

#Frequency Scaling

Re-running the experiment with boost enabled produced this graph on the Zen 2 test laptop:

The cache-resident part sped up more than the DRAM-resident part. This is a useful pattern, but not a law that every cache property scales with the advertised core clock. A processor may clock its cores, last-level cache, interconnect, memory controller, and DRAM in different domains. Cache latency is often nearly constant in core cycles over part of the range, while DRAM has its own transfer clock and still incurs core-side overhead.

Control and report the frequency policy when comparing implementations. Pinning a nominal frequency also does not eliminate thermal limits, uncore frequency changes, or power-management effects; measure the effective clocks and repeat the run.

#Directional Access

An increment is a read-modify-write operation. To separate useful read and write throughput, we can also sum an array and fill an array:

std::uint64_t sum = 0;
for (std::uint32_t x : a)
    sum += x;

for (std::uint32_t &x : a)
    x = 0;

Compilers readily vectorize both loops, and a zero fill may become memset. That transformation can itself select different implementations for different sizes, including streaming stores in an optimized C library, so a bandwidth experiment must inspect the final assembly rather than infer it from the source.

The curves are not simply “one bus direction” versus “two bus directions.” Ordinary stores to write-back memory normally use a write-allocate policy. If a line is not present with write permission, the core first obtains ownership of the whole line, commonly through a read-for-ownership request, modifies it locally, and eventually writes the dirty line back. A full-line store loop can therefore generate roughly one line fill and one line write-back even though the source never reads the old values.

An incrementing loop also obtains the line and writes it back. Once the line is resident, however, additional passes can update it without repeating both lower-level transfers. Report whether the measurement is a cold single pass, a warm repeated pass, or an average over both. Hardware counters for requested, filled, and written-back lines are more informative than multiplying the loop count by sizeof(a[0]).

Read and write traffic can still have different sustained rates. Reads occupy request-tracking resources until data returns. Writes can be buffered and combined, while DRAM buses must turn around between read and write bursts. The balance depends on the microarchitecture, memory controller, access pattern, and number of cores.

#Streaming Stores

For a large, aligned output that will not be read soon, x86 provides non-temporal or streaming stores. They use write-combining resources and avoid the ordinary write-allocate path, reducing cache pollution and the read-for-ownership traffic of a cold full-line store.

Here are ordinary and streaming AVX2 stores, with a now denoting a separately allocated 32-byte-aligned std::uint32_t *:

const __m256i zeros = _mm256_setzero_si256();

for (std::size_t i = 0; i + 8 <= N; i += 8)
    _mm256_store_si256(reinterpret_cast<__m256i *>(a + i), zeros);

const __m256i zeros = _mm256_setzero_si256();
std::size_t i = 0;

for (; i + 8 <= N; i += 8)
    _mm256_stream_si256(reinterpret_cast<__m256i *>(a + i), zeros);
for (; i < N; ++i)
    a[i] = 0;

_mm_sfence(); // include completion before stopping the timer or consuming the output

For best results, streaming stores should cover complete cache lines with consecutive writes. Too-small or scattered streams may only add overhead, and evicting useful cached data is not the only possible cost: write-combining buffers are finite, and the fence needed at a synchronization boundary is observable.

On this machine, streaming stores substantially improved the large-array result because they avoided write allocation and combined adjacent writes efficiently. The exact ratio is not portable, and the apparent throughput can be exaggerated if the timer stops while stores are still buffered—which is why the final fence belongs inside the measured operation.

Do not assume that every memset or memcpy is a simple vector loop. Production libraries dispatch by size and ISA and may already use rep stos, rep movsb, cached vectors, or non-temporal stores. Likewise, _mm256_stream_load_si256 is not a general “uncached load”: on x86 its useful semantics depend on the memory type and processor. Treat cache-control instructions as platform-specific tools and benchmark the complete operation, including ordering and later reuse.

One core may also lack enough outstanding misses to reach the socket’s DRAM limit. We will separate this request-concurrency limit from aggregate bandwidth in Memory-Level Parallelism and Memory Sharing.
