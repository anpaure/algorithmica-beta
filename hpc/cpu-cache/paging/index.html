Memory Paging

Return once more to the strided increment, but keep the number of useful updates fixed at $N=2^{13}$ while growing the allocation with the stride $D$:

constexpr std::size_t N = 1u << 13;
std::vector<std::uint32_t> a(D * N, 0);

for (std::size_t i = 0; i < a.size(); i += D)
    ++a[i];

The production benchmark checks that D * N does not overflow, allocates on the heap, and consumes a checksum. For $D \ge 16$, successive accesses are at least one 64-byte line apart, so there are $N$ useful accesses and approximately $N$ touched data lines. Yet the historical curve stops being flat as $D$ grows:

The additional bottleneck is address translation. Programs issue virtual addresses, while caches and memory ultimately need physical locations and access permissions. A translation lookaside buffer (TLB) caches recent virtual-page to physical-frame translations so that most loads do not require a page-table walk.

The Zen 2 test core was documented with two relevant levels for ordinary 4 KiB pages:

  • 64 L1 data-TLB entries, covering at most $64 \times 4\ \text{KiB}=256\ \text{KiB}$ of distinct pages;
  • 2048 L2 TLB entries, covering at most $2048 \times 4\ \text{KiB}=8\ \text{MiB}$.

“Coverage” is only a capacity upper bound. TLBs are set-associative, page sizes may share structures, and the access pattern can conflict before every entry is useful.

At $D=256$, the allocation spans

$$ 8192 \times 256 \times 4\ \text{bytes}=8\ \text{MiB}. $$

The stride is 1024 bytes, so four accesses land in each 4 KiB page and exactly 2048 pages are touched. Beyond this point, the working translations no longer fit in the nominal L2 TLB. A miss triggers a hardware page walk; its page-table entries may themselves hit in paging-structure caches or ordinary data caches, so “going to the main page table” is not one fixed-latency operation.

#Larger Pages

Increasing the page size lets each TLB entry translate more data. Common x86-64 sizes are 4 KiB, 2 MiB, and, where supported and configured, 1 GiB. Other architectures and operating systems expose different sets.

Linux offers two distinct mechanisms:

  • hugetlbfs and MAP_HUGETLB use explicitly reserved huge pages;
  • Transparent Huge Pages (THP) can promote eligible ordinary mappings and fall back to base pages.

The global THP policy is visible in sysfs:

cat /sys/kernel/mm/transparent_hugepage/enabled
# typical output: always [madvise] never

Changing it is a privileged, system-wide operation, for example:

echo madvise | sudo tee /sys/kernel/mm/transparent_hugepage/enabled

Under madvise, a program can mark an eligible range as a THP candidate:

const std::size_t bytes = round_up_to_base_page(array_bytes);
void *ptr = mmap(nullptr, bytes, PROT_READ | PROT_WRITE,
                 MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
if (ptr == MAP_FAILED)
    throw std::system_error(errno, std::generic_category());

if (madvise(ptr, bytes, MADV_HUGEPAGE) != 0) {
    const int error = errno;
    munmap(ptr, bytes);
    throw std::system_error(error, std::generic_category());
}

// Fault and initialize the mapping after giving the advice.
// ...

munmap(ptr, bytes);

round_up_to_base_page is an application helper using the page size returned by sysconf(_SC_PAGESIZE). mmap supplies base-page alignment, which is enough for madvise; direct allocation of a naturally aligned 2 MiB THP has stronger alignment conditions, and only aligned subranges can be promoted.

Most importantly, MADV_HUGEPAGE is advice, not an allocation guarantee. The kernel may allocate a huge page on a later fault, collapse base pages asynchronously, split it later, or keep base pages because of fragmentation or policy. The Linux THP documentation describes this best-effort behavior. Verify an experiment through /proc/<pid>/smaps fields such as AnonHugePages, together with the kernel’s THP counters, rather than assuming the call succeeded semantically because it returned zero.

Windows large pages are explicit rather than transparent. A process must obtain SeLockMemoryPrivilege, query GetLargePageMinimum, round the size accordingly, and then request MEM_LARGE_PAGES with VirtualAlloc. Microsoft’s large-page documentation also requires checking allocation failure; the privilege is intentionally not granted to ordinary processes by default.

#Performance and Costs

The huge-page variants flattened the stride curve on the historical test system:

They also reduced dependent-load latency by roughly 10–15% for some large working sets:

Those are plausible TLB benefits, not universal speedups. Huge pages can also:

  • waste physical memory when only a small part of a promoted region is used;
  • add page-fault, zeroing, reclamation, or compaction latency;
  • interact differently with cache indexing and DRAM address mapping;
  • be unavailable inside a container, virtual machine, fragmented host, or restricted account.

Use them for large, densely used mappings after measuring both steady-state throughput and allocation/tail latency. For sparse data structures, improving spatial locality often reduces data-cache misses and TLB pressure simultaneously, without relying on a particular huge-page policy.
