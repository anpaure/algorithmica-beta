Memory Sharing

Some levels of the memory hierarchy are shared. Sharing saves die area and lets one idle core leave more capacity to another, but it also creates contention for cache space, request queues, interconnect links, and DRAM bandwidth.

The boundary is architecture-specific. Separate cores commonly have private L1 caches, but simultaneous hardware threads may share them; some processors share L2 within a cluster; and a last-level cache may be partitioned into slices rather than acting as one uniform pool. On the Ryzen 7 4700U used for these graphs, each group of four cores shares a 4 MiB L3 region, for 8 MiB total.

NUMA adds another distance: a core can access all memory coherently, but local and remote nodes can have different latency and bandwidth. NUMA is common in multi-socket servers, but chiplet and accelerator systems can expose non-uniform topologies too. Linux documents both its NUMA topology and scheduler behavior.

On Linux, inspect the actual machine with lscpu -e, lstopo, and numactl --hardware. Logical CPU numbers do not promise that 0,1,2,3 are four distinct physical cores or that 0 and 4 belong to different cache groups.

#CPU Affinity

To study sharing, each worker must have a distinct, known placement. This GNU Parallel command launches one process on each of logical CPUs 0 through 3:

parallel -j4 taskset -c {} ./run ::: 0 1 2 3

The braces matter. taskset -c 0,1,2,3 ./run gives every process the same four-CPU affinity mask; it does not assign process $i$ to CPU $i$. The scheduler may then migrate or co-locate them inside that mask.

Once each private L2 is exceeded, the workers compete for shared L3 and DRAM resources. To compare two workers in one L3 group with two workers in different groups, first derive the relevant CPU IDs from lstopo, then pin each worker separately. On this particular laptop the commands were:

parallel -j2 taskset -c {} ./run ::: 0 1  # same 4-core L3 group
parallel -j2 taskset -c {} ./run ::: 0 4  # different L3 groups

Linux is topology-aware and tries to preserve useful locality while balancing load; it does not assign runnable tasks wholly at random. It also cannot know every application’s future sharing pattern, and load imbalance can still trigger migration. Affinity is therefore useful for a controlled experiment, but it is not automatically the best production policy.

On a NUMA system, CPU affinity alone is insufficient. Anonymous memory is commonly placed by first touch, so initialize a worker’s data on the node where that worker will run, or set an explicit policy with numactl, mbind, or set_mempolicy. Otherwise a perfectly pinned thread can spend the benchmark accessing remote pages.

#Saturating DRAM

A single core often cannot maintain enough outstanding requests to saturate all memory channels. Aggregate useful bandwidth can rise as workers are added, then flatten or even fall when queues, channels, or power limits saturate:

Two DDR4-2666 channels have a raw transfer rate of about

$$ 2 \times 8\ \text{bytes} \times 2666\ \text{million transfers/s} \approx 42.7\ \text{GB/s}. $$

This is a pin rate, not an application guarantee. Refresh, commands, read/write turnarounds, page conflicts, and other traffic reduce sustained payload bandwidth. The step between four and five workers in this historical graph is consistent with using both L3 regions and more of the memory path, but the timing alone does not prove which internal resource was responsible.

Spread bandwidth-heavy workers across the topology when that improves the measured application, while keeping communicating workers close enough to share data efficiently. “Always split symmetrically” is too strong: the right placement depends on whether the bottleneck is private cache, shared cache, coherence, NUMA distance, or DRAM channels.

#False Sharing

Even threads that update different variables can interfere if those variables occupy one cache line. Coherence tracks ownership at line granularity, so writes from different cores make the line bounce between their private caches. This false sharing can serialize an otherwise independent counter loop.

Padding per-thread writable state to the machine’s destructive-interference size is one remedy:

struct alignas(64) Counter {
    std::atomic<std::uint64_t> value{0};
};

The 64 is appropriate for the test machine, not a portable constant. C++17 exposes std::hardware_destructive_interference_size when the implementation supplies a useful value; otherwise obtain the line size from the target and validate the layout. Padding read-mostly data can waste cache capacity, so apply it only where counters demonstrate ownership traffic.
