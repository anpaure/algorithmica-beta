Algorithmica βCache Lines

Cache Lines

CPU caches transfer and track fixed-size blocks called cache lines. A 64-byte line is common on current x86-64 and AArch64 systems, but it is not universal; query the target machine rather than baking the number into a portable interface.

When a load misses, the hierarchy normally fetches the entire line containing the requested byte. An ordinary store miss in write-back memory normally obtains ownership of the line first, as discussed in Memory Bandwidth. Later accesses to neighboring bytes can then hit the resident copy.

To see the consequence, add a stride $D$ to the incrementing loop:

for (std::size_t i = 0; i < N; i += D)
    ++a[i];

With 32-bit elements, $D=16$ touches one element per 64-byte line, whereas $D=1$ touches all sixteen:

For working sets beyond the caches, the elapsed times converge even though the strided loop performs one-sixteenth as many useful increments. Both patterns visit and dirty essentially the same set of cache lines, so line fills and write-backs dominate the useful arithmetic.

Inside L1, the stride-one loop can be vectorized while the one-per-line loop uses scalar read-modify-write operations. On the Zen 2 test system the latter was only about twice as fast, not sixteen times. That ratio follows from the generated micro-operations and the core’s load/store throughput, not from a general rule that one scalar store and one vector store cost the same. Changing the compiler or microarchitecture can change it.

At $D=8$, two 32-bit elements are updated in each line and the historical curves nearly coincide:

#Isolating One Value per Line

The same idea can deliberately remove spatial locality from the latency benchmark. Put each successor in its own line:

struct alignas(64) PaddedIndex {
    std::uint32_t value;
    std::array<std::byte, 60> padding{};
};

static_assert(sizeof(PaddedIndex) == 64);

std::vector<PaddedIndex> next(nodes);
std::vector<std::uint32_t> order(nodes);
std::iota(order.begin(), order.end(), 0);
std::mt19937 rng(42);
std::shuffle(order.begin(), order.end(), rng);

for (std::size_t i = 0; i < nodes; ++i)
    next[order[i]].value = order[(i + 1) % nodes];

std::uint32_t k = order[0];

for (std::size_t i = 0; i < steps; ++i)
    k = next[k].value;

Padding increases the footprint sixteenfold and guarantees, on a machine with 64-byte lines, that two successors do not share a line. The result exposes cache-capacity boundaries more sharply:

This is a diagnostic transformation, not an optimization. In production, wasting sixty bytes per index usually makes performance worse. Its purpose is to demonstrate the practical accounting rule: for a memory-bound access pattern, count distinct lines transferred and their ownership changes, not just source-level loads and stores.
