Pointer Alternatives

The latency benchmark stores 32-bit indices relative to one base address:

for (std::size_t i = 0; i < steps; ++i)
    k = next[k];

On x86-64, a compiler can combine the load with a scaled-index addressing mode. With the base in rdi and the zero-extended index in rax, the essential instruction is:

mov eax, DWORD PTR [rdi + rax*4]

The instruction performs one load, but its next address depends on the loaded index and on the fixed base. Address generation is part of the load-to-use path. On the Zen 2 test machine this form had a longer dependent L1 path than a simple load through a pointer. Exact load-use latencies and supported address forms are microarchitecture-specific; an instruction count alone does not reveal them.

#Native Pointers

A self-referential node makes the pointer form explicit:

struct Node {
    Node *next;
};

std::vector<Node> nodes(N);
Node *k = &nodes[order[0]];

for (std::size_t i = 0; i < N; ++i)
    nodes[order[i]].next = &nodes[order[(i + 1) % N]];

for (std::size_t i = 0; i < steps; ++i)
    k = k->next;

The dependent instruction can now use the loaded pointer directly as the next address:

mov rax, QWORD PTR [rax]

In the historical 2 GHz Zen 2 run, the pointer chain took about 2 ns per L1-resident step, compared with roughly 3 ns for the 32-bit scaled-index chain. The simpler dependency path explains the direction of the difference; these numbers are not portable guarantees.

The trade-off appears as soon as capacity matters. A native pointer is 8 bytes in the common 64-bit data model, twice the size of a 32-bit index, so half as many successors fit in a cache:

Building a 32-bit executable requires a compatible ABI, libraries, and toolchain, and constrains the process’s virtual address space. Switching the whole program’s ABI merely to compress one data structure is rarely attractive. Relative 32-bit offsets often provide the same density inside a large 64-bit process, provided the arena is smaller than the representable range and movement of the arena does not invalidate external references.

#Three-Byte Indices

If an arena has fewer than $2^{24}$ nodes, an index needs only three bytes. C++ bit-field layout is implementation-defined, so an explicit representation makes the contract clearer:

struct Index24 {
    std::array<std::byte, 3> bytes;
};

static_assert(sizeof(Index24) == 3);

std::uint32_t load(const Index24 &x) {
    return std::uint32_t(std::to_integer<std::uint8_t>(x.bytes[0]))
         | (std::uint32_t(std::to_integer<std::uint8_t>(x.bytes[1])) << 8)
         | (std::uint32_t(std::to_integer<std::uint8_t>(x.bytes[2])) << 16);
}

void store(Index24 &x, std::uint32_t value) {
    x.bytes[0] = std::byte(value & 0xffu);
    x.bytes[1] = std::byte((value >> 8) & 0xffu);
    x.bytes[2] = std::byte((value >> 16) & 0xffu);
}

The benchmark then has well-formed braces and unsigned indices:

std::vector<Index24> next(N);
std::uint32_t k = order[0];

for (std::size_t i = 0; i < N; ++i)
    store(next[order[i]], order[(i + 1) % N]);

for (std::size_t i = 0; i < steps; ++i)
    k = load(next[k]);

Three byte loads plus shifts cost more arithmetic than a native 32-bit load. On little-endian x86, a benchmark can legally expose a fourth accessible byte and let memcpy express an unaligned, alias-safe load:

std::uint32_t load24_fast(const std::byte *p) {
    std::uint32_t value;
    std::memcpy(&value, p, sizeof(value));
    return value & 0x00ffffffu;
}

For a packed byte arena, allocate 3 * N + 1 bytes so every four-byte read beginning at a three-byte record remains inside the allocation. The extra byte, little-endian requirement, and 24-bit range are part of this function’s precondition. Casting p to int * would not be an equivalent optimization: it can violate alignment, type-access, and object-bound rules.

In that experiment, native pointers won for very small working sets, while the denser representation won around the L2/L3 boundary because more successors fit in cache. For large DRAM-resident sets, memory latency dominated and the difference narrowed.

Compressed references are a real design technique, not just a microbenchmark trick: managed runtimes, databases, and in-memory indexes often trade decoding work for capacity. The right width is the smallest one that represents the arena safely, with an explicit sentinel and overflow policy.
