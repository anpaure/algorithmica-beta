Alignment and Packing

An object is aligned when its address is a multiple of the alignment required by its type. The C++ requirement is alignof(T), not sizeof(T): the two often happen to be equal for small scalar types, but they are different properties.

Alignment matters for correctness and performance. Some instructions require aligned operands. Even where unaligned loads are legal, an access that crosses a cache-line or page boundary may need two transfers and extra work to combine them.

#Aligned Allocation

Every object and every array element is placed at an address satisfying alignof(T). A stricter alignment can be requested with alignas:

alignas(32) float values[N];
assert(reinterpret_cast<std::uintptr_t>(values) % 32 == 0);

This is useful when an algorithm uses 32-byte AVX loads or stores. The instruction requires a 32-byte-aligned address; merely fitting inside a 64-byte cache line is not the same guarantee.

C++17 also provides std::aligned_alloc. Its size must be an integral multiple of the requested alignment, it returns null on failure, and its storage must be released with std::free:

constexpr std::size_t alignment = 32;
const std::size_t bytes = N * sizeof(float);
const std::size_t padded = (bytes + alignment - 1) / alignment * alignment;

void *storage = std::aligned_alloc(alignment, padded);
if (storage == nullptr)
    throw std::bad_alloc{};

auto *values = static_cast<float *>(storage);
// use the storage for implicit-lifetime objects such as float
std::free(storage);

Supported extended alignments are implementation-defined, and Microsoft’s C runtime uses _aligned_malloc/_aligned_free rather than implementing std::aligned_alloc in the same way. For an over-aligned C++ object, aligned operator new and a matching aligned operator delete are another option.

An alignment can also be attached to a type:

struct alignas(64) CacheLineRecord {
    std::uint64_t value;
};

static_assert(alignof(CacheLineRecord) == 64);
static_assert(sizeof(CacheLineRecord) % 64 == 0);

Every array element then starts on a 64-byte boundary. On a machine with 64-byte lines this isolates records, at the cost of rounding each record’s size up to a multiple of 64.

#Structure Layout

For an ordinary non-bit-field member, the implementation places the member at an offset satisfying alignof(member_type). It may insert padding before members and at the end of the structure so that every element of an array of the structure is properly aligned.

Consider this common ABI layout:

struct Data {
    char a;
    short b;
    int c;
    char d;
};

On an ABI where short has alignment 2 and int has alignment 4, the layout is equivalent to:

struct DataLayoutExample {
    char a;       // offset 0
    char pad1[1];
    short b;      // offset 2
    int c;        // offset 4
    char d;       // offset 8; char itself never needs padding
    char pad2[3];
};

static_assert(sizeof(DataLayoutExample) == 12);

The exact size and offsets are ABI properties, not values guaranteed by the language. Check them with sizeof, alignof, and offsetof for the target that must interoperate with a file format or foreign interface.

#Member Order

Reordering members can reduce padding:

struct CompactData {
    int c;
    short b;
    char a;
    char d;
};

On the same ABI this type occupies 8 bytes instead of 12. Sorting plain data members by decreasing alignment is a useful heuristic, but sorting by sizeof is not the rule and the heuristic is not a proof of optimality. Arrays, nested structures, base classes, ABI constraints, and intentionally separated hot fields can change the best layout.

Smaller is also not automatically faster. Put fields used together near one another, but separate independently written per-thread fields when false sharing is the larger cost.

#Packed Structures

GCC and Clang provide a non-standard packed attribute:

struct __attribute__((packed)) PackedData {
    std::uint64_t value;
    bool flag;
};

On those compilers the object typically occupies 9 bytes instead of the 16 used by the natural layout. A member may then be misaligned. The compiler can generate safe bytewise or unaligned accesses when accessing it directly, but taking its address and treating it as a normally aligned std::uint64_t * is not safe. Some ISAs handle unaligned loads efficiently, some impose a large penalty, and some fault for particular instructions.

Packing is most defensible for a specified external representation. Even then, byte order, object lifetime, and versioning need explicit handling; copying a native structure to disk is rarely a portable serialization format.

#Bit-Fields

Bit-fields assign a width in bits to a member:

struct Flags {
    std::uint32_t kind : 3;
    std::uint32_t index : 24;
    std::uint32_t valid : 1;
};

Their allocation, alignment, direction, and straddling are implementation-defined. A bit-field cannot be addressed independently, and an array still advances by the whole-byte value sizeof(Flags): neighboring array elements are never merged across a fractional byte boundary by the C++ object model. Adding packed makes the layout a compiler/ABI contract, not a portable one.

For an exact 24-bit little-endian representation, explicit bytes are clearer and portable:

std::uint32_t load_u24_le(const std::byte *p) {
    return std::uint32_t(std::to_integer<std::uint8_t>(p[0]))
         | (std::uint32_t(std::to_integer<std::uint8_t>(p[1])) << 8)
         | (std::uint32_t(std::to_integer<std::uint8_t>(p[2])) << 16);
}

void store_u24_le(std::byte *p, std::uint32_t x) {
    p[0] = std::byte(x & 0xffu);
    p[1] = std::byte((x >> 8) & 0xffu);
    p[2] = std::byte((x >> 16) & 0xffu);
}

This avoids shifting negative char values, violating alignment or type-access rules, and reading a fourth byte outside the object. Compilers can combine the byte operations when the target has a profitable unaligned-load sequence. If a specialized loader deliberately reads four bytes, its API must require four accessible bytes and use memcpy or another alias-safe operation; masking the result does not legalize an out-of-bounds read.
