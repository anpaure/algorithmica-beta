Binary Exponentiation

Computing $a^n$ by multiplying by $a$ exactly $n-1$ times is reasonable when $n$ is five. It is less attractive when $n$ is a 64-bit integer or a cryptographic exponent.

The exponent contains enough structure to do better. Every time it is even, we can halve it by squaring the base:

$$ \begin{aligned} a^{2k} &= (a^k)^2,\\ a^{2k+1} &= (a^k)^2a. \end{aligned} $$

This is binary exponentiation, also called exponentiation by squaring. Each step removes one binary digit of $n$, so it uses $O(\log n)$ multiplications.

#A Recursive Derivation

The most direct recurrence computes the half-power only once:

$$ f(a,n)= \begin{cases} 1, & n=0,\\ f(a,\lfloor n/2\rfloor)^2, & n>0\text{ and }n\text{ is even},\\ f(a,\lfloor n/2\rfloor)^2a, & n\text{ is odd}. \end{cases} $$

For multiplication modulo $m$, reduction after every product keeps the values bounded. A 128-bit intermediate is enough for two 64-bit residues:

#include <cstdint>

uint64_t mul_mod(uint64_t a, uint64_t b, uint64_t m) {
    return uint64_t((__uint128_t(a) * b) % m);
}

uint64_t pow_mod_recursive(uint64_t a, uint64_t n, uint64_t m) {
    if (n == 0)
        return 1 % m;

    uint64_t half = pow_mod_recursive(a, n / 2, m);
    uint64_t square = mul_mod(half, half, m);
    return n % 2 == 0 ? square : mul_mod(square, a % m, m);
}

The function requires $m>0$. Writing 1 % m handles the unusual but valid modulus $m=1$, where every residue is zero.

The recursion is only $O(\log n)$ levels deep, but it is unnecessary. More importantly, the iterative form exposes two useful dependency chains to the processor.

#Reading the Exponent as Bits

The binary expansion of 42 is $101010_2$, or $32+8+2$. Therefore,

$$ a^{42}=a^{32}a^8a^2. $$

While scanning the exponent from its least significant bit, maintain two invariants:

  • base is $a^{2^k}$ after $k$ bits have been consumed;
  • result is the product selected by the consumed bits.
uint64_t pow_mod(uint64_t a, uint64_t n, uint64_t m) {
    uint64_t result = 1 % m;
    uint64_t base = a % m;

    while (n != 0) {
        if (n & 1)
            result = mul_mod(result, base, m);
        n >>= 1;
        if (n != 0)
            base = mul_mod(base, base, m);
    }
    return result;
}

The final guard avoids a square whose value will not be used. It is not necessary for correctness.

If the exponent has $L=\lfloor\log_2n\rfloor+1$ bits, the algorithm performs $L-1$ squarings and popcount(n) multiplications into the result. Thus its exact multiplication count is

$$ L-1+\operatorname{popcount}(n), $$

apart from small special cases. The asymptotic bound hides this dependence on the bit pattern.

#Modular Inverses

For prime $p$ and $a\not\equiv0\pmod p$, Fermat’s theorem gives

$$ a^{-1}\equiv a^{p-2}\pmod p. $$

The implementation is consequently one line once binary exponentiation is available:

uint64_t inverse_prime(uint64_t a, uint64_t p) {
    // Preconditions: p is prime and a % p != 0.
    return pow_mod(a, p - 2, p);
}

This is convenient, but not always the fastest route. The extended Euclidean algorithm also takes $O(\log p)$ arithmetic steps, works for composite moduli whenever the inverse exists, and avoids a long sequence of modular multiplications.

For a compile-time exponent, the branch pattern is fixed. A compiler may unroll or partially evaluate the loop, but source-level unrolling should be justified by measurement: it increases code size, and modular multiplication—not the loop counter—is usually the expensive part. When the modulus is also fixed, constant-division optimizations apply; when many products share an odd run-time modulus, Montgomery multiplication may be more suitable.

#The Algorithm Is Not About Integers

Nothing in the derivation requires ordinary multiplication. It requires an associative operation and an identity element—a monoid. The same loop can raise matrices to a power, compose permutations, or repeatedly apply a state transition.

For example, powers of the Fibonacci transition matrix

$$ \begin{pmatrix}1&1\\1&0\end{pmatrix} $$

compute Fibonacci numbers in $O(\log n)$ matrix multiplications. Binary exponentiation is best understood as a way to repeat any associative transformation, not as a number-theory party trick.

The performance lesson is similarly general: a better representation of the work—in this case, the bits of the exponent—can remove an exponential amount of repetition before instruction-level optimization even begins.
