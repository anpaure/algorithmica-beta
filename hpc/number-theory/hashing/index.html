Hashing

A hash function takes a potentially large object and returns a small fixed-size value. That description sounds suspiciously similar to compression, except that a hash has no decompressor. Information is deliberately discarded, so collisions—different inputs with the same hash—are not an accident but a mathematical certainty.

The useful property is that good hash values behave enough like uniformly distributed integers for a particular task. The phrase “enough like” carries most of the complexity. A hash table, a file-integrity check, a password database, and a denial-of-service boundary need very different guarantees, even though all four APIs may return a string of bits called a hash.

#Collisions and the Birthday Bound

For an ideal $b$-bit hash, two independently chosen distinct inputs collide with probability $2^{-b}$. With $n$ inputs there are $\binom n2$ pairs, so when $n$ is small relative to $2^{b/2}$, the probability of at least one accidental collision is approximately

$$ \frac{n(n-1)}{2^{b+1}}. $$

This is the birthday effect: collisions become likely after roughly $2^{b/2}$ values, not $2^b$. A 64-bit fingerprint is excellent for many internal probabilistic algorithms, but it does not provide 64 bits of collision security for a large collection, and it must not silently replace equality when correctness requires exact answers.

A hash table stores the hash to avoid recomputing it and uses it to choose a candidate bucket, but it still compares the full key:

#include <cstdint>
#include <string>
#include <string_view>

struct slot {
    bool occupied = false;
    std::uint64_t hash = 0;
    std::string key;
    int value = 0;
};

bool matches(const slot& s, std::uint64_t hash, std::string_view key) {
    return s.occupied && s.hash == hash && s.key == key;
}

The hash comparison is a fast rejection test. The key comparison is what makes the result exact.

#Mixing Fixed-Width Keys

Integer keys often contain structure: aligned pointers end in zero bits, sequential IDs differ only slightly, and grid coordinates repeat regular patterns. If a table with a power-of-two capacity uses the low bits directly, that structure becomes clustering.

A mixing function diffuses input differences over the output. The following finalizer comes from the public-domain MurmurHash3 reference implementation and is a useful example for a single 64-bit word:

#include <cstdint>

std::uint64_t mix64(std::uint64_t x) {
    x ^= x >> 33;
    x *= 0xff51afd7ed558ccdULL;
    x ^= x >> 33;
    x *= 0xc4ceb9fe1a85ec53ULL;
    x ^= x >> 33;
    return x;
}

std::uint64_t hash_integer(std::uint64_t key, std::uint64_t seed) {
    return mix64(key ^ seed);
}

Unsigned overflow is intentional and well-defined. Multiplication spreads low-bit changes upward, while XOR-shifts feed high-bit changes downward. This function is suitable as a compact non-cryptographic mixer for controlled integer inputs; it is not a byte-string hash, a message-authentication code, or a defense against an adversary. The transform is invertible on 64-bit words, and a secret XOR seed does not turn it into cryptography.

Hashing variable-length data adds more decisions:

  • how bytes are grouped into words;
  • which byte order defines the format;
  • how the final partial word and total length are encoded;
  • whether concatenated fields are framed unambiguously;
  • whether updates can be streamed;
  • and how several independent lanes are combined.

For example, hashing ("ab", "c") by concatenation must not equal hashing ("a", "bc") unless the application considers those records identical. Canonical serialization is part of the hash definition. Never hash a C/C++ structure by copying its raw object representation: padding bytes, pointer values, endianness, and ABI layout are not stable data formats.

#Randomized and Universal Hashing

A fixed non-cryptographic hash may distribute ordinary inputs beautifully and still have a family of inputs that collide on purpose. Randomizing the selected function makes it harder for an input distribution to be bad independently of the choice of hash.

Carter and Wegman’s original paper on universal hash families formalizes this idea. Instead of assuming random keys, choose a function $h$ randomly from a family $\mathcal H$ mapping keys to $m$ buckets such that for any distinct keys $x$ and $y$,

$$ \Pr_{h\in\mathcal H}[h(x)=h(y)] \le \frac{1}{m}. $$

is small. The probability is over the function chosen at initialization, not over a friendly input distribution. Multiply-shift and polynomial families make this practical for fixed-size keys.

Universal hashing gives an analyzable collision bound; it does not necessarily hide the seed after an attacker observes outputs. For public-facing hash tables, use a keyed function designed for short-input pseudorandomness, such as SipHash, through a maintained library. SipHash was introduced specifically as a fast keyed function for short inputs. Reseeding a weak, invertible mixer is not an equivalent construction.

#Cryptographic Hashes Are a Different Tool

A cryptographic hash is designed to resist computational attacks in addition to producing well-distributed output. The usual goals include:

  • preimage resistance: given a digest, finding a matching message should be infeasible;
  • second-preimage resistance: given one message, finding a different message with the same digest should be infeasible;
  • collision resistance: finding any colliding pair should be infeasible.

For an ideal $b$-bit digest, generic preimage search takes about $2^b$ work and generic collision search about $2^{b/2}$. These are security targets, not guarantees obtained merely by choosing a wide output.

Use standardized or widely reviewed library implementations. NIST specifies the SHA-2 family in FIPS 180-4 and the SHA-3 family in FIPS 202. SHA-1 is deprecated for collision-sensitive uses; MD5 is not a modern collision-resistant hash.

A plain cryptographic digest authenticates nothing. If an attacker can replace a message, they can also replace its digest. A message-authentication code combines a secret key with the message; HMAC is a standard construction, but it must be instantiated with a currently suitable underlying hash and a properly managed key.

Passwords are another separate problem. Fast hashing helps an attacker test guesses. Password storage needs a salted, deliberately expensive password-hashing function with configurable memory and time costs; RFC 9106 specifies Argon2 and deployment profiles. Do not build password storage by repeatedly calling a general-purpose hash an arbitrary number of times.

#Checksums, Fingerprints, and Hashes

Several nearby tools are easy to confuse:

  • A checksum or CRC targets accidental transmission/storage errors and often has strong guarantees for a particular burst-error model. It is not adversarial.
  • A non-cryptographic hash targets fast distribution or probabilistic fingerprinting.
  • A keyed hash or MAC authenticates messages to parties that share a secret.
  • A cryptographic hash provides unkeyed one-way and collision-resistance goals.
  • A password hash is intentionally resource-intensive and includes salting and parameterization.

Using a stronger category can be unnecessary and slow; using a weaker one can be a security failure. Start from the required guarantee, not from an algorithm name already available in a header.

#Performance Is Shape-Dependent

There is no single “fastest hash.” The bottleneck depends on the workload:

  • For 8-byte keys in a hash table, initialization and finalization latency dominate.
  • For large files, steady-state bytes per cycle and memory bandwidth dominate.
  • A tree hash can process large independent chunks in parallel, while a serial state creates a dependency chain.
  • SIMD helps when several messages or several lanes of one long message are available together.
  • Hardware instructions for CRC, SHA, or carryless multiplication help only algorithms structured to use them.
  • Returning 128 bits may be nearly free internally but increases table footprint and comparison traffic.

Benchmark with the real key sizes and table load factor, and keep collision resolution in the benchmark. A mixer that wins in a tight loop may lose once its larger state displaces useful buckets from cache.

Hashing is controlled information loss. Correct engineering means deciding exactly what may be lost, who controls the input, how collisions are resolved, and whether the output is merely a performance hint or part of a security boundary.
