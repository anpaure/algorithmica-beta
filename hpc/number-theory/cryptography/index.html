Cryptography

Cryptography is often introduced as a collection of difficult arithmetic problems. That is a little like introducing aviation as a collection of strong metal alloys: the components matter, but the interesting question is how they are assembled into a system that remains safe when someone is actively trying to break it.

An adversary may read traffic, modify it, replay an old message, impersonate one endpoint, or measure how long a computation takes. Different tools address different parts of that list. Encryption alone does not prove who sent a message. A hash alone does not prevent an attacker from replacing both a file and its hash. A correct cipher inside an ambiguous protocol can still be completely insecure.

The first rule of practical cryptography is therefore simple: use a maintained, high-level protocol or library whose interface already encodes the required checks. The algorithms below are worth understanding, but implementing them is not a safe way to deploy them.

#Primitives and Their Jobs

Modern systems are built from several kinds of primitive:

PrimitiveHas a secret key?Main purpose
cryptographic hashnocompact, collision-resistant digest
message-authentication code (MAC)shared keyintegrity and authenticity between key holders
authenticated encryption (AEAD)shared keyconfidentiality, integrity, and authenticity
digital signatureprivate/public key pairpublicly verifiable origin and integrity
key derivation function (KDF)secret inputderive separate keys with explicit context
key exchange or KEMprivate/public materialestablish a shared secret

These interfaces deliberately do less than a complete protocol. They do not decide who owns a public key, how keys are rotated, whether an old message may be replayed, or what bytes a structured message means. Those decisions need framing, versioning, identities, sequence numbers, and a precise threat model.

A useful distinction is between authentication and authorization. A valid MAC may prove that a holder of a shared key created a request; it does not prove that this holder is allowed to delete a database. Similarly, a digital signature proves a relationship between bytes and a private key, not that a human read or intended the document.

#Symmetric Encryption Must Authenticate

AES is a standardized block cipher: for one key, it permutes 128-bit blocks. FIPS 197 specifies AES with 128-, 192-, and 256-bit keys, but raw AES does not say how to encrypt a message longer than one block. That is the job of a mode of operation.

Applications should normally ask for authenticated encryption with associated data, or AEAD. Its abstract interface is

$$ (C,T)=\operatorname{Seal}_K(N,A,P), $$ where $P$ is plaintext, $K$ is a secret key, $N$ is a nonce, $A$ is associated data, and $(C,T)$ is ciphertext plus an authentication tag. Decryption returns either the complete plaintext or failure: $$ \operatorname{Open}_K(N,A,C,T)\in\{P,\operatorname{FAIL}\}. $$

Associated data is authenticated but left visible. A network protocol can put its version, message type, sequence number, and routing fields there, preventing an attacker from changing how the ciphertext is interpreted. Variable-length fields must be encoded unambiguously.

RFC 5116 defines this interface and its nonce requirements. With common AEADs such as AES-GCM and ChaCha20-Poly1305, a nonce must not repeat under the same key. Reuse can expose plaintext relationships and destroy authentication; a nonce is not merely an optional random decoration. Let a well-reviewed library manage it, or follow the protocol’s counter construction exactly.

Authenticated decryption is an all-or-nothing operation. Do not parse, display, decompress, or otherwise act on plaintext until the tag has been verified, and treat failure as ordinary hostile input. RFC 8439 specifies ChaCha20-Poly1305 and illustrates how a stream cipher and authenticator are composed into one AEAD construction. Designing a new composition from a cipher and a MAC is specialist work.

#Hashes, MACs, and Signatures

A cryptographic hash function maps any byte string to a fixed-size digest. It is useful for content addressing, transcript construction, and checking a file against a digest obtained through a trusted channel. If an attacker controls both file and digest, the check proves nothing.

A MAC adds a shared secret. HMAC, standardized in RFC 2104, is a standard way to build a MAC from a suitable hash. Anyone who can verify an ordinary MAC also possesses the key needed to create another one, so a MAC does not provide public verifiability.

A digital signature separates those roles. The private key signs; the public key verifies. This is useful for software updates, certificates, and protocol handshakes, but only after the verifier has established whose public key it is. Signatures also need unambiguous serialization and domain separation: a signature intended for invoice:v1 should not silently validate the same bytes as a firmware authorization.

Use a complete signature scheme through a maintained library, not a raw group operation. For example, RFC 8032 specifies Ed25519 and Ed448, including encoding and verification rules that are just as important as the underlying curve arithmetic.

#RSA as Arithmetic

RSA is a useful example of a one-way public operation with a private inverse. Choose distinct primes $p$ and $q$, set

$$ n=pq,\qquad \varphi(n)=(p-1)(q-1), $$ and choose $e$ coprime to $\varphi(n)$. The private exponent $d$ satisfies $$ ed\equiv 1\pmod{\varphi(n)}. $$ For a representative $0\le m<n$, the textbook operations are $$ c=m^e\bmod n,\qquad m=c^d\bmod n. $$

The following tiny values make the identity testable without a big-integer library:

#include <cstdint>
#include <stdexcept>

constexpr std::uint32_t mod_power(std::uint32_t base,
                                  std::uint32_t exponent,
                                  std::uint32_t modulus) {
    if (modulus == 0)
        throw std::invalid_argument("zero modulus");

    std::uint64_t result = 1 % modulus;
    std::uint64_t x = base % modulus;

    while (exponent != 0) {
        if ((exponent & 1u) != 0)
            result = (result * x) % modulus;
        x = (x * x) % modulus;
        exponent >>= 1;
    }
    return static_cast<std::uint32_t>(result);
}

// p = 61, q = 53, n = 3233, e = 17, d = 2753.
static_assert(mod_power(65, 17, 3233) == 2790);
static_assert(mod_power(2790, 2753, 3233) == 65);

This demonstrates only the number theory. Every parameter is intentionally tiny, the multiplication is not suitable for large moduli, and textbook RSA is deterministic and malleable. It is not an encryption or signature scheme.

Real RSA encryption uses an encoding such as RSAES-OAEP, and modern RSA signatures use a construction such as RSASSA-PSS. RFC 8017 specifies these schemes and their many validation requirements. Real implementations also need large keys, cryptographic randomness, constant-time arithmetic, blinding, and defenses against malformed-ciphertext oracles. Use a vetted implementation and keep encryption and signing keys separate.

Factoring $n$ reveals the private key, but that observation is not the whole security argument: the RSA problem, the encoding scheme, key generation, and implementation leakage all matter. Public-key cryptography is normally used to authenticate or establish a short shared secret; symmetric AEAD then protects the bulk data.

#What HTTPS Actually Does

TLS 1.3 is a good example of primitives becoming a protocol. In a normal certificate-authenticated handshake:

  1. the client and server exchange supported parameters and ephemeral key shares;
  2. an ephemeral Diffie–Hellman computation establishes shared secret material;
  3. the server sends a certificate chain and signs the handshake transcript with the corresponding private key;
  4. both sides derive separate handshake and application keys with HKDF;
  5. Finished messages MAC the transcript, confirming that both sides derived the same keys;
  6. application records are protected with AEAD and sequence-derived nonces.

The exact state machine is specified in RFC 8446. A server may have an RSA certificate, but TLS 1.3 does not use RSA key transport: that RSA key signs the transcript. Resumption and pre-shared-key modes change parts of the handshake, and optional 0-RTT data is replayable, so applications must not put non-idempotent actions in early data.

Certificates solve the man-in-the-middle problem only if validation succeeds. The client must check the chain to an accepted trust anchor, the requested hostname, validity and usage constraints, and the transcript signature. Clicking through a certificate error discards the authentication property while leaving the connection looking encrypted.

Ephemeral key exchange provides forward secrecy: after ephemeral secrets have been erased, later theft of the certificate’s long-term signing key should not reveal previously recorded session keys. It does not protect an endpoint that was compromised during the session.

#The Implementation Is Part of the Protocol

Mathematical security assumes that secret-dependent behavior is not visible. Real machines expose timing, cache accesses, branch patterns, page faults, power use, and fault responses. A lookup table indexed by a secret or an early-exit tag comparison can turn a sound primitive into an oracle. Constant-time code is a whole-program property and should come from a cryptographic library designed and tested for the target platform.

Keys should come from an operating-system cryptographic random source, live in narrowly scoped storage, carry an identifier and algorithm version, and never enter logs or crash reports. Ciphertext formats should authenticate their version and metadata. Rotation needs a migration plan: deleting an old key before rewriting its data is data loss, while accepting an old algorithm forever defeats retirement.

Algorithm agility does not mean inventing combinations at runtime. It means following a versioned protocol with a reviewed upgrade path. NIST’s FIPS 203 standardizes ML-KEM for post-quantum key establishment, but combining classical and post-quantum mechanisms safely is itself a protocol decision. Adopt the construction supplied by an updated protocol and library.

Test implementations with published vectors, malformed inputs, and failure paths; fuzz the parser around the cryptographic core. Most importantly, make the secure operation the easy API: open should return either authenticated plaintext or an error, never “plaintext plus a Boolean that the caller might forget to inspect.”

Cryptography does not remove trust. It narrows trust to explicit keys, algorithms, implementations, and protocol state. Good engineering begins by writing those assumptions down—and by refusing to replace a reviewed construction with something that merely looks mathematically difficult.
