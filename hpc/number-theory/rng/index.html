Random Number Generation

Ask a computer for a random bit twice with the same program state and it will normally return the same answer twice. This is not a defect. Most software does not generate new entropy; it expands a small seed into a long deterministic sequence that merely has the statistical shape required by the application.

Determinism is valuable for simulations, randomized algorithms, tests, and games. A failing run can be replayed from its seed, and generating each value costs only a few arithmetic instructions. It is disastrous when unpredictability is the requirement. Random number generation therefore begins by separating two jobs that unfortunately share one name.

#Engines and Distributions

A pseudorandom number generator (PRNG), or engine, maintains a state and repeatedly produces fixed-width words. A distribution turns those words into the values the program actually requested: an integer in [0, n), a floating-point value in [0,1), a normal variate, or a shuffled permutation.

Keeping the layers separate prevents many subtle biases. The C++ random-number library follows exactly this design: its engine and distribution requirements specify uniform random bit generators separately from uniform_int_distribution and the other transformations.

The engine has several relevant properties:

  • state size and period;
  • statistical quality in the dimensions the application uses;
  • cost and dependency latency per output;
  • speed of seeding, copying, jumping, and creating independent streams;
  • reproducibility across implementations;
  • and, only for a cryptographic generator, resistance to predicting past or future output.

Passing a test suite checks some statistical consequences of these properties. It does not prove unpredictability, and a huge period does not by itself imply good output.

#Linear Congruential Generators

The classical linear congruential generator updates

$$ x_{i+1} = a x_i + c \pmod m. $$

With $m=2^w$, unsigned overflow performs the reduction for free. Suitable parameters can make the state visit all $2^w$ possible values, so the period looks ideal. The output is still highly structured: low bits can have short cycles, and tuples of consecutive values lie on a limited family of hyperplanes.

This distinction—good state traversal but visibly linear output—is useful. It explains why “the period is enormous” is not a sufficient generator review, and it motivates a modern pattern: use a cheap state transition, then apply a nonlinear-looking permutation before exposing the bits.

#A Small General-Purpose Generator

PCG is a family of permuted congruential generators. The underlying state follows an LCG, while an output permutation uses XOR, shifts, and rotation to mix the bits. Melissa O’Neill’s PCG paper describes the family, stream selection, and statistical evaluation.

Here is the 64-bit-state, 32-bit-output XSH-RR variant. It is compact enough to study and useful for ordinary randomized algorithms; it is not cryptographically secure.

#include <bit>
#include <cstdint>

class pcg32 {
public:
    using result_type = std::uint32_t;

    pcg32(std::uint64_t seed, std::uint64_t sequence)
        : state_(0), increment_((sequence << 1u) | 1u) {
        operator()();
        state_ += seed;
        operator()();
    }

    result_type operator()() {
        const std::uint64_t old = state_;
        state_ = old * 6364136223846793005ULL + increment_;

        const auto xorshifted = static_cast<std::uint32_t>(
            ((old >> 18u) ^ old) >> 27u
        );
        const auto rotation = static_cast<int>(old >> 59u);
        return std::rotr(xorshifted, rotation);
    }

    static constexpr result_type min() { return 0; }
    static constexpr result_type max() { return UINT32_MAX; }

private:
    std::uint64_t state_;
    std::uint64_t increment_; // odd; low 63 bits of sequence select a stream
};

The two warm-up calls are part of seeding: they mix both the initial state and stream parameter into the recurrence. Two objects with identical parameters produce identical sequences, which is exactly what reproducible experiments need.

Do not use this listing as a reason to invent a generator by changing constants. Generator parameters, seeding, and output permutations are one design. Use a maintained implementation when compatibility or long-term statistical behavior matters.

#Mapping to a Range Without Bias

The tempting expression generator() % bound is biased unless the engine’s range size is divisible by bound. If an engine had 256 possible byte outputs and bound were 6, residues 0 through 3 would each have 43 preimages, while 4 and 5 would have only 42.

Rejection sampling removes the excess part of the source range. Daniel Lemire’s multiply-and-reject method maps a 32-bit word through the high half of a multiplication and normally avoids division in the loop:

#include <cstdint>
#include <stdexcept>

std::uint32_t bounded(pcg32& generator, std::uint32_t bound) {
    if (bound == 0)
        throw std::invalid_argument("bound must be positive");

    std::uint64_t product = std::uint64_t{generator()} * bound;
    std::uint32_t low = static_cast<std::uint32_t>(product);

    if (low < bound) {
        const std::uint32_t threshold = (std::uint32_t{0} - bound) % bound;
        while (low < threshold) {
            product = std::uint64_t{generator()} * bound;
            low = static_cast<std::uint32_t>(product);
        }
    }

    return static_cast<std::uint32_t>(product >> 32);
}

For ordinary application code, std::uniform_int_distribution is clearer and delegates this problem to the library. The explicit version matters when a range conversion is proven to be a bottleneck or when a serialized algorithm requires fully specified behavior.

Floating-point conversion has similar edges. Dividing an integer by the engine’s maximum can produce exactly 1, which violates the common half-open [0,1) contract. Use a distribution or std::generate_canonical instead of reconstructing its scaling rules casually.

#Seeds, Streams, and Parallel Programs

A seed is an input, not a quality certificate. Seeding every worker with the current second can give many workers the same state; seeding with consecutive integers may create related streams in generators whose initialization was not designed for it.

Choose a policy based on the application:

  • Tests should print or store the exact seed and generator version.
  • Scientific results should record enough state to reproduce the run, including stream assignment and distribution parameters.
  • Independent workers should use a documented stream-selection, jump-ahead, or counter-based construction—not merely seed + thread_id unless the generator specifies that use.
  • Work stealing and nondeterministic scheduling require extra design if results must be bit-for-bit reproducible.

Counter-based generators are attractive for parallel work because output is a function of a key and counter rather than a mutable predecessor. A worker can own a counter range, and the program can regenerate any value without replaying the stream. The Random123 paper, “Parallel Random Numbers: As Easy as 1, 2, 3”, develops this model for CPUs and accelerators.

#Randomness for Security

PCG, Mersenne Twister, xorshift-family generators, and ordinary LCGs are not appropriate for keys, nonces that require unpredictability, password-reset tokens, or session identifiers. Statistical quality is not enough: after observing outputs, an attacker must still be unable to recover state or predict another output.

For these tasks, obtain bytes from the operating system or a vetted cryptographic library. On Linux, getrandom draws from the kernel cryptographic random source and handles early-boot initialization semantics better than opening a device path by hand. Other operating systems provide corresponding APIs. A protocol may then expand or structure that randomness with a specified cryptographic construction such as ChaCha20; the IETF construction is documented in RFC 8439.

std::random_device is not a portable synonym for an operating-system CSPRNG. The C++ interface permits implementation-defined behavior, so security-sensitive software must verify what its platform and library actually provide.

Never seed a security generator from a timestamp, process ID, address, or general-purpose PRNG. Such values may be different without containing meaningful entropy.

#Testing and Performance

The first validation layer consists of exact properties: known-answer tests, full-period proofs where applicable, serialization round trips, range bounds, and deterministic replay. Statistical batteries then search for patterns. TestU01 provides families of empirical tests and illustrates an important limitation: passing the tested sample sizes is evidence against specific defects, not proof that no defect or predictor exists.

Benchmark the operation the application uses. A raw engine may be fast while bounded sampling rejects often; a generator with excellent throughput may have a long dependency latency in a single stream; a large state may hurt when thousands of workers each own one; and a vector generator helps only when consumers can use a batch of values.

Random generation is therefore another case of separating model from mechanism. Decide whether the goal is reproducibility, statistical simulation, parallel stream management, or adversarial unpredictability. Then choose an engine, distribution, and seeding interface whose guarantees match that goal—rather than asking one mysterious rand() function to do all four.
