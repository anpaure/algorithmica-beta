Algorithmica βHash Tables

Hash Tables

A hash table is often introduced as an array plus a clever formula that turns a key into an index. This description is mathematically sufficient and architecturally misleading.

The hash function only chooses where a search begins. Performance is mostly determined by what happens after two keys choose the same place: how entries are laid out, how many unrelated bytes are fetched, which condition terminates a failed lookup, and what deletion leaves behind. Two tables with the same expected $O(1)$ complexity can have very different memory traffic.

In this chapter, we will design a flat hash table in stages. We start with chaining, move the entries into one contiguous array, control long probe sequences with Robin Hood insertion, and finally separate one-byte metadata so that a SIMD comparison can reject many slots at once.

The result is not meant to replace a production container. A real generic map must deal with object lifetimes, exceptions, heterogeneous lookup, allocator rules, and iterator guarantees. Our goal is to understand the layout decisions underneath containers such as absl::flat_hash_map.

#The Contract Comes First

We will discuss a map with these operations:

find(key)          -> pointer to value, or not found
insert(key, value) -> insert a new key, or replace its value
erase(key)         -> whether a key was removed
reserve(n)         -> prepare for at least n live entries

Three counters will matter:

  • capacity: the number of physical slots;
  • size: the number of live entries;
  • deleted: the number of tombstones.

The usual load factor is $\alpha=\text{size}/\text{capacity}$, but a table with tombstones is probed as if both live and deleted slots were occupied. Its operational load is

$$ \alpha_\text{occupied} = \frac{\text{size}+\text{deleted}}{\text{capacity}}. $$

Growth policy must use the second quantity. Otherwise a table can be only half full according to size() and still have almost no empty slots at which an unsuccessful search may stop.

We also assume that equal keys have equal hashes and that the hash distributes the workload well. The table can repair collisions; it cannot repair a function that sends every key to the same bucket. See Hashing for mixing and adversarial considerations.

#Separate Chaining

The conventional implementation stores an array of bucket heads. Each head refers to a linked list, or sometimes a small dynamic array, of entries with the same bucket index:

buckets          separately allocated nodes

  0  --------->  [key,value,next] -> [key,value,next]
  1  --------->  [key,value,next]
  2  --------->  null
  3  --------->  [key,value,next] -> [key,value,next]

Chaining has pleasant semantics. Insertion does not need an empty slot in the primary array, erasing a node does not affect the search path of another key, and node addresses can remain stable across a rehash. It also has a hardware problem: a lookup may fetch a bucket pointer, follow one or more pointers to unrelated allocations, and compare only one key per cache miss.

This is a good trade when entries are large, stable addresses are part of the interface, or the table stores nodes for other reasons. For small keys and values, the pointers, allocator metadata, and poor spatial locality may cost more than the payload.

#Open Addressing

Open addressing puts every entry directly in a fixed array. A collision means trying another slot according to a probe sequence. The simplest sequence is linear probing:

$$ i_j = (h(k) + j) \bmod C. $$

When the capacity $C$ is a power of two, the modulo becomes & (C - 1). This requires the low bits of the hash to be well distributed; using the key itself as the hash is not harmless merely because the code compiles.

Each slot has one of three states:

EMPTY     the slot has never been occupied since the last rehash
FULL      the slot contains a live key and value
DELETED   the slot used to be full

A lookup follows the probe sequence until it finds either the key or an EMPTY slot:

for (std::size_t i = hash(key) & mask; ; i = (i + 1) & mask) {
    if (state[i] == EMPTY)
        return not_found;
    if (state[i] == FULL && keys[i] == key)
        return &values[i];
    // DELETED does not terminate the search.
}

The last comment is the core deletion invariant. Suppose keys A and B have the same home slot and B was placed after A. Clearing A to EMPTY would make a later lookup for B stop too early. A tombstone says, “nothing is stored here, but the probe history continues.”

#Correct insertion with tombstones

Insertion remembers the first tombstone but keeps searching until it sees an empty slot or the key itself:

first_deleted = none

for each slot in the probe sequence:
    if FULL and key matches:
        replace the value; size does not change; return

    if DELETED and first_deleted is none:
        first_deleted = this slot

    if EMPTY:
        target = first_deleted if one was seen, otherwise this slot
        construct the new entry at target
        size += 1
        deleted -= 1 if target was a tombstone
        return

Inserting immediately into the first tombstone is wrong: the same key may already exist later in the cluster. Incrementing size before determining whether the operation is a replacement is another common bug.

The table must also preserve at least one EMPTY slot. Otherwise a missing-key lookup has no terminating state and loops forever. In practice we rehash well before that point. A policy might rebuild when occupied slots exceed a chosen fraction of capacity, or rebuild at the same capacity when tombstones are the main problem. The best threshold depends on entry size, hash quality, probe scheme, and the ratio of successful to unsuccessful searches; 7/8 or 3/4 is a policy, not a theorem.

#Rehashing is garbage collection

Rehashing allocates a fresh array and inserts every live entry into it. This does three jobs at once:

  1. changes the capacity,
  2. clears all tombstones,
  3. recomputes probe sequences under the new mask.

Copying the old byte layout into a larger array would not work: home positions and stopping points have changed. For nontrivial C++ types, a generic implementation must construct entries in the new storage, destroy the old ones exactly once, and specify what happens if moving or hashing throws.

Most flat tables invalidate references and iterators during rehash. Node-based tables can offer stronger stability at the price of an extra indirection. This is an interface choice with a direct physical cost.

#Clusters

Linear probing has an excellent inner loop. Sequential metadata and entries are friendly to hardware prefetching, and one cache line supplies several candidates. Its weakness is primary clustering: an occupied run attracts insertions whose home position is anywhere inside or immediately before that run, so long runs tend to grow longer.

As $\alpha$ approaches one, the problem is not just that the average search grows. The tail becomes unpleasant: an occasional missing key scans a large fraction of the table. Lowering the maximum load factor buys empty stopping points, but also consumes memory and enlarges the working set.

Probe length should therefore be a first-class benchmark statistic. Average nanoseconds alone can hide whether a table is predictably fast or usually fast.

#Robin Hood Hashing

Robin Hood hashing, introduced by Celis, Larson, and Munro, reduces the variance of probe lengths. Each resident entry has a displacement—the distance from its home slot. During insertion, the entry with the larger displacement keeps the current slot:

incoming displacement = 0

for each slot:
    if slot is empty:
        place incoming entry; stop

    resident displacement = distance(resident home, slot)
    if resident displacement < incoming displacement:
        swap resident and incoming entries
        incoming displacement = resident displacement

    advance; incoming displacement += 1

The metaphor is accurate: an unlucky key that has travelled far “steals” a position from a richer key that is still close to home. This does not abolish collisions or change the expected asymptotic bound. It makes displacement more even, which improves the tail and enables another lookup rule.

With ordinary Robin Hood insertion and no tombstones, a lookup can use the displacement invariant directly. If it has travelled distance $d$ and meets an entry whose displacement is less than $d$, the searched key cannot occur later: had it been present, Robin Hood insertion would not have allowed this less-displaced entry to precede it. The lookup can therefore terminate before reaching an empty slot.

Deletion must preserve that invariant. A standard solution is backward-shift deletion: after removing an entry, repeatedly move the following entry one slot backward until reaching an empty slot or an entry at its home position. Simply dropping a tombstone into the sequence and continuing to use early termination can produce false negatives unless the metadata and search rule are redesigned together.

Robin Hood insertion also moves existing objects. For large or nontrivially movable values, this may cost more than the saved probes. A common response is to keep small keys or indices in the flat table and store large payloads elsewhere.

#One Byte of Control

So far, testing a slot may require loading the entire key. A more cache-efficient design stores a small control byte separately for every slot:

control:  [e][3a][d][17][e][e][62][...]
entries:  [ ][ K][ ][ K][ ][ ][ K][...]

e  = empty
d  = deleted
xx = full, with a small hash fingerprint

Split a wide hash into two parts:

  • H1 chooses the initial group;
  • H2, commonly seven bits, is stored in the control byte as a fingerprint.

To search a group, broadcast H2, compare it with 16 or 32 adjacent control bytes, and turn the result into a bit mask. Only matching bits require full key comparisons. A second mask reports empty bytes; if no candidate matches and the group contains an empty slot, an unsuccessful lookup can stop.

Conceptually, the hot loop becomes:

for (group g : probe_sequence(H1)) {
    unsigned candidates = match_fingerprint(g.control, H2);
    while (candidates) {
        unsigned lane = std::countr_zero(candidates);
        if (entries[g.start + lane].key == key)
            return &entries[g.start + lane].value;
        candidates &= candidates - 1;
    }
    if (match_empty(g.control) != 0)
        return not_found;
}

The exact SIMD operations, group width, sentinel bytes at the end of the allocation, and probe permutation are implementation details that must agree. Wrapping a vector load past the array end is not justified because the logical probe wraps; production tables either clone a control-byte suffix, pad the allocation, or handle the boundary explicitly.

This design is often called a Swiss table. The official Abseil Swiss Tables design notes describe the one-byte metadata, H1/H2 split, SIMD candidate mask, and the crucial distinction between an empty byte, which stops a search, and a deleted byte, which does not.

The fingerprint is only a filter. Seven equal hash bits do not prove key equality, and a poor hash that lacks entropy in H2 turns every group into many full key comparisons. Hash quality now affects both home positions and metadata selectivity.

#Metadata updates

Control bytes make the state machine explicit, which is good, but they do not remove its obligations:

  • publish an entry as FULL only after its key and value have been constructed;
  • destroy the object before marking a full slot deleted;
  • decrement deleted when a tombstone is reused;
  • base growth on size + deleted;
  • rebuild before there is no empty group;
  • never treat the sentinel or cloned suffix as real capacity.

These orderings are still not enough for lock-free concurrency. A normal flat table permits no simultaneous mutation and lookup without external synchronization; data races remain undefined behavior even if a control byte happens to fit in one machine store.

#Layout Choices

For a map, keys and values can be stored together:

struct entry { Key key; Value value; };

or in separate arrays. An array of structures needs one address computation and gives good locality when every successful lookup consumes the value. Separate arrays avoid fetching large values during unsuccessful searches and can make relocation of keys or indices cheaper. This is the same AoS versus SoA tradeoff seen elsewhere.

Alignment and padding matter. A nominal (uint32_t, uint64_t) entry may occupy 16 bytes, not 12, while a one-byte control array adds only one byte per slot. On the other hand, storing huge values inline makes rehashes and Robin Hood swaps expensive. There is no universally “flat” answer; sometimes the right table is flat metadata and keys pointing to stable payload nodes.

#Hashing and the Adversary

Power-of-two tables expose weak low bits immediately. Before masking, mix integer keys with an avalanche-style function or use a library hash designed for the table. Strings need a real string hash, not a few selected characters. Hashing itself can dominate tiny lookups, so benchmark it separately.

Non-cryptographic mixing assumes benign input. If an attacker can choose keys and observe behavior, collision attacks can turn expected constant time into linear work. Use a keyed, denial-of-service-resistant hash or a container that provides one. Re-seeding on rehash can also make stored hash values and serialized layouts process-specific; that should be an explicit contract rather than an accident.

#Evaluation

Hash table benchmarks are exceptionally sensitive to workload. At minimum, vary:

  • table size across cache levels;
  • load factor and tombstone ratio;
  • successful versus unsuccessful lookup rate;
  • insertion, replacement, and erasure mix;
  • key and value sizes;
  • hash cost and key distribution;
  • reserved capacity versus repeated growth;
  • warm and cold caches.

Report probe-count distributions alongside time. Include memory per live entry, because buying speed with a four-times-larger table may lose once the working set crosses a cache boundary. Keep the same hash function when comparing layouts, or report hashing as part of the difference.

The historical companion experiments for this chapter compare chaining, linear probing, Robin Hood insertion, and a 32-byte AVX2 control group on a Zen 2-era setup. They correctly reveal the progression from pointer chasing to contiguous probes to metadata filtering, but the sketches use a half- or three-quarter-full table, identity-like hashing, fixed integer sentinels, and synthetic random queries. Some also count replacements as new insertions and omit production deletion semantics. Their measurements are therefore evidence about that experiment, not a general speedup claim.

A stronger validation harness runs each operation against std::unordered_map or a simple sorted reference map, checking the entire contents after randomized sequences. It should force hash collisions, repeatedly erase and reinsert, replace existing keys, cross every growth threshold, use keys equal to any tempting sentinel value, and finish with missing-key lookups in a tombstone-heavy table.

#Choosing a Table

The design space can be summarized without crowning one winner:

LayoutMain advantageMain cost
Separate chainingstable nodes, simple deletionpointers, allocation, poor locality
Linear probingcompact and cache-friendlyclustering and long negative probes
Robin Hoodtighter probe-length distributionmoved entries, deletion complexity
Control-byte groupsmany cheap rejections per loadextra metadata and a more complex state machine

Use a mature implementation when the container is infrastructure. But when a hash table is the bottleneck, “expected $O(1)$” is only the beginning of the investigation. The useful questions are how many cache lines a miss touches, how the search knows it is over, and what yesterday’s deletions make today’s lookup do.
