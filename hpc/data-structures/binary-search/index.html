Binary Search

Binary search is short enough to memorize and subtle enough to keep producing bugs. Performance work magnifies both properties: removing one branch is useful only if the replacement still handles an empty range, duplicate keys, and the past-the-end answer.

This chapter keeps one contract throughout. Given a sorted array a and a key x, lower_bound returns the first index i such that a[i] is not less than x. The answer belongs to the half-open set $[0,n+1)$: it is n when no such element exists, including when $n=0$.

#A Half-Open Search

The clean reference implementation maintains a half-open candidate interval. first is its beginning and count is its length:

#include <algorithm>
#include <cstddef>
#include <cstdint>
#include <functional>
#include <limits>
#include <span>
#include <stdexcept>
#include <vector>

template <class T, class U, class Less = std::less<>>
std::size_t lower_bound_index(std::span<const T> values,
                              const U& key,
                              Less less = {}) {
    std::size_t first = 0;
    std::size_t count = values.size();

    while (count != 0) {
        const std::size_t step = count / 2;
        const std::size_t middle = first + step;

        if (less(values[middle], key)) {
            first = middle + 1;
            count -= step + 1;
        } else {
            count = step;
        }
    }

    return first;
}

std::size_t branchless_lower_bound_index(
    std::span<const std::int64_t> values,
    std::int64_t key
) {
    if (values.empty())
        return 0;

    std::size_t base = 0;
    std::size_t length = values.size();

    while (length > 1) {
        const std::size_t half = length / 2;
        const bool move_right = values[base + half - 1] < key;
        base += static_cast<std::size_t>(move_right) * half;
        length -= half;
    }

    return base + static_cast<std::size_t>(values[base] < key);
}

The reference version never forms n - 1, so an empty range needs no special representation. The midpoint first + count / 2 cannot overflow because both terms describe positions inside the original span. Duplicate values go left, which is precisely what distinguishes lower_bound from upper_bound.

The second function uses a less conventional invariant. Each iteration keeps the leftmost surviving candidate at base and rounds the remaining length upward. The final comparison is essential: it turns the last element into the past-the-end index when every value is less than the key. Omitting it is a common way to make a fast search that cannot represent n.

The multiplication by a Boolean expresses predication, but C++ does not promise a conditional move. A compiler may still emit a branch, and whether that is faster depends on the target and query distribution. Inspect the generated code and measure it; source code is not a pipeline diagram. The relevant mechanisms are covered in branchless programming and branch prediction.

#The Dependency Chain

For uniformly distributed independent queries, the left/right decision is difficult to predict. A branch miss can then dominate searches whose working set is resident in cache. Once the array is large, another dependency becomes more important: the next address is unknown until the current key arrives and the comparison finishes.

This is why binary search exposes latency rather than bandwidth. It reads only $O(\log n)$ values, but those reads are mostly serial. Speculation sometimes helps a branchy implementation by issuing a load down the predicted path. A branchless implementation removes the misprediction and may also remove that accidental prefetch.

The access probabilities are far from uniform. The first midpoint is read by every query, its two children by roughly half the queries each, and the leaves only rarely. A sorted array stores these hot and cold keys beside one another:

The final few probes have useful spatial locality, while the first levels have useful temporal locality. A layout optimized for one usually sacrifices some of the other.

#Eytzinger Layout

The Eytzinger layout stores the comparison tree in breadth-first order. With one-based indices, the root is 1 and the children of node k are 2k and 2k+1:

Breadth-first storage puts the frequently accessed upper levels together. It also places all descendants exactly $d$ levels below node k in the contiguous interval

$$ [2^d k,\;2^d k+2^d). $$

That interval is the reason software prefetching becomes attractive: one cache-line request can cover several possible future paths.

#Construction and Search

An in-order traversal of the implicit tree consumes the sorted input from left to right. The reference implementation below stores the original rank beside every node. Remembering the best node seen during the descent is less clever than recovering it from trailing bits, but it handles every size without a sentinel or an overflowing child index.

class eytzinger_index {
public:
    explicit eytzinger_index(
        std::span<const std::int64_t> sorted_values
    ) : size_(sorted_values.size()) {
        if (!std::is_sorted(sorted_values.begin(), sorted_values.end()))
            throw std::invalid_argument("input must be sorted");
        if (size_ == std::numeric_limits<std::size_t>::max())
            throw std::length_error("index size overflow");

        tree_.resize(size_ + 1);
        rank_.resize(size_ + 1);

        std::size_t cursor = 0;
        build(1, sorted_values, cursor);
        if (cursor != size_)
            throw std::logic_error("Eytzinger construction failed");
    }

    std::size_t lower_bound_index(std::int64_t key) const noexcept {
        std::size_t node = 1;
        std::size_t candidate = 0;

        while (node <= size_) {
            prefetch_descendants(node);

            const bool go_right = tree_[node] < key;
            if (!go_right)
                candidate = node;

            const std::size_t direction =
                static_cast<std::size_t>(go_right);
            if (node > (size_ - direction) / 2)
                break;
            node = node * 2 + direction;
        }

        return candidate == 0 ? size_ : rank_[candidate];
    }

    std::size_t size() const noexcept {
        return size_;
    }

private:
    static constexpr std::size_t prefetch_distance = 16;

    void build(std::size_t node,
               std::span<const std::int64_t> sorted_values,
               std::size_t& cursor) {
        if (node > size_)
            return;

        if (node <= size_ / 2)
            build(node * 2, sorted_values, cursor);

        tree_[node] = sorted_values[cursor];
        rank_[node] = cursor;
        ++cursor;

        if (node <= (size_ - 1) / 2)
            build(node * 2 + 1, sorted_values, cursor);
    }

    void prefetch_descendants(std::size_t node) const noexcept {
#if defined(__GNUC__) || defined(__clang__)
        if (node <= size_ / prefetch_distance) {
            __builtin_prefetch(
                tree_.data() + node * prefetch_distance,
                0,
                1
            );
        }
#else
        static_cast<void>(node);
#endif
    }

    std::size_t size_;
    std::vector<std::int64_t> tree_;
    std::vector<std::size_t> rank_;
};

The recursion depth is the tree height, $O(\log n)$, rather than $O(n)$. Both child calculations are guarded before multiplication, so even a theoretical span near SIZE_MAX cannot wrap an index. For $n=0$, construction performs no traversal and lookup returns zero.

The prefetch address is formed only when 16 * node <= n. A prefetch instruction may be non-faulting on a particular processor, but C++ still has to evaluate its address expression; forming an arbitrary pointer beyond the allocation is not a portable bounds check. The guarded version requests the first great-great-grandchild only when that element exists.

Prefetching four levels ahead is a hypothesis, not part of correctness. It spends bandwidth and cache capacity to overlap latency, and it can lose under concurrent memory traffic. Remove it, change the distance, and benchmark again for each target.

#Padding, Sentinels, and Alignment

Padding a tree to a full final level gives every query the same number of iterations. The padding still needs a representation.

Using INT_MAX as “infinity” silently removes that value from the legal key domain. It also does not distinguish a real maximum key from a padded slot, and it says nothing useful for floating-point NaNs. Correct choices include:

  • storing a validity bit or a count with every node;
  • storing ranks and checking them against $n$;
  • restricting the key domain explicitly and enforcing that restriction at construction.

The reference Eytzinger index needs none of these because it never reads a nonexistent node and returns an index rather than a magic key.

Alignment is similarly a contract rather than a cast. A cache-line-aligned base makes the $16$ four-byte descendants beginning at 16k occupy one aligned 64-byte line. If std::aligned_alloc is used, its byte count must be a multiple of the requested alignment and the result must be released with std::free. Round only after checking that bytes + alignment - 1 cannot overflow. C++ aligned operator new avoids the multiple-of-alignment size rule, but it must be paired with the matching aligned operator delete. A zero-length index should not depend on either allocator accepting a zero-byte request.

Alignment can reduce split-line loads; it does not make an invalid prefetch valid, guarantee a 64-byte cache line, or enable huge pages. Those are separate alignment, cache-line, and paging questions.

#What to Measure

There is no timeless “binary search is four times faster” result. At minimum, a useful experiment reports:

  • processor, compiler, flags, integer width, and layout alignment;
  • array sizes on both sides of each cache and TLB boundary;
  • successful and unsuccessful queries, including duplicates and extreme keys;
  • the query distribution, because it determines branch predictability and hot nodes;
  • preprocessing time and extra memory for transformed layouts;
  • independent-query throughput separately from dependency-chained latency;
  • single-threaded results separately from bandwidth-contended runs.

Independent searches can overlap in the out-of-order core, so elapsed time divided by query count is reciprocal throughput, not single-query latency. To measure a dependency chain, derive query $i+1$ from result $i$; to measure service throughput, issue independent queries and say so.

Eytzinger order is one point in a larger design space that includes cache-line blocking, implicit B-trees, and van Emde Boas layouts. Khuong and Morin’s paper on array layouts for comparison-based searching analyzes several of them.
