Algorithmica βBitmaps

Bitmaps

Suppose we need to store a subset of the integers $0,1,\ldots,U-1$. A hash set stores the elements that are present. A bitmap stores one answer for every possible element: $$ B_i = [i \in S]. $$

This sounds wasteful until the universe is reasonably dense. Then the representation uses exactly $U$ bits, has no hashes or pointers, and answers membership with one indexed load. More importantly, one machine instruction can combine 64 membership answers at once. Set intersection becomes bitwise AND; union becomes OR; difference becomes AND NOT.

Bitmaps are therefore both a data structure and a form of word-level parallelism. They are used for graph frontiers, allocation maps, database indexes, dynamic programming states, visited sets, and as the storage layer of probabilistic filters.

#Packing the Bits

Using 64-bit words, bit $i$ lives in word $\lfloor i/64\rfloor$ at offset $i \bmod 64$:

#include <algorithm>
#include <bit>
#include <cstddef>
#include <cstdint>
#include <vector>

class bitmap {
    std::size_t bit_count_;
    std::vector<std::uint64_t> words_;

    void clear_unused_bits() {
        unsigned used = unsigned(bit_count_ & 63);
        if (used != 0)
            words_.back() &= (std::uint64_t(1) << used) - 1;
    }

public:
    explicit bitmap(std::size_t n)
        : bit_count_(n), words_((n + 63) / 64, 0) {}

    std::size_t size() const { return bit_count_; }

    bool test(std::size_t i) const {
        return (words_[i >> 6] >> (i & 63)) & 1;
    }

    void set(std::size_t i) {
        words_[i >> 6] |= std::uint64_t(1) << (i & 63);
    }

    void reset(std::size_t i) {
        words_[i >> 6] &= ~(std::uint64_t(1) << (i & 63));
    }

    void flip(std::size_t i) {
        words_[i >> 6] ^= std::uint64_t(1) << (i & 63);
    }

    void complement() {
        for (std::uint64_t &word : words_)
            word = ~word;
        if (!words_.empty())
            clear_unused_bits();
    }
};

The cast before the shift is essential. 1 << 40 shifts a 32-bit int on common platforms and is not a way to construct bit 40. The index is assumed to be in range; a public container can add checked access separately rather than putting a branch in every internal operation.

The final word introduces another invariant. If $U$ is not divisible by 64, some physical bits do not belong to the logical universe. They must remain zero after operations such as complement. Otherwise cardinality and iteration may report elements greater than or equal to $U$.

For $U=0$, the word vector is empty, so even tail cleanup must avoid touching back(). Small boundary conditions have a way of becoming large memory errors in bit manipulation code.

#Bulk Set Operations

If two bitmaps describe the same universe, their set operations are simple loops:

for (std::size_t i = 0; i != words; ++i)
    result[i] = left[i] & right[i];       // intersection

for (std::size_t i = 0; i != words; ++i)
    result[i] = left[i] | right[i];       // union

for (std::size_t i = 0; i != words; ++i)
    result[i] = left[i] & ~right[i];      // difference

for (std::size_t i = 0; i != words; ++i)
    result[i] = left[i] ^ right[i];       // symmetric difference

Each scalar iteration processes 64 elements. Compilers can also auto-vectorize these independent loops, processing several words per instruction. Once the arrays are large, however, there is little arithmetic left to optimize: reading two streams and writing one often makes the loop memory-bandwidth bound.

This changes how compound expressions should be evaluated. For

$$ R = (A \cap B) \cup (C \setminus D), $$

materializing both intermediate bitmaps performs unnecessary memory passes. Fuse the expression per word:

result[i] = (a[i] & b[i]) | (c[i] & ~d[i]);

The CPU has no difficulty with the Boolean algebra; it is the extra traffic that hurts. Alignment can help vector loads and stores, but a correctly written unaligned loop is often already close to the bandwidth limit. Use profiling before building a library of architecture-specific versions.

#Cardinality

The number of elements is the sum of population counts:

std::size_t cardinality(const std::vector<std::uint64_t> &words) {
    std::size_t result = 0;
    for (std::uint64_t word : words)
        result += std::popcount(word);
    return result;
}

std::popcount is C++20; on targets with a scalar population-count instruction it is normally compiled to that instruction. Wider ISAs may count several words at once, while older vector targets use lookup or arithmetic techniques. See SIMD reductions for the general pattern.

Maintaining cardinality eagerly makes count() constant time but adds work to updates. Setting a bit must first determine whether it was already set, and concurrent word updates need synchronization. A static query bitmap usually computes and caches counts; a write-heavy visited set often does not.

#Iterating over Set Bits

Scanning all $U$ positions throws away most of the benefit when the set is sparse. Instead, skip zero words and repeatedly remove the least significant set bit:

template <class Function>
void for_each_set_bit(const std::vector<std::uint64_t> &words,
                      Function function) {
    for (std::size_t i = 0; i != words.size(); ++i) {
        std::uint64_t x = words[i];
        while (x != 0) {
            unsigned bit = std::countr_zero(x);
            function(64 * i + bit);
            x &= x - 1;
        }
    }
}

The expression x & (x - 1) clears the lowest set bit. Calling countr_zero(0) would be invalid for several low-level intrinsics and gives the word width for the C++ function, so the nonzero loop condition is part of the algorithm, not decoration.

This traversal costs roughly one inner iteration per element plus one test per word. It is excellent for a sparse result and less attractive when nearly every bit is set; density can justify separate iteration paths.

The unused-tail-bits invariant now pays off again: the generic loop never needs to compare its generated index against the universe size.

#Rank and Select

Membership is not the only useful bitmap query. Two operations form the indexing vocabulary of succinct data structures:

  • $\operatorname{rank}_1(i)$ is the number of set bits in the prefix $[0,i)$;
  • $\operatorname{select}_1(k)$ is the position of the zero-indexed $k$-th set bit.

A raw bitmap answers rank by counting all complete words before $i$ and the relevant prefix of one word. That is linear in the number of preceding words. For a static bitmap, store prefix cardinalities:

class rank_index {
    const std::vector<std::uint64_t> &words_;
    std::vector<std::uint64_t> prefix_;  // prefix_[i] counts words [0, i)

public:
    explicit rank_index(const std::vector<std::uint64_t> &words)
        : words_(words), prefix_(words.size() + 1, 0) {
        for (std::size_t i = 0; i != words.size(); ++i)
            prefix_[i + 1] = prefix_[i] + std::popcount(words[i]);
    }

    std::uint64_t rank(std::size_t i) const {
        std::size_t word = i >> 6;
        unsigned offset = unsigned(i & 63);
        std::uint64_t result = prefix_[word];
        if (offset != 0) {
            std::uint64_t mask = (std::uint64_t(1) << offset) - 1;
            result += std::popcount(words_[word] & mask);
        }
        return result;
    }
};

The caller supplies $0 \le i \le U$. The definition uses a half-open prefix deliberately: rank(0) == 0, and rank(U) is the total cardinality.

One 64-bit prefix per 64-bit data word doubles the bitmap’s storage, which is often excessive. A practical compromise stores a wide cumulative counter once per large superblock and a small relative counter per smaller block. Rank then reads two counters and performs one popcount. By making the sampling hierarchy progressively sparser, the classic work beginning with Jacobson’s Succinct Static Data Structures supports constant-time rank and select with sublinear auxiliary space.

Select can use the same summaries in the opposite direction. First locate the block whose cumulative count straddles $k$, then locate the word, and finally select within that word. A simple static implementation binary-searches prefix_:

std::size_t select(const std::vector<std::uint64_t> &words,
                   const std::vector<std::uint64_t> &prefix,
                   std::uint64_t k) {
    // Precondition: k < prefix.back().
    auto it = std::upper_bound(prefix.begin(), prefix.end(), k);
    std::size_t word = std::size_t(it - prefix.begin() - 1);
    unsigned within = unsigned(k - prefix[word]);

    std::uint64_t x = words[word];
    while (within != 0) {
        x &= x - 1;
        --within;
    }

    return 64 * word + std::countr_zero(x);
}

This is $O(\log (U/64))$ for the binary search and at most 63 clear-lowest-bit steps. Faster word-select routines use broadword arithmetic or small tables. More important is choosing an index that matches the update model: every bit change invalidates a static prefix array, while a Fenwick tree or a hierarchy of mutable counters trades more update work and space for dynamic rank.

#When a Plain Bitmap Is Too Large

A bitmap pays for the universe, not for the set. If identifiers range over $[0,2^{64})$ and only a million occur, allocating one bit per possible identifier is not an option. The alternatives exploit one of three kinds of structure.

#Sparse positions

Store the set bits as a sorted array. Membership becomes binary search, iteration is trivial, and set intersection becomes a merge or a galloping search. Ignoring container overhead, $n$ values of $w$ bits use $nw$ bits instead of $U$. This wins when $n \ll U/w$; the exact crossover also includes cache behavior and the cost of the required operations.

An array is especially attractive when the set is static. Random insertion into its middle is expensive, while appending sorted values is cheap.

#Runs

Store intervals such as (start, length). A million consecutive set bits become one run; a million independently scattered bits become a million runs. Run-length formats are therefore excellent for sorted or clustered data and can expand on random data. Boolean operations must merge runs, so compressed size alone does not determine query speed.

#Chunked hybrid layouts

A hybrid chooses a representation locally instead of once for the whole universe. Roaring bitmaps partition a 32-bit integer by its high 16 bits. For each present high half, the low 16-bit values are represented by a container:

high 16 bits       low-half container

0x0001  ------->   sorted uint16_t array
0x0002  ------->   65,536-bit bitmap
0x17af  ------->   runs

A dense container occupies $2^{16}$ bits, or 8192 bytes. A sorted array of 4096 16-bit values also occupies 8192 bytes, which explains the natural transition near 4096 elements. Modern variants may use run containers when intervals are smaller still. The original and follow-up primary work reports the detailed array/bitmap/run algorithms and SIMD set operations; the important idea is that density is measured per chunk.

Operations then dispatch on a pair of container types:

  • bitmap–bitmap uses word-wise Boolean operations;
  • array–array uses merge, galloping, or vectorized intersection;
  • array–bitmap probes or sets the listed positions;
  • run combinations merge intervals or visit covered words.

The dispatch and top-level index add overhead, so a hybrid is not automatically better than a plain bitmap. It earns that complexity when the global universe is sparse but some local regions are dense, or when compressed size keeps more of the working set in cache.

#Updates and Concurrency

Setting different bits in the same word is not independent at the machine level: both operations are read-modify-write updates of one 64-bit location. Without atomics or a lock, simultaneous updates are a data race and may lose a bit. With atomics, contention and false sharing can serialize otherwise unrelated work.

Useful parallel strategies include partitioning the universe by word ranges, giving each worker a private bitmap and reducing them with OR, or using atomic fetch_or when updates are sparse enough. The right choice depends on whether memory bandwidth, synchronization, or the final reduction is dominant.

Serialization also needs a contract: record the logical bit count, word byte order, and representation version. Dumping the in-memory uint64_t array bakes host endianness into the file and loses the number of valid bits in the tail.

Do not choose from the table alone. Measure the operations your application performs, including the size of intermediate results. An intersection may turn two dense inputs into a sparse output; a query engine that keeps representing that result as a full bitmap can spend most of its time scanning zeros.

The central advantage of a bitmap is not merely that a Boolean value fits in one bit. It is that the layout turns set algebra into long, predictable streams of word operations. Compression is worthwhile when it preserves enough of that regularity while avoiding words that contain no information.
