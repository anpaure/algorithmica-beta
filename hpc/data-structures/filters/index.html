Probabilistic Filters

Suppose checking whether a key exists requires a disk read, a network request, or a lookup in a much larger data structure. Most queries are misses. A small in-memory structure that rejects almost all of those misses can save much more time than it costs, even if it occasionally says “maybe” and forces an unnecessary lookup.

This is an approximate membership filter. For a set $S$, it answers:

definitely absent     x is not in S
possibly present      x may or may not be in S

The asymmetry is the point. Under its stated contract, a filter has no false negatives: every inserted key produces “possibly present.” An absent key may also produce that answer, which is a false positive. The exact data structure remains the authority.

A filter does not store values, normally cannot enumerate its keys, and is not a cache. A cache hit can return the object itself; a filter hit only authorizes the expensive check. A filter miss is stronger than a cache miss because it rules the key out—provided that the filter is synchronized with the underlying set.

That proviso will follow us throughout the chapter. “No false negatives” assumes correct hashing, successful construction, no unsupported deletion, no data races, and no update that reached the database but not the filter.

#The Bloom Filter

Burton Bloom’s original 1970 paper describes the classic construction. Allocate a bitmap of $m$ initially zero bits and choose $k$ hash-derived positions for each key.

Insertion sets all $k$ bits:

for i = 0 .. k-1:
    B[h_i(x)] = 1

A query returns “possibly present” only if all $k$ bits are set. Clearing one of them is not safe: the same bit may have been set by several keys.

The representation is exceptionally compact. It is also a useful example of a data structure whose performance and error probability are inseparable: more probes can reduce false positives but require more hashing and memory accesses.

#Deriving the False-Positive Rate

Assume for the moment that all $kn$ bit choices made by $n$ inserted keys are independent and uniform. One particular bit remains zero with probability

$$ \left(1-\frac{1}{m}\right)^{kn} \approx e^{-kn/m}. $$ It is therefore one with probability approximately $1-e^{-kn/m}$. An absent query is a false positive when all of its $k$ positions are one: $$ p \approx \left(1-e^{-kn/m}\right)^k. $$

This is an approximation, not a per-instance guarantee. Bit states and probes are not perfectly independent, finite-size effects matter, and a real hash function is not a random oracle. It is nevertheless the standard and useful sizing model.

For fixed bits per key $b=m/n$, differentiating the expression gives the optimal real-valued number of probes:

$$ k^* = b \ln 2. $$ At that point about half of the bits are set, and $$ p_{\min} \approx 2^{-k^*} = (0.6185\ldots)^b. $$ Solving for the required storage and then rounding to implementable values gives $$ \frac{m}{n} = -\frac{\ln p}{(\ln 2)^2}, \qquad k \approx -\frac{\ln p}{\ln 2}. $$

For example, a target of one percent requires about $9.59$ bits per expected key and $k\approx6.64$, so seven probes is a reasonable starting point. Rounding the bitmap up and recomputing the expected rate with the actual $m$, $n$, and integer $k$ is better than quoting the continuous optimum.

Most importantly, $n$ is a capacity promise. If twice as many keys are inserted, the filter remains free of false negatives but its false-positive rate is no longer the advertised one. Filters should expose their design capacity, observed insertion count, and rebuild policy.

#A Small Implementation

Computing $k$ unrelated hashes is usually unnecessary. Kirsch and Mitzenmacher’s primary work, Less Hashing, Same Performance, analyzes positions of the form

$$ g_i(x) = h_1(x) + i h_2(x). $$

The following implementation accepts two already mixed 64-bit hashes. It uses a power-of-two bitmap and makes the step odd, so the probe sequence can visit every bit instead of cycling through a smaller power-of-two subset:

#include <bit>
#include <cstddef>
#include <cstdint>
#include <stdexcept>
#include <vector>

class bloom_filter {
    std::vector<std::uint64_t> words_;
    std::uint64_t bit_mask_;
    unsigned probes_;

public:
    bloom_filter(std::size_t bit_count, unsigned probes)
        : words_(bit_count / 64, 0),
          bit_mask_(bit_count - 1),
          probes_(probes) {
        if (bit_count < 64 || !std::has_single_bit(bit_count) ||
            probes == 0 || probes > bit_count)
            throw std::invalid_argument("invalid Bloom filter shape");
    }

    void add_hash(std::uint64_t h1, std::uint64_t h2) {
        h2 |= 1;  // a full-period step modulo a power of two
        for (unsigned i = 0; i != probes_; ++i) {
            std::uint64_t bit = h1 & bit_mask_;
            words_[bit >> 6] |= std::uint64_t(1) << (bit & 63);
            h1 += h2;  // unsigned wraparound is defined
        }
    }

    bool possibly_contains_hash(std::uint64_t h1, std::uint64_t h2) const {
        h2 |= 1;
        for (unsigned i = 0; i != probes_; ++i) {
            std::uint64_t bit = h1 & bit_mask_;
            if (((words_[bit >> 6] >> (bit & 63)) & 1) == 0)
                return false;
            h1 += h2;
        }
        return true;
    }
};

Rounding the bit count up to a power of two may spend substantially more memory than the mathematical minimum. A general implementation can use fast range reduction for arbitrary $m$; the power-of-two version keeps the state transition visible.

The two input hashes must contain good entropy. They can come from independently seeded hashes or the halves of a suitable wide hash. Feeding the raw key into both arguments, or deriving both from the same weak low bits, does not satisfy the model. For attacker-controlled keys, use keyed hashing and treat the published false-positive probability as a benign-input estimate, not a security guarantee.

The class is deliberately single-threaded. Concurrent insertions need atomic word updates or external partitioning, and readers must be synchronized with writers according to the publication contract.

#Why there is no erase

If key a and key b set the same bit, clearing it while deleting a creates a false negative for b. A basic Bloom filter is insert-only.

A counting Bloom filter replaces bits with small counters, incrementing on insertion and decrementing on deletion. This costs more space and introduces saturation, underflow, and duplicate-insertion semantics. It is safe only when deleting an element known to have been inserted with a matching count. Asking the approximate filter whether an arbitrary key is present is not enough permission to decrement: a false positive could damage another key.

When a workload needs deletion, a counting Bloom filter is one option; a cuckoo filter is another. Neither makes update consistency with the authoritative set disappear.

#The Memory-Access Problem

A classic Bloom query makes $k$ approximately random bit probes. If the filter fits in the last-level cache, this can be cheap. If it resides in RAM, the arithmetic may be dwarfed by several independent cache misses.

The misses do have memory-level parallelism, but a dependent hash pipeline, a small number of outstanding requests, or competition with the surrounding application can limit it. Increasing $k$ toward the mathematical optimum may therefore reduce the false-positive rate while making each query slower.

The real objective is system cost. If an absent key would trigger an operation costing $C$, the filter query costs $H$, and the false-positive probability is $p$, the expected cost for that absent key is

$$ H + pC. $$

The filter helps when $H < (1-p)C$. This is why an imperfect filter can be excellent in front of a disk and pointless in front of a tiny in-cache array.

#Blocked Bloom Filters

A blocked Bloom filter uses part of the hash to choose one small block—often sized around a cache line—and places all remaining probes inside that block:

hash(key) -> block number | positions within the block

The query then touches one local region instead of $k$ unrelated regions. The primary blocked-filter analysis by Putze, Sanders, and Singler explores this cache/hash/space tradeoff.

Locality is not free. Keys are distributed unevenly among blocks, so an unlucky block becomes fuller and has a higher false-positive rate. Positions inside a small block also have more correlation. A blocked filter generally needs different sizing from a classic Bloom filter to reach the same overall error target; substituting its block size into the classic formula is not a complete analysis.

Block size itself is hardware- and workload-dependent. One cache line avoids extra line fetches for an isolated query. Several smaller filters queried in a batch may benefit from different packing, and a concurrent writer may turn one popular line into a coherence hotspot.

#Cuckoo Filters

A cuckoo filter stores short fingerprints in small buckets rather than setting bits. For key $x$, compute a fingerprint $f$ and two candidate buckets:

$$ i_1 = h(x), \qquad i_2 = i_1 \oplus h(f). $$

The XOR construction is reversible: knowing one bucket and the fingerprint identifies the other. A lookup reads the two buckets and searches for $f$.

If a bucket uses the all-zero fingerprint to mean “empty,” construction must remap a zero fingerprint to a nonzero value or store occupancy separately. Otherwise a real key can disappear into the representation’s sentinel.

Insertion places the fingerprint in either bucket. If both are full, it evicts a resident fingerprint, moves that fingerprint to its alternate bucket, and continues. This is the familiar cuckoo-hashing walk. It can exceed a relocation limit, at which point the implementation must grow, rebuild with a new seed, place the item in a stash, or report failure. Silently dropping the fingerprint would create a false negative.

Deletion is possible by removing a matching fingerprint from either candidate bucket, but its contract is narrower than it first appears:

  • deleting a key that was not inserted can remove another key’s colliding fingerprint after a false-positive lookup;
  • duplicate keys require reference counts or set semantics established outside the filter;
  • concurrent relocation and lookup require a designed synchronization protocol.

Thus “supports deletion” means deletion of known inserted keys under the implementation’s duplicate policy.

Fingerprint width and bucket occupancy determine both space and false-positive probability. A rough intuition is that a query compares against up to twice the bucket size, each short fingerprint matching with probability around $2^{-f}$. The paper gives a fuller analysis; the simple product is not reliable near high occupancy or under correlated hashing.

Compared with a classic Bloom filter, the appeal is two localized bucket reads and dynamic deletion. The costs are a more complicated insertion path, possible construction failure, and sensitivity to high load.

#Xor Filters

An xor filter is built for a static set. It stores one $f$-bit value at each array position and maps a key to three positions. Construction chooses the stored values so that every member satisfies

$$ F[h_0(x)] \oplus F[h_1(x)] \oplus F[h_2(x)] = \operatorname{fingerprint}(x). $$

A query reads three values, XORs them, and compares the result with the key’s fingerprint. An absent key matches with probability close to $2^{-f}$ under the hashing model.

The interesting work happens during construction. The three positions define a random hypergraph. The builder repeatedly removes a key incident to a position of degree one, records that peeling order, and assigns fingerprints in reverse. Sometimes the graph cannot be fully peeled; construction then retries with a new seed or a larger array. Input keys should be deduplicated before building.

The primary xor-filter paper by Graf and Lemire evaluates this design against Bloom and cuckoo filters. Its attractive query path does not make it a general replacement: adding or deleting a key normally requires rebuilding the filter, and construction needs temporary storage for the key set and graph state.

Xor filters are therefore well matched to immutable database segments, index files, and periodically rebuilt snapshots. They are poorly matched to a stream that must become visible one insertion at a time.

The table deliberately omits a universal “fastest” or “smallest” column. Results change with false-positive target, filter size relative to caches, hash cost, batch size, instruction set, load factor, and update mix. A structure that saves one bit per key may be slower if it adds a dependent cache miss; a filter with a higher false-positive rate may win if the protected operation is cheap.

There are many further designs—quotient filters, ribbon filters, binary fuse filters, and others—but they can be evaluated with the same questions:

  1. What exactly is the false-negative contract?
  2. What hash-independence model supports the advertised false-positive rate?
  3. How many independent memory regions does a query touch?
  4. Can insertion or construction fail, and how is failure surfaced?
  5. Which updates are supported without damaging other keys?
  6. What happens when actual cardinality exceeds planned capacity?

#Engineering the Whole System

#Hash once when possible

If the authoritative hash table already computes a high-quality wide hash, the filter may reuse carefully separated bits or derived values. This can save substantial work, but only when both structures document the coupling. Changing a seed, hash version, or serialization format must rebuild the filter.

Fingerprints are not cryptographic authenticators. They are deliberately short and collisions are expected.

#Batch queries

Several independent filter queries expose memory-level parallelism. Software can compute their hashes, issue block or bucket loads, and finish earlier queries while later data arrives. This is often more portable than trying to vectorize a single query whose addresses are data-dependent.

#Publish updates in the safe order

If a filter fronts a database, inserting into the filter before committing the database can temporarily create a false positive, which is normally harmless. Committing the database first and delaying the filter can create a false negative, which violates the reason the filter exists. Deletion has the safe order reversed: remove the authoritative key first and clean up a deletion-capable filter afterward, leaving only a temporary false positive. Recovery and distributed replication make these orderings more complicated; they belong in the system contract.

For immutable segments, publish the data and its completely built filter as one versioned unit. For mutable structures, rebuilds commonly create a new filter beside the old one and switch readers only after it is complete.

#Serialize the parameters

A persisted filter needs its type, bit/fingerprint width, number of probes, capacity, hash algorithm and seed, byte order, and format version. Storing only the bitmap produces an object that may look valid and answer every query incorrectly after a software upgrade.

#Validation and Benchmarking

First test the absolute property: every inserted key must query positive after every supported operation. Exercise zero keys, duplicate keys, rebuilds, full-capacity behavior, failed construction, and deletion according to the documented preconditions.

Then estimate false positives on keys independently drawn from the query distribution. Report the number of trials and uncertainty, not just a percentage. A filter tuned on random 64-bit integers may behave differently on structured strings if the hash or seeding is weak.

Finally measure the complete path:

  • present and absent queries separately;
  • filter sizes below and above each cache level;
  • scalar and batched access;
  • hash time included and excluded;
  • the latency of the protected operation;
  • insertion, rebuild, and peak construction memory;
  • actual cardinality versus design capacity.

The false-positive formula predicts wasted authoritative lookups, while the benchmark measures how expensive the prediction machinery is. A good filter minimizes their sum. Its most valuable answer is still the cheap one: “do not look any further.”
