Theoretical Performance Limits

After optimizing a loop for long enough, every remaining instruction starts to look suspicious. This is a good time to stop asking “what else can I change?” and ask a sharper question: “what physical resource could make this version faster?”

A performance bound does not predict exactly how long a program will run. It proves that, under stated assumptions, it cannot run faster than some limit. Comparing several bounds often reveals which resource deserves attention and which proposed optimization cannot matter yet.

#A Maximum of Lower Bounds

Suppose one loop iteration needs:

  • $U$ uops delivered by a front-end capable of $F$ uops per cycle;
  • $N_r$ uses of each execution resource $r$, which accepts $C_r$ relevant uops per cycle;
  • a loop-carried dependency with latency $D$ cycles;
  • $Q_k$ bytes transferred through each memory boundary $k$, whose sustainable bandwidth is $B_k$ bytes per cycle.

Ignoring interactions for a moment, cycles per iteration are bounded below by

$$ T \ge \max\left( \frac{U}{F}, \max_r \frac{N_r}{C_r}, D, \max_k \frac{Q_k}{B_k} \right). $$

The maximum is important. Front-end work, arithmetic, and memory transfers can overlap, so adding all their isolated costs is usually too pessimistic. Yet none of the individual limits can be violated. If stores require at least one cycle per iteration, a hypothetical zero-cycle addition does not make the loop faster.

This model is still an approximation. A uop may be eligible for several ports, resources can be shared in complicated ways, and burst bandwidth differs from sustained bandwidth. Its purpose is to identify a candidate bottleneck that can be tested.

#Front-End and Execution Limits

The front-end has finite fetch, decode, and delivery bandwidth. Large instructions may cross fetch boundaries; branches can interrupt the stream; code that does not fit in the instruction cache or decoded-uop cache adds further delays. For a compact hot loop, the simplest bound is its delivered uop count divided by front-end width.

In the back-end, count resource demand rather than assembly lines. One x86 instruction may decompose into multiple uops, while fusion can let parts travel together through some stages. Each uop can use a particular set of execution resources. The tight resource bound is the best feasible assignment of these uops to their eligible resources, not merely the count of whichever mnemonic looks most exotic.

Instruction latency creates a different limit. In

s = ((s + x0) + x1) + x2;

each addition needs the previous result. If the relevant addition latency is one cycle, this recurrence cannot advance more than once per cycle regardless of how many add units exist. Splitting a reduction across independent accumulators changes the dependency graph and can approach the throughput limit, as discussed in Throughput Computing.

Static tools can estimate these bounds. llvm-mca reports a block reciprocal throughput and resource pressure from LLVM’s scheduling model. It assumes an idealized surrounding loop and optimistic memory behavior, so it is a ceiling calculation, not a stopwatch.

#Bandwidth: The Roofline Bound

Let an implementation perform $W$ useful operations and transfer $Q$ bytes across a chosen memory boundary. If peak relevant compute throughput is $C$ operations per second and sustainable bandwidth is $B$ bytes per second, then

$$ T \ge \max\left(\frac{W}{C}, \frac{Q}{B}\right). $$ Define operational intensity $I = W/Q$ and performance $P = W/T$. Rearranging gives $$ P \le \min(C, B \cdot I). $$

This is the basic Roofline model. At low intensity, the sloped bandwidth roof dominates. At high intensity, the flat compute roof dominates. Their intersection is the intensity required to make peak computation relevant.

For example, consider addition of two arrays of 32-bit values:

#include <cstddef>
#include <cstdint>

void add(const std::uint32_t* a, const std::uint32_t* b,
         std::uint32_t* c, std::size_t n) {
    for (std::size_t i = 0; i < n; ++i)
        c[i] = a[i] + b[i];
}

Each element performs one integer addition and logically transfers at least eight input bytes plus four output bytes. This is low operational intensity. SIMD reduces instruction overhead and raises the compute ceiling, but it does not reduce those twelve logical bytes. Once the relevant memory bandwidth is saturated, wider arithmetic alone has nowhere to obtain more data.

Actual traffic may be higher because of write allocation, imperfect locality, or unrelated users of the cache. It may be lower at a deeper memory boundary when data is reused in cache. Always state whether $Q$ describes source-level bytes, L1 traffic, last-level-cache traffic, or DRAM traffic.

#Latency and Memory-Level Parallelism

Bandwidth says how many bytes can arrive over time; latency says how long one request takes. A sequential scan can keep many cache misses in flight, allowing their latencies to overlap. A linked-list traversal cannot request node $i+1$ until node $i$ reveals its address.

If a computation performs $N$ long-latency requests, each taking approximately $L$ cycles, and can sustain at most $K$ independent requests at once, then a rough lower bound is

$$ T \ge \frac{N \cdot L}{K}. $$

For a strict dependency chain, $K=1$. For several independent streams, $K$ may grow until load queues, miss-status buffers, translation resources, or bandwidth become limiting. Prefetching and restructuring pointer-based data do not make memory intrinsically faster; they try to increase $K$ or arrange for requests to begin earlier.

This explains why “the data fits in bandwidth” is not enough. A workload can consume little total bandwidth and still be completely latency-bound.

#Branches and Other Ceilings

Unpredictable control flow adds another workload-dependent limit. If a branch is mispredicted, younger wrong-path work is discarded and useful instruction delivery is interrupted. Unlike an execution-port count, this cost cannot be derived from the static instruction mix alone: it depends on data and branch history. Measure the misprediction rate on the intended workload, then compare a branchy implementation with the extra work and dependency cost of a branchless one.

Other ceilings include instruction-cache capacity, translation bandwidth, store-buffer capacity, and limits imposed by the algorithm itself. Comparison sorting, for example, has a comparison lower bound independent of how quickly the CPU can execute one comparison. A hardware limit and an algorithmic lower bound can both be true; the larger one controls the current implementation.

#Peak Is Not Attainable Performance

Published peak throughput assumes a favorable instruction mix, enough independent work, suitable vector width, and data already arriving at the required rate. Real code may use an instruction supported by only one unit, mix loads and stores that contend for address-generation resources, or fail to expose enough parallelism.

Frequency is not constant either. Vector width, power limits, temperature, active cores, and host policy can change it. Shared caches and memory channels introduce competition. For this reason, use measured sustainable bandwidth and the frequency observed during the benchmark when constructing a practical bound.

A disciplined analysis proceeds as follows:

  1. Pick the unit: one query, one element, one byte, or one loop iteration.
  2. Draw true dependencies and identify the longest recurrence.
  3. Count uops and demand on constrained execution resources.
  4. Count bytes at the memory boundary relevant to the working set.
  5. Compute several lower bounds and take their maximum.
  6. Measure hardware events to check whether the predicted resource is actually saturated.

If performance is far below every plausible bound, the model is missing something. If it is close to one bound, optimize that resource or change the algorithm so the bound itself moves. Once another bound becomes larger, stop polishing the old bottleneck. It has already done all the damage it can.
