Instruction Scheduling

Consider the following function:

#include <cstdint>

std::uint64_t f(std::uint64_t a, std::uint64_t b,
                std::uint64_t c, std::uint64_t d) {
    return (a + 1) * (b + 1) + (c + 1) * (d + 1);
}

Written as a sentence, it appears to request four additions, then one multiplication, then another multiplication, then a final addition. The data dependencies tell a different story. The two products are independent: either can be computed first, and on a suitable processor they can progress at the same time. Only the final addition needs both.

Modern CPUs schedule the dependency graph, not the punctuation of the source code.

#From Instructions to Operations

The front-end fetches and decodes machine instructions. On x86, many instructions translate into one or more simpler internal operations, commonly called micro-operations or uops. A register addition may become one uop; a read-modify-write instruction may require address generation, a load, arithmetic, and a store; sufficiently complex instructions may be supplied by a microcode sequencer.

This does not mean that the x86 instruction set is secretly replaced with one universal internal language. Uop formats and fusion rules are properties of a particular microarchitecture. The useful abstraction is merely that execution resources usually schedule finer-grained operations than the assembly listing suggests.

Decoded uops enter a bounded out-of-order part of the core. Names vary between vendors and generations, but the mechanism has a few recurring pieces:

  1. register renaming creates a new physical destination for each register-writing operation;
  2. a reorder buffer tracks operations in program order;
  3. scheduling queues hold operations until their inputs and an appropriate execution resource are available;
  4. load and store queues track memory operations;
  5. completed operations retire in program order.

The Intel optimization manual documents concrete instances of these structures. Their exact sizes and grouping are implementation details; code should not assume that every x86 CPU has one scheduler with the same shape.

#Register Renaming

An architectural register such as rax is a name in the instruction-set interface, not necessarily one fixed storage cell throughout execution. Suppose three instructions successively assign rax. The renamer can map their results to three physical registers and remember which version each later input needs.

This removes two kinds of false dependency:

  • write after read: a later write need not wait merely because an older operation still needs the previous value;
  • write after write: two outputs can be computed independently and made visible in the required order later.

A true read-after-write dependency remains. Renaming can give (a + 1) and (c + 1) different homes, but it cannot multiply a + 1 by b + 1 before either value exists.

Renaming is also finite. Every in-flight destination consumes a physical register until the old mapping can be reclaimed. Excessive unrolling can exhaust this and other bookkeeping capacity even when the source language offers an unlimited supply of variable names.

#Wake Up, Select, Execute

After dispatch, an operation waits until its input operands are ready. It then becomes a candidate for an execution resource capable of handling it. Each cycle, scheduling logic selects from the ready candidates, subject to issue width and resource availability.

This is dynamic scheduling: the decision reflects events only known at runtime, such as cache hits, cache misses, and the actual progress of older operations. If one product in our example waits for an operand while the other is ready, the ready product may issue first even if it appeared later in machine code.

Execution resources are commonly connected through ports or similar routing structures. Different uops can use different subsets of them. Two instructions with equal latency may therefore have very different effects on throughput: one may have several eligible units, while another monopolizes a single specialized unit. This is why an instruction table needs both latency and reciprocal throughput, and why port pressure matters for loops.

The scheduler is not omniscient. It sees only operations already admitted to its finite window. A long dependency chain, full reorder buffer, exhausted load queue, or unresolved branch can prevent useful future work from entering the window.

#Memory Scheduling

Registers carry explicit dependencies; memory addresses must be compared or predicted.

Stores are kept until the processor can make them architecturally visible in the required order. Loads may execute before older stores when the processor determines, or predicts, that their addresses do not overlap. If an address later proves the prediction wrong, dependent operations are replayed.

There is another useful kind of speculation here. A cache miss does not normally stop all execution. Independent loads and arithmetic can continue while the missing line is requested. This memory-level parallelism is limited by dependencies and by finite tracking structures. Pointer chasing performs poorly because each missing load reveals the address of the next one too late to overlap them.

Memory-ordering rules, fences, device memory, and atomic operations impose additional constraints. Static analyzers often model only a subset of them, so a beautifully scheduled report is not evidence that the cache will cooperate.

#Retirement and Precise State

If operations execute out of order, why do exceptions not expose a half-finished future?

The processor separates execution from retirement. Results can be computed and forwarded speculatively, but operations retire in program order. If a branch was mispredicted or an older instruction faults, younger operations can be discarded before their speculative state becomes architecturally visible. The machine then appears to have executed up to one precise point in the original instruction stream.

Stores require special care because writing cache-visible memory is difficult to undo. Their addresses and data may be prepared early, but ordinary stores are committed only when they are safe to retire.

In-order retirement is itself a finite resource. A slow old instruction can occupy the head of the reorder buffer while many younger instructions have finished behind it. Once the window fills, the front-end must wait even if execution units would otherwise be available.

#The Compiler’s Part

Hardware scheduling is automatic, but software determines which opportunities it can see.

The compiler can reorder independent instructions, unroll loops, use several accumulators, and choose instructions with suitable resource usage. It can do this only when language rules and alias information prove the transformation correct. A possible pointer overlap or strict floating-point order may create dependencies at compile time even when a particular dataset would have allowed more freedom.

The processor then adapts the resulting instruction stream to runtime events. These roles complement each other:

  • the compiler has broad program context but limited runtime information;
  • the CPU has exact runtime timing but only a small future window.

Hand scheduling every instruction is rarely useful on out-of-order CPUs, and a sequence tuned for one core may be poor on another. The durable goal is to expose independent work without creating excessive code size, register pressure, or memory traffic.

For a small loop, llvm-mca can estimate dependencies, reciprocal throughput, and resource pressure using LLVM’s processor scheduling models. Its own documentation is explicit about the limitations: the default analysis does not model instruction fetch, branch prediction, or real cache behavior. Use it to test a scheduling hypothesis, then verify that hypothesis with measurements on the target machine.

Once independent operations are available, the next question is how many parallel chains are required to keep a pipelined execution unit busy. That is the subject of throughput computing.
