Pipeline Hazards

Pipelining overlaps different stages of several instructions. This raises an immediate question: what happens when the next instruction cannot advance?

On a simple in-order pipeline, the answer may be a literal stall: hold one or more stages until the obstruction disappears, leaving an unused slot traditionally called a bubble. Modern out-of-order processors are less dramatic. They keep many decoded operations in flight, wait only where a dependency or resource requires it, and continue issuing unrelated work when possible.

The traditional taxonomy is still useful, provided we do not imagine that every hazard freezes the entire core.

#Structural Hazards

A structural hazard occurs when several operations need the same finite resource. They may compete for a decoder, an execution unit, a load port, an entry in a scheduling queue, or retirement bandwidth.

If two ready operations both need a resource that accepts only one of them, one waits. Other independent operations using different resources may still execute. When a queue is completely full, the obstruction can propagate backward and eventually stop the front-end from admitting more work.

Structural limits determine steady-state throughput. We handle them by reducing pressure on the busy resource, selecting instructions that can use other resources, or doing more useful work per operation. Instruction tables and machine-code analyzers help identify these limits.

#Data Hazards

A data hazard occurs when ordering is required to preserve values.

The unavoidable case is a read-after-write dependency: if instruction B consumes the result of instruction A, B cannot execute before that result exists. A chain of such dependencies forms a critical path, and its latency cannot be hidden by executing more copies of the dependent operation.

Two other textbook cases, write-after-read and write-after-write, often arise only because instructions reuse the same architectural register name. Modern processors map these names to a larger set of physical registers, a technique called register renaming. Different logical versions then occupy different physical locations, removing the false dependency.

Memory is harder. A younger load may or may not refer to the same address as an older store. The processor predicts or checks this relationship using its load/store machinery; a wrong guess requires replaying affected work. Compilers face a similar problem when they cannot prove that two pointers do not alias.

Data hazards are addressed by shortening dependency chains or exposing independent work. Throughput computing develops this idea using multiple accumulators.

#Control Hazards

A control hazard occurs when the processor does not yet know which instruction should come next. Conditional branches, indirect jumps, calls, and returns all affect the future instruction stream.

Rather than waiting, the front-end predicts a destination and continues fetching and executing speculatively. A correct prediction hides most of the uncertainty. A wrong prediction discards the younger wrong-path operations, redirects the front-end, and reconstructs the correct stream. Older instructions are not erased, and the penalty is not simply “the number of pipeline stages”: it depends on when the branch resolves, how much useful work was in flight, and the microarchitecture.

Control hazards are reduced by making branches easier to predict, resolving them earlier, or replacing them with data flow when computing both alternatives is cheaper. The trade-off is explored in The Cost of Branching and Branchless Programming.

The common theme is lack of usable parallel work. A resource is busy, an operand is unavailable, or the next instruction is uncertain. Out-of-order execution can search around a local obstruction, but only inside a finite window. Understanding how that search works is the purpose of instruction scheduling.
