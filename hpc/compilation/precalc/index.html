Precomputation

When a compiler can prove that a value does not depend on runtime input, it may calculate the value during compilation and embed the result into the program. This optimization is called constant folding.

Constant folding is permitted by the C++ as-if rule, but it is not guaranteed merely because all arguments happen to be literals. A compiler may decide that a computation is too expensive to perform while compiling, or may simply miss the opportunity.

#Constant Expressions

The constexpr specifier allows a function to participate in constant evaluation:

#include <cstdint>

constexpr std::uint64_t fibonacci(unsigned n) {
    std::uint64_t a = 0, b = 1;
    for (unsigned i = 0; i < n; ++i) {
        std::uint64_t next = a + b;
        a = b;
        b = next;
    }
    return a;
}

static_assert(fibonacci(10) == 55);

The static_assert requires a constant expression, so this particular call must be evaluated during translation. A constexpr function can also be called with runtime data, in which case it behaves like an ordinary function:

std::uint64_t runtime_fibonacci(unsigned n) {
    return fibonacci(n); // n is not generally known while compiling
}

If every potentially evaluated call must happen at compile time, C++20 provides consteval immediate functions:

consteval std::uint64_t compile_time_fibonacci(unsigned n) {
    return fibonacci(n);
}

constexpr auto f10 = compile_time_fibonacci(10);

Calling compile_time_fibonacci with a runtime value is ill-formed instead of silently becoming a runtime computation.

Constant evaluation has evolved across C++ standards. Modern constexpr functions can contain loops and local state, and C++20 even permits dynamic allocation when the allocation is released within constant evaluation. They still cannot perform arbitrary runtime I/O or leave allocated storage behind. Compilers also limit evaluation depth or work so a mistaken exponential computation does not occupy the build machine indefinitely.

#Lookup Tables

Compile-time evaluation is useful for constructing static lookup tables while keeping their generation logic next to the data:

#include <array>

constexpr int floor_sqrt(int x) {
    int r = 0;
    while ((r + 1) * (r + 1) <= x)
        ++r;
    return r;
}

consteval std::array<int, 1000> make_isqrt_table() {
    std::array<int, 1000> table{};
    for (int i = 0; i < 1000; ++i)
        table[i] = floor_sqrt(i);
    return table;
}

inline constexpr auto isqrt = make_isqrt_table();
static_assert(isqrt[42] == 6);

The table occupies space in the binary, and looking up a value is not automatically faster than computing it. Precomputation exchanges execution work for compilation time, binary size, memory traffic, and possibly cache capacity. It is most attractive when the table is small, reused often, and replaces a meaningfully expensive operation.

Even a fixed-trip-count runtime loop is not a constant-expression context:

std::uint64_t sum_first_100() {
    std::uint64_t sum = 0;
    for (unsigned i = 0; i < 100; ++i)
        sum += fibonacci(i);
    return sum;
}

An optimizer may unroll the loop and fold some or all calls, but the language does not require it. If compile-time evaluation is part of correctness or of the intended resource budget, express that requirement with static_assert, a constexpr variable, or a consteval function rather than hoping to observe it in optimized assembly.
