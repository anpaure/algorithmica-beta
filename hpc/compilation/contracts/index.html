Contract Programming

Memory-safe language subsets such as safe Rust sharply restrict the operations that can cause undefined behavior. They can still report errors, panic, run out of resources, or leave details such as hash-table iteration order to an implementation; “safe” does not mean that every operation succeeds.

C and C++ expose a larger set of operations with undefined behavior. If a program evaluates one of them, the language places no requirements on the result. This is not an alternative error-handling mechanism: undefined behavior usually means that a bug has invalidated the assumptions under which the program was compiled.

#Why Undefined Behavior Exists

There are two common reasons for leaving behavior undefined:

  • Some operations are almost certainly bugs, such as dereferencing a null pointer or reading an uninitialized scalar. Sanitizers can instrument many of these operations during testing; GCC and Clang provide -fsanitize=undefined, although no one sanitizer detects every kind of undefined behavior.
  • Some operations would otherwise require targets to emulate a behavior their native instructions do not provide. For example, shifting by a negative count or by a count greater than or equal to the promoted left operand’s width is undefined.

Old descriptions of these rules need occasional maintenance. Since C++20, right-shifting a negative signed integer is specified as division by a power of two rounded toward negative infinity, and is therefore an arithmetic right shift with sign extension. The current rule is in [expr.shift].

Undefined signed overflow gives optimizers useful information. For a defined execution, (x + 1) > x is always true when x is an int; it is not always true when x is unsigned, because unsigned arithmetic wraps modulo a power of two.

This does not make a signed loop immune to overflow. Consider:

for (unsigned int i = 0; i <= n; ++i) {
    // ...
}

If n == UINT_MAX, this loop never terminates: after reaching UINT_MAX, i wraps to zero. An analogous signed loop that increments beyond INT_MAX has undefined behavior rather than a guaranteed iteration count. The programmer still has to choose a type and condition that represent the intended range. size_t is suitable for container sizes because it can represent every valid index, not because unsigned wraparound is inherently faster.

#Removing Checks

Safe interfaces often perform runtime checks. A simplified C++ .at() implementation looks like this:

T at(size_t k) {
    if (k >= size())
        throw std::out_of_range("Array index exceeds its size");
    return _memory[k];
}

When a caller loops from zero while i < size() and accesses element i, an optimizer can often prove the index valid and remove the repeated check. Less obvious control flow may prevent that proof even when the programmer knows the precondition holds.

C++23 provides the [[assume(expression)]] attribute for communicating such facts:

[[assume(k < size())]];
return _memory[k];

Clang and GCC also provide compiler-specific builtins. If an evaluated assumption is false, the program has undefined behavior; an assumption is not a validation mechanism. A common pattern is to check the condition with assert in debug builds and expose it as an assumption only in production builds where the surrounding contract guarantees it.

#Arithmetic Contracts

Arithmetic transformations often differ at boundary values. Unsigned division by two becomes one logical right shift:

unsigned div_unsigned(unsigned x) {
    return x / 2;
}

Signed division rounds toward zero, while an arithmetic right shift rounds toward negative infinity. Consequently, -5 / 2 is -2, but -5 >> 1 is -3. A compiler can implement signed division by two with a correction before shifting:

mov  edx, eax
shr  edx, 31    ; 1 for a negative input, 0 otherwise
add  eax, edx   ; correct the rounding direction
sar  eax, 1

If negative inputs are outside the function’s contract, an unsigned parameter or an explicit assumption can remove the correction.

Floating-point flags require a broader contract. -ffast-math grants assumptions involving NaNs, infinities, signed zero, rounding, and algebraic reassociation. It can enable major transformations, but it changes observable semantics by more than a few low mantissa bits. Without it, compilers can still apply transformations that preserve the language’s floating-point rules.

#Memory Aliasing

Compilers also need to preserve all permitted relationships between pointers. Consider:

void add(int* a, const int* b, int n) {
    for (int i = 0; i < n; ++i)
        a[i] += b[i];
}

If b == a - 1 for views into a larger allocation, iteration $i$ writes a[i], and iteration $i+1$ reads that value through b[i+1]. The iterations are dependent. The opposite direction, b == a + 1, does not create this particular forward dependency.

const and restrict communicate different facts. const prevents modification through that pointer; it does not imply that another pointer cannot refer to the same object. C’s restrict qualifier, and C++ extensions such as __restrict__, express a no-aliasing contract for accesses in a scope:

void add(int* __restrict__ a,
         const int* __restrict__ b,
         int n) {
    for (int i = 0; i < n; ++i)
        a[i] += b[i];
}

Breaking this promise makes the program undefined. When it is true, the compiler can vectorize without first generating a runtime overlap check.

#C++26 Contracts

C++26 contains language support for preconditions, postconditions, and assertion statements. The adopted design is WG21 P2900R14, and the current working-draft grammar uses pre, post, and contract_assert:

bool is_power_of_two(int m) {
    return m > 0 && ((m & (m - 1)) == 0);
}

int mod_power_of_two(int x, int m)
    pre(x >= 0)
    pre(is_power_of_two(m))
    post(r: r >= 0 && r < m)
{
    int r = x & (m - 1);
    contract_assert(r == x % m);
    return r;
}

This is C++26 code; compiler support is still emerging. A postcondition is associated with normal return, and the optional result name (r here) denotes the returned value.

Contract assertions are not merely alternative spelling for optimizer assumptions. Their evaluation semantics are implementation-defined, and code should not rely on an unchecked predicate being assumed true. Use an explicit assumption only when violating it is genuinely outside every valid execution.

The general lesson is to inspect the assembly when an expected optimization does not happen and ask which input, aliasing relationship, or language rule prevents it. Then express the missing fact with the narrowest truthful contract rather than deleting a check and hoping the caller behaves.
