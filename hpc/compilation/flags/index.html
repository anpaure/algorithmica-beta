Flags and Targets

The first step of getting high performance from the compiler is to ask for it, which is done with over a hundred different compiler options, attributes, and pragmas.

#Optimization Levels

There are 4 and a half main levels of optimization for speed in GCC:

  • -O0 is the default one that does no optimizations (although, in a sense, it does optimize: for compilation time).
  • -O1 (also aliased as -O) does a few “low-hanging fruit” optimizations, almost not affecting the compilation time.
  • -O2 enables a broad set of generally profitable transformations with moderate compile-time and code-size costs (this is what many projects use for production builds).
  • -O3 adds more aggressive loop and vector transformations that may increase compile time or code size and are not guaranteed to speed up every workload.
  • -Ofast includes -O3 and enables options that disregard parts of strict language semantics. In particular, its floating-point assumptions affect NaNs, infinities, signed zero, rounding, and reassociation, which may be unacceptable for numerically sensitive code.

There are also many other optimization flags that are not included even in -Ofast, because they are very situational, and enabling them by default is more likely to hurt performance rather than improve it — we will talk about some of them in the next section.

#Specifying Targets

The next thing you may want to do is tell the compiler more about the computers this code will run on: the smaller the required platform set, the more features it may use. The default x86 baseline is chosen when the toolchain is configured and is intentionally conservative. The simplest way to narrow it is -march, for example -march=haswell. If the binary will run on the build machine, -march=native asks the compiler to detect its features.

The instruction sets are generally backward-compatible, so it is often enough to just use the name of the oldest microarchitecture you need to support. A more robust approach is to list specific features that the CPU is guaranteed to have: -mavx2, -mpopcnt. When you just want to tune the program for a particular machine without using any instructions that may crash it on incompatible CPUs, you can use the -mtune flag (by default -march=x also implies -mtune=x).

GCC can also apply these options to functions defined in a region of a source file. Push and pop the current options so the setting does not accidentally leak into the rest of the file:

#pragma GCC push_options
#pragma GCC optimize("O3")
#pragma GCC target("avx2")

unsigned hot_function(unsigned x) {
    return x * x;
}

#pragma GCC pop_options

Function attributes are usually clearer when only one definition needs a different target. Pragmas and attributes are compiler extensions; keep a portable fallback when the code is intended for other toolchains.

#Multiversioned Functions

Sometimes you may want to provide several architecture-specific implementations in one binary. On supported x86 ELF targets, GCC can emit the versions plus a resolver that detects CPU features and selects an implementation at runtime, as described in the official function multiversioning documentation:

__attribute__(( target("default") )) // fallback implementation
int popcnt(unsigned x) {
    int s = 0;
    for (int i = 0; i < 32; i++)
        s += (x >> i) & 1u;
    return s;
}

__attribute__(( target("popcnt") )) // selected when the running CPU supports POPCNT
int popcnt(unsigned x) {
    return __builtin_popcount(x);
}

The exact multiversioning syntax and dispatch mechanism are target- and toolchain-specific. Clang supports per-function target attributes, but source-level optimization pragmas are not interchangeable with GCC’s.
