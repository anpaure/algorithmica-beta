What Compilers Can and Can't Do

Suppose a program spends most of its time looking up strings in a sorted vector. Replacing the vector with a hash table would make the workload faster. Why does -O3 not do it for us?

Because this is not an optimization in the compiler sense. A hash table uses more memory, iterates in a different order, invalidates references under different conditions, has different worst-case behavior, and requires a hash function whose cost and security properties depend on the application. The new program may be better, but it is not the same program.

This boundary explains both the astonishing power and the frequent disappointment of optimizing compilers. They are excellent at finding cheaper implementations inside a semantic envelope. Most large performance gains come from changing the envelope.

#The Observable Program

C++ implementations follow the as-if rule: they may transform code however they want as long as the observable behavior allowed by the language remains the same. This is why a compiler can delete an unused calculation, inline a function, keep a variable only in a register, or replace division by a constant with multiplication.

The rule also explains why apparently harmless transformations sometimes do not happen.

Side effects. Reads and writes involving volatile, I/O calls, atomics, locks, and unknown external functions may be observable or may order other operations. They cannot be freely removed or rearranged.

Aliasing. If two pointers may refer to the same storage, a write through one may change a later read through the other. Without a proof that they do not overlap, loads cannot always be cached in registers and loops cannot always be vectorized.

Exceptions and errors. Replacing or moving an operation can change whether it throws, traps, sets errno, raises a floating-point exception, or touches an invalid page. Even if your input never triggers the corner case, the compiler needs a language-level reason to exclude it.

Arithmetic semantics. Signed overflow, floating-point rounding, NaNs, infinities, and signed zero make many school-algebra identities invalid as program transformations. Contracts and explicit floating-point options can narrow this semantic space, but only the programmer can decide whether doing so matches the application.

Undefined behavior is not a convenient performance annotation. It means that an invalid execution has no requirements at all; it does not make valid executions faster by itself. Useful optimization comes from expressing true preconditions in a form the compiler understands and testing that the program actually maintains them.

#Missing Information

An optimizer can only use facts available at the point where it runs.

Separate compilation hides function bodies. Dynamic libraries can be replaced without recompiling their callers. A virtual call or function pointer may target code that did not exist when the current file was compiled. An input-dependent branch probability is unknown. Two pointers arriving from an API may or may not overlap.

Several language and tool features exist mainly to move information across these boundaries:

  • header-defined functions and templates expose implementations to callers;
  • const, restrict-style qualifiers, and assumptions describe valid accesses and values;
  • link-time optimization analyzes multiple translation units together;
  • profile-guided optimization supplies observed branch and call frequencies;
  • target flags describe the instructions and cost model of the machines that will run the binary.

These features do not order the compiler to perform a particular trick. They remove reasons why the trick might be wrong or unprofitable.

#Cost Models Are Predictions

Correctness is only the first gate. The compiler must also predict whether a transformation is worthwhile.

Inlining removes call overhead and exposes more optimization opportunities, but duplicates code. Unrolling removes loop-control instructions and exposes independent work, but increases register pressure and instruction-cache usage. Vectorization processes more elements per instruction, but may require alignment checks, scalar tails, masks, and expensive shuffles. Prefetching can hide latency, but may waste bandwidth and cache capacity.

There is no universally correct choice. The outcome depends on microarchitecture, input size and distribution, surrounding code, and whether the workload cares about latency, throughput, binary size, energy, or startup time. Compiler cost models approximate these trade-offs using target descriptions and heuristics. They cannot run a statistically sound benchmark for every possible rewrite while compiling your program.

This is why changing a compiler version, target flag, or innocent-looking source expression can alter generated code. It is also why forcing every optimization with pragmas is not a strategy: a hint can outlive the assumptions that made it useful.

#The Scale Barrier

Most compiler optimizations preserve the program’s data structures and asymptotic shape. They simplify expressions, move computations, combine operations, schedule instructions, transform loops, and remove abstraction machinery.

They generally do not:

  • choose a different algorithm with different edge behavior;
  • change an array of structures into a structure of arrays;
  • add an index, cache, compressed representation, or probabilistic filter;
  • batch requests across an API boundary;
  • trade precision for speed without permission;
  • decide that a result may be stale, approximate, or occasionally wrong;
  • redesign a file format or network protocol.

These are often the highest-leverage optimizations precisely because they require knowledge outside the source expression: workload statistics, ownership, acceptable error, latency objectives, operational constraints, and future maintenance.

A compiler may recognize a small idiom such as population count or rotate and replace it with one instruction. It is not expected to recognize an entire database join and invent a cache-aware execution plan. When a transformation needs a paragraph to state its preconditions, it probably belongs in a library or in your program rather than in a peephole pass.

#Compilers Have Resource Limits Too

Optimization consumes compilation time and memory. Exact answers to many optimization problems—optimal instruction scheduling and register allocation among them—are computationally hard, so production compilers use approximations. They also cap inlining depth, constexpr evaluation, template instantiation, and the amount of analysis devoted to a function.

Making a function larger can therefore make its machine code worse even when no runtime work was added. The inliner may stop, an analysis may lose precision, or register pressure may cause spills. Splitting a hot kernel from cold error handling can help both the human and the optimizer.

The same applies to abstractions. A deeply generic expression may be theoretically erasable, yet require so much interprocedural reasoning that the optimizer gives up. This is not evidence that all abstractions are slow; it is evidence that the specific boundary is in the wrong place for this compiler and build configuration.

#A Productive Failure Analysis

When generated code is disappointing, asking “why is the compiler stupid?” is emotionally satisfying but diagnostically weak. A better sequence is:

  1. Confirm the hotspot. Use representative inputs and a profiler. Optimizing cold code only makes the binary harder to inspect.
  2. State the expected machine behavior. Which loads, branches, arithmetic operations, and dependencies should remain? What resource should be the bottleneck?
  3. Inspect optimized output. Compiler Explorer is convenient for a small reproducer; a real binary, source-correlated disassembly, optimization remarks, and machine-code analysis are better for the final decision.
  4. Classify the blocker. Is the desired rewrite illegal, missing information, judged unprofitable, beyond an analysis limit, or simply unimplemented?
  5. Change the narrowest contract. Add a valid precondition, expose a function body, move a dispatch out of the loop, simplify the representation, or implement the algorithmic change explicitly.
  6. Test before timing. Differential tests, sanitizers, boundary cases, and numerical error checks protect against benchmarking a faster wrong program.
  7. Measure again. Include compiler, flags, CPU, input distribution, and dispersion. Assembly that looks shorter is not automatically faster.

GCC can emit optimization diagnostics such as -fopt-info, and Clang has optimization remarks; both are often more useful than guessing why a loop did not inline or vectorize. LLVM’s documented optimization pass catalogue is also a good map of the kinds of local and loop transformations modern compilers attempt.

#Division of Labor

The compiler knows exact language rules, target instructions, register constraints, and hundreds of local transformations. You know the data, invariants, acceptable trade-offs, and the algorithm’s purpose.

High-performance code comes from letting each side do its part. Give the compiler clear, simple code with truthful contracts and enough visibility. Keep algorithm selection, data layout, approximation, and measurement in human hands. Then inspect the boundary between them whenever the result is surprising.

The goal is not to outsmart the optimizer instruction by instruction. It is to arrange the problem so that the optimizer’s easiest legal choice is also the code you wanted.
