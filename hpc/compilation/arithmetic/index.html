Arithmetic Optimizations

Here is a function that divides an unsigned integer by ten:

#include <cstdint>

std::uint32_t div10(std::uint32_t x) {
    return x / 10;
}

There is no reason for this tiny function to be interesting, except that its machine code normally contains no division. Optimizing compilers replace the constant divisor with a multiplication by a precomputed reciprocal followed by a shift. The derivation is subtle enough to occupy a good part of the integer division chapter, yet the optimization happens without being requested.

Compilers know a large collection of such arithmetic identities. More importantly, they know the conditions under which each identity is legal. This second part is why a handwritten “obvious optimization” is often either unnecessary or wrong.

#Constant Folding and Propagation

The simplest arithmetic optimization is to do the work during compilation:

int f(int x) {
    constexpr int width = 7 * 9;
    return x * width + (3 - 3);
}

The expression becomes x * 63; the addition of zero disappears. If the caller supplies a constant x and the function is visible, the entire result can disappear too. This combination of constant folding, constant propagation, inlining, and dead-code elimination is the reason compile-time information is so valuable.

The constexpr keyword is not what performs the optimization. It makes an expression eligible for constant evaluation and, in some contexts, requires it. Ordinary code with known inputs can also be folded under the language’s as-if rule: the implementation may transform a program in any way that preserves its observable behavior.

Conversely, hiding a value behind a separately compiled function, a mutable global, or an unpredictable memory load may prevent propagation. Link-time optimization and header-defined templates help because they expose more of the program to the optimizer.

#Strength Reduction

Strength reduction replaces an expensive operation with a cheaper equivalent. The classic examples are multiplication or division by a power of two:

std::uint32_t mul8(std::uint32_t x) { return x * 8; }
std::uint32_t div8(std::uint32_t x) { return x / 8; }
std::uint32_t mod8(std::uint32_t x) { return x % 8; }

For unsigned integers these become, respectively, a left shift, a right shift, and a bitwise and with seven. You should normally write the operation you mean. The compiler knows the target instruction costs, while x / 8 documents division and remains correct if the type or divisor changes.

Signed division is already less trivial. C++ division rounds toward zero, while an arithmetic right shift rounds negative odd values toward negative infinity. Replacing x / 8 with x >> 3 changes the result for values such as -9. The compiler either emits the required correction or uses the shift only when it can prove that x is nonnegative.

Strength reduction also happens inside loops. A source-level array access such as a[i * stride] does not necessarily multiply from scratch on every iteration. The optimizer can maintain a pointer and advance it by stride each time. This transformation is called induction-variable simplification, and it is one reason pointer arithmetic and indexing usually compile to the same code.

#Hoisting Invariants

Consider applying an affine transformation to an array:

void normalize(float* a, int n, float lo, float hi) {
    for (int i = 0; i < n; ++i)
        a[i] = (a[i] - lo) / (hi - lo);
}

The denominator does not change between iterations. A compiler can move its computation out of the loop, calculate its reciprocal once, and multiply each element by it:

float scale = 1.0f / (hi - lo);
for (int i = 0; i < n; ++i)
    a[i] = (a[i] - lo) * scale;

Moving an unchanged expression out of a loop is loop-invariant code motion. For integer division, calculating one reciprocal can be a major saving. For floating point, replacing several divisions with multiplication changes rounding and exceptional behavior, so whether it happens depends on the requested floating-point model.

Loads can also be loop-invariant, but only if nothing in the loop may overwrite their memory. This is where aliasing contracts matter. If two pointers may refer to overlapping ranges, a store through one can invalidate a value loaded through the other, and the compiler must remain conservative.

#Reassociation and Reductions

Arithmetic expressions describe both a value and, sometimes accidentally, a dependency graph.

float sum(const float* a, int n) {
    float s = 0;
    for (int i = 0; i < n; ++i)
        s += a[i];
    return s;
}

Each addition depends on the previous one. Splitting the sum into several accumulators exposes instruction-level parallelism, and packing those accumulators into vectors exposes SIMD parallelism. For integers whose overflow behavior permits it, compilers routinely perform this transformation.

For floating point, (a + b) + c can differ from a + (b + c) because each addition rounds. Under strict IEEE semantics, arbitrary reassociation is therefore forbidden. Options such as GCC’s -fassociative-math relax specific rules; the broad -ffast-math group relaxes several more, including assumptions about signed zero, infinities, and NaNs. Clang documents its individual controls in its floating-point command-line reference.

This is not merely a choice between “accurate” and “a few bits less accurate.” Reassociation can improve a well-conditioned sum, destroy a carefully stabilized formula, or make behavior depend on the compiler and target. Enable relaxed arithmetic only when the numerical contract and tests permit each transformation. The rounding errors chapter develops these concerns in detail.

#Fused Operations

Many processors have a fused multiply-add instruction that computes

$$ a \cdot b + c $$

with one final rounding. It is usually faster than a separate multiplication and addition, and often more accurate because the intermediate product is not rounded. Compilers can select it from a matching expression when the target supports FMA and the contraction rules allow it:

float polynomial(float x, float a, float b) {
    return a * x + b;
}

std::fma asks for fused semantics explicitly, even on a target where the implementation must emulate them. A compiler option may instead permit contraction of ordinary source expressions. These are different contracts, although they can lead to the same instruction.

Fused memory operands are another, unrelated x86 feature: an arithmetic instruction can read one operand directly from memory. That saves a separately encoded load instruction, but internally it may still decode into more than one micro-operation.

#Narrower Arithmetic

Using a smaller type may reduce memory traffic and fit more elements in a SIMD register. It does not automatically make scalar arithmetic faster: general-purpose registers commonly operate at a fixed native width, and narrow values may require extension before use.

The profitable pattern is usually to store data narrowly and widen it for computation:

std::uint64_t sum_samples(const std::uint16_t* samples, std::size_t n) {
    std::uint64_t total = 0;
    for (std::size_t i = 0; i < n; ++i)
        total += samples[i];
    return total;
}

The accumulator must be wide enough for the largest possible sum. This is a proof obligation, not a compiler preference. Accidental signed overflow is undefined behavior in C++, while unsigned overflow wraps modulo a power of two. Choosing unsigned solely because it enables wraparound can make comparisons and loop termination harder to reason about; choose the type that matches the mathematical range.

#What the Compiler Will Not Invent

Local algebra is the compiler’s home ground. It will fold constants, eliminate identities, derive reciprocals, combine shifts, recognize rotations, simplify induction variables, and select target instructions. GCC lists the enabled transformations for each optimization level in its optimization options, although the result also depends on cost models and surrounding code.

It normally will not replace an unstable formula with a stable one, change a matrix representation, introduce a lookup table with a meaningful memory trade-off, or decide that approximate arithmetic is acceptable. Those transformations change an algorithm’s contract or resource usage.

A practical workflow is therefore:

  1. Write the clearest exact expression.
  2. Compile with the intended optimization level and target.
  3. Inspect the hot loop, not an isolated source line.
  4. If an operation remains expensive, identify which semantic condition blocks the rewrite.
  5. Express the missing precondition or perform a tested algorithmic transformation.

Memorizing bit tricks is less valuable than learning which facts make them true. The compiler has already memorized more of them than either of us.
