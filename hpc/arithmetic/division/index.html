Integer Division

Integer addition is a short trip through a carry chain. Integer division is a search for a quotient, and the hardware has much more work to do.

On contemporary CPUs, an integer divide commonly has a latency measured in tens of cycles. The exact number depends on the microarchitecture, operand width, and sometimes the values being divided. It is also usually only partly pipelined. This makes division unusual: replacing one div can matter more than deleting a small loop around it.

Before trying to replace it, we need to be precise about which division we are performing. This chapter deals with nonzero integer divisors. C++ integer division truncates toward zero; the corresponding remainder has the sign of the dividend. Most reciprocal techniques are easiest to derive for unsigned integers and require an extra adjustment for signed ones.

#Division and Remainder on x86

x86 uses the same instruction to produce a quotient and a remainder. The instruction has an implicit double-width dividend:

  • div r/m32 divides edx:eax by its operand and writes the quotient to eax and the remainder to edx;
  • div r/m64 divides rdx:rax by its operand and writes the quotient to rax and the remainder to rdx.

For an ordinary unsigned 32-by-32 division, the upper half is zero:

; uint32_t quotient(uint32_t x, uint32_t y)
mov eax, edi
xor edx, edx
div esi
ret

Signed division uses idiv. The cdq instruction sign-extends eax into edx:eax (cqo does the 64-bit version):

; int32_t quotient(int32_t x, int32_t y)
mov  eax, edi
cdq
idiv esi
ret

The remainder is already in edx, so % differs only in which result is returned:

; uint32_t remainder(uint32_t x, uint32_t y)
mov eax, edi
xor edx, edx
div esi
mov eax, edx
ret

The double-width form is useful in multiple-precision arithmetic. For example, this divides a 128-bit unsigned integer hi:lo by a 64-bit divisor:

; uint64_t quotient(uint64_t lo, uint64_t hi, uint64_t d)
; precondition: d != 0 and hi < d
mov rcx, rdx        ; save d before overwriting rdx
mov rax, rdi
mov rdx, rsi
div rcx             ; rdx:rax / rcx
ret

The precondition hi < d is not cosmetic. If the quotient does not fit in 64 bits—or if the divisor is zero—div raises a divide exception. A compiler implementing an unconstrained __uint128_t / uint64_t must therefore handle the other cases too, often by calling a software routine.

#Powers of Two

Unsigned division by $2^k$ is a right shift, and the remainder is a mask:

uint32_t q = x >> k;
uint32_t r = x & ((uint32_t(1) << k) - 1);

The mask expression requires $k<32$; a shift by the width of a type is undefined in C++. Signed division is less direct because an arithmetic shift rounds negative values down, while C++ division rounds toward zero. Compilers insert a bias before shifting when it is needed.

This distinction is a recurring theme: a strength reduction is valid only when it preserves the language operation, not merely when it resembles the corresponding arithmetic identity.

#Reciprocal Multiplication

Suppose an unsigned divisor $d$ is known before the program runs. We would like to replace

$$ q=\left\lfloor\frac{x}{d}\right\rfloor $$ with multiplication by a fixed-point approximation to $1/d$. A product naturally gives us twice as many bits. Keeping its high half is equivalent to dividing by the scale factor: $$ \operatorname{high}_w(xm)=\left\lfloor\frac{xm}{2^w}\right\rfloor. $$

With a carefully chosen multiplier $m$, a shift, and—in some cases—one add or correction, this is exactly equal to $\lfloor x/d\rfloor$ for every $w$-bit input. These constants are usually called magic numbers. Their construction must account for the rounding error and the full input range; simply choosing $\lceil 2^w/d\rceil$ is not sufficient for every divisor.

For example, division of a 64-bit unsigned integer by 10 can be implemented as

$$ \left\lfloor\frac{x}{10}\right\rfloor = \operatorname{high}_{64}(x\cdot\mathtt{0xCCCCCCCCCCCCCCCD})\mathbin{\gg}3. $$ On x86-64, the multiplication that produces both halves is cheaper than a general div. The remainder then follows from $$ r=x-qd. $$

You normally should not write the magic constant yourself. GCC and Clang already perform this transformation for compile-time divisors, including the awkward signed cases. Libraries such as libdivide extend the same idea to divisors that are fixed only at run time: they precompute a small descriptor once and reuse it for many divisions.

The break-even point depends on how often the divisor is reused. One division plus precomputation is rarely a win; a million divisions by the same value often is.

#Barrett Reduction

Reciprocal multiplication for a quotient and Barrett reduction are related, but they are not the same algorithm.

Barrett reduction targets repeated modular reductions. Let $0<n<2^w$, choose a scale $2^k$, and precompute

$$ \mu=\left\lfloor\frac{2^k}{n}\right\rfloor. $$ For an input in a stated range—commonly a product $0\le x<n^2$—we estimate the quotient from the high part of $x\mu$: $$ \hat q=\left\lfloor\frac{x\mu}{2^k}\right\rfloor, \qquad \hat r=x-\hat qn. $$

Because $\mu$ rounds $2^k/n$ down, $\hat q$ may be slightly too small. Choosing $k$ for the promised input range bounds that error; one or a small fixed number of conditional subtractions then puts $\hat r$ in $[0,n)$. The range and scale are part of the algorithm. Without them, the claim that the approximation is exact is false.

This is particularly useful in large-integer and cryptographic code, where products are already represented as several machine words. The implementation can select limb-sized shifts and avoid a general multiword division.

#Direct Remainders for 32-Bit Inputs

If the input and divisor are 32-bit but a 128-bit product is available, Daniel Lemire’s method computes the remainder without first materializing the quotient. For $2\le d<2^{32}$, precompute

$$ m=\left\lceil\frac{2^{64}}{d}\right\rceil =\left\lfloor\frac{2^{64}-1}{d}\right\rfloor+1. $$

Then the low half of $mx$ acts like the fractional part of $x/d$. Multiplying that fraction by $d$ and taking the high half recovers the exact remainder:

#include <cstdint>
#include <stdexcept>

struct fast_remainder_u32 {
    uint32_t d;
    uint64_t m;

    explicit fast_remainder_u32(uint32_t divisor)
        : d(divisor), m(0) {
        if (d < 2)
            throw std::invalid_argument("divisor must be at least 2; handle 1 separately");
        m = UINT64_MAX / d + 1;
    }

    uint32_t operator()(uint32_t x) const {
        uint64_t low = m * x;
        return uint32_t((static_cast<__uint128_t>(low) * d) >> 64);
    }
};

The special case $d=1$ should return zero directly: $\lceil2^{64}/1\rceil$ does not fit in 64 bits. The use of __uint128_t also makes this implementation specific to compilers that provide that extension. On other targets, the same calculation can use a high-half multiplication intrinsic.

The same intermediate gives a fast divisibility test:

bool is_divisible(uint32_t x) const {
    return m * x < m;
}

This comparison is exact under the same preconditions. It is a useful example of a broader optimization pattern: once an expensive transformation has produced both a high and a low half, ask whether the half you were about to discard already encodes the answer to a nearby problem.

#Choosing a Method

There is no universally fastest replacement for division:

  • for a compile-time constant, let the compiler generate reciprocal multiplication;
  • for one run-time divisor reused many times, use a tested divider object such as libdivide;
  • for bounded modular products, Barrett reduction is often a natural fit;
  • for long chains modulo an odd integer, Montgomery multiplication avoids division in a different representation;
  • for a single unpredictable divisor, the hardware instruction may be the simplest and fastest correct choice.

Measure the complete computation rather than an isolated instruction. A replacement can use more multiplications and registers, increase pressure on execution ports, or lengthen a dependency chain. Removing div is an opportunity, not a proof of speedup.
