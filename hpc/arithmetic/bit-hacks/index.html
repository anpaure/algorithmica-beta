Bit Manipulation

An integer is usually introduced as a number, but the processor also sees it as a small, fixed-size set. If bit $i$ is one, the set contains $i$; if it is zero, it does not. Addition moves carries through this set, multiplication combines shifted copies of it, and the bitwise instructions modify many membership flags at once.

This second interpretation is useful far beyond contest-style tricks. Memory allocators round sizes to powers of two, schedulers maintain masks of available CPUs, parsers classify bytes in parallel, and compressed data structures routinely store one Boolean value per bit. The important skill is not memorizing a page of incantations. It is recognizing when an integer is the right representation and then expressing the operation so that both the language and the hardware agree on its meaning.

#Use Unsigned Words

For a $w$-bit unsigned type, C++ arithmetic is performed modulo $2^w$. There is no exceptional overflow case:

$$ x + y \equiv (x+y) \pmod {2^w}. $$

This is exactly the algebra most bit-manipulation identities expect. Signed arithmetic is different: overflow is undefined behavior, while converting a large unsigned result to a signed type can produce a surprising negative value. A good default is therefore to do the bit work in a fixed-width unsigned type and convert only at a checked boundary.

Shifts have their own precondition. For x << k and x >> k, the shift count must be smaller than the width of x. Writing 1 << k is also a common bug because the literal 1 has type int; use uint64_t{1} << k when constructing a 64-bit mask.

#include <cstdint>
#include <optional>

std::optional<bool> test_bit(std::uint64_t x, unsigned k) {
    if (k >= 64)
        return std::nullopt;
    return ((x >> k) & 1u) != 0;
}

std::optional<std::uint64_t> set_bit(std::uint64_t x, unsigned k) {
    if (k >= 64)
        return std::nullopt;
    return x | (std::uint64_t{1} << k);
}

std::optional<std::uint64_t> clear_bit(std::uint64_t x, unsigned k) {
    if (k >= 64)
        return std::nullopt;
    return x & ~(std::uint64_t{1} << k);
}

The checks are part of the interface here: an invalid index produces std::nullopt rather than a false answer or a silent no-op. If the caller has already established k < 64, keeping that invariant outside the hot loop is normally better than checking it for every element.

#Ask the Standard Library First

Since C++20, the <bit> header provides portable names for most operations that used to require compiler-specific builtins:

OperationMeaning
std::popcount(x)number of one-bits
std::countl_zero(x)zero-bits before the highest one-bit
std::countr_zero(x)zero-bits after the lowest one-bit
std::bit_width(x)number of bits needed to represent x
std::has_single_bit(x)whether x is a power of two
std::bit_floor(x), std::bit_ceil(x)neighboring powers of two
std::rotl(x, k), std::rotr(x, k)cyclic shifts

Unlike the older GCC __builtin_clz and __builtin_ctz, the standard counting functions have defined behavior for zero. GCC explicitly documents zero as undefined for those two builtins in its bit-operation reference, which is why wrapping them carelessly used to produce surprisingly creative bugs.

These functions describe intent and still compile to specialized instructions when the target has them. std::popcount, for example, may become popcnt; on another target it may become a short arithmetic sequence or a library call. The source code should normally specify the operation, while compiler flags specify the machine on which it is allowed to run.

#include <bit>
#include <cstdint>

struct bit_summary {
    int ones;
    int leading_zeroes;
    int trailing_zeroes;
    int width;
};

bit_summary inspect(std::uint32_t x) {
    return {
        std::popcount(x),
        std::countl_zero(x),
        std::countr_zero(x),
        static_cast<int>(std::bit_width(x))
    };
}

#Two’s-Complement Identities

Unsigned negation is defined as subtraction from $2^w$. Consequently, 0 - x has the same bit pattern commonly associated with two’s-complement -x, without involving signed overflow.

This gives two particularly useful identities:

#include <cstdint>

std::uint64_t lowest_bit(std::uint64_t x) {
    return x & (0 - x);
}

std::uint64_t clear_lowest_bit(std::uint64_t x) {
    return x & (x - 1);
}

Why do they work? Subtracting one changes the lowest one-bit to zero and turns every lower zero-bit into one. AND-ing with the original word therefore removes exactly that bit. Negating a word performs the complementary transformation, leaving only the lowest one-bit common to both operands.

The zero case is worth stating rather than discovering later: both functions return zero for zero. The often-seen power-of-two test (x & (x - 1)) == 0 also accepts zero, so a complete version is x != 0 && (x & (x - 1)) == 0, or simply std::has_single_bit(x).

One practical application is checked power-of-two alignment:

#include <bit>
#include <cstdint>
#include <limits>
#include <optional>

std::optional<std::uint64_t>
align_up(std::uint64_t x, std::uint64_t alignment) {
    if (!std::has_single_bit(alignment))
        return std::nullopt;

    const std::uint64_t mask = alignment - 1;
    if (x > std::numeric_limits<std::uint64_t>::max() - mask)
        return std::nullopt;

    return (x + mask) & ~mask;
}

The familiar one-line formula is still there, but its two real preconditions—power-of-two alignment and no addition overflow—are now visible.

#Masks as Small Sets

If a problem has at most $w$ independent yes/no states, a $w$-bit word can represent the whole state. Union becomes OR, intersection becomes AND, symmetric difference becomes XOR, and complement becomes NOT followed by a mask that removes unused high bits.

This is especially convenient when enumerating subsets. The following loop visits every submask of mask, including zero, exactly once:

#include <cstdint>
#include <utility>

template<class F>
void for_each_submask(std::uint32_t mask, F&& f) {
    std::uint32_t sub = mask;
    while (true) {
        f(sub);
        if (sub == 0)
            break;
        sub = (sub - 1) & mask;
    }
}

The subtraction finds the next smaller bit pattern, while the AND removes bits that are not members of the original set. If this is done for every $n$-bit mask, the total number of visits is $3^n$: each bit is either outside mask, inside mask but outside sub, or inside both.

Packed masks trade memory for extra work. They are excellent when bandwidth or cache capacity is the bottleneck, but less attractive when individual elements are updated concurrently: several logical values share one machine word, so an update may require a read-modify-write instruction and may create false sharing. Representation is part of the algorithm, not a free compression switch.

#When One Instruction Is Not One Cycle

x86 has increasingly specialized bit instructions: popcnt, count-leading/trailing-zero instructions, rotations, and BMI2 operations such as pext and pdep, which gather or scatter selected bits. The Intel Intrinsics Guide is useful for finding their interfaces, but an instruction’s existence does not make it universally fast. Latency and throughput differ substantially between microarchitectures, and some intrinsics expand into instruction sequences when the requested feature is unavailable.

The reverse is also important: handwritten tricks are often unnecessary. Compilers recognize x & (x - 1), rotations, byte swaps, power-of-two divisions, and many branchless selection idioms. A clever source expression can be slower than a comparison followed by cmov, or can prevent vectorization by obscuring what the loop computes.

The reliable workflow is the same as for any other low-level optimization:

  1. express the operation with unsigned arithmetic and explicit preconditions;
  2. prefer <bit> when it has the operation;
  3. compile for the real target and inspect the generated code;
  4. benchmark the entire loop, not an isolated instruction;
  5. keep the straightforward version unless the specialized one wins in the workload that matters.

Bit manipulation is powerful precisely because it crosses several levels at once: algebra modulo $2^w$, data representation, compiler pattern matching, and the instruction set. Most “bit hacks” go wrong when they account for only one of them.
