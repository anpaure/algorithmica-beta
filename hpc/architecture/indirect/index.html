Indirect Branching

A normal branch says where it is going in its own machine code. An indirect branch takes the destination from a register or memory location:

jmp rax
call QWORD PTR [rdi]

This small difference lets us implement switch tables, function pointers, interpreters, and runtime polymorphism. It also creates a harder prediction problem: the processor must guess not only whether a branch is taken, but which of many possible addresses comes next.

#Jump Tables

Consider a dense switch:

int classify(unsigned x) {
    switch (x) {
        case 0: return 11;
        case 1: return 19;
        case 2: return 23;
        case 3: return 31;
        default: return -1;
    }
}

For a tiny example the compiler may discover a formula or use a table of results. When each case contains real code, a common implementation is a jump table: check that x is in range, load the x-th destination from an array, and jump there.

    cmp  edi, 3
    ja   default
    lea  rax, [rip + table]
    jmp  QWORD PTR [rax + rdi * 8]

This dispatch takes constant time regardless of the number of cases. A chain of comparisons can be better when cases are sparse or one value is overwhelmingly common, so compilers choose between trees, tables, and arithmetic using density and profile information.

An indirect jump is not automatically mispredicted. Modern processors maintain target-prediction structures, and a stable sequence—an interpreter repeatedly executing the same opcode pattern, for example—can be learned. Unpredictable target changes are the expensive case because a wrong target sends the front-end down the wrong instruction stream and later forces it to discard that work.

#Function Pointers

A function pointer separates an operation from the code that invokes it:

using operation = float (*)(float);

float map_sum(const float* a, int n, operation op) {
    float sum = 0;
    for (int i = 0; i < n; ++i)
        sum += op(a[i]);
    return sum;
}

The indirect call happens once per element, so it can easily cost more than the operation itself. More importantly, the compiler usually cannot inline op, which blocks simplification and SIMD vectorization across the call.

If the operation is fixed for the whole array, moving dispatch outward helps. A caller can select one specialized loop once, or make the operation a template parameter so the target is known during compilation. If each element genuinely needs a different operation, the indirection is part of the problem rather than syntactic overhead.

#Virtual Functions

C++ virtual dispatch is normally implemented with the same mechanism. Here is a valid class hierarchy:

#include <cstdio>

struct Animal {
    virtual ~Animal() = default;
    virtual void speak() const = 0;
};

struct Dog final : Animal {
    void speak() const override { std::puts("Bark"); }
};

struct Cat final : Animal {
    void speak() const override { std::puts("Meow"); }
};

In common ABIs, each polymorphic object contains a hidden pointer called a vptr. It points to a virtual table containing function pointers in fixed slots. A call such as

void announce(const Animal& animal) {
    animal.speak();
}

is conceptually implemented as:

; rdi = &animal
mov  rax, QWORD PTR [rdi]       ; load vptr
call QWORD PTR [rax + SLOT]     ; call the speak entry

Derived methods are not padded to equal machine-code lengths and are not stored consecutively inside every object. The fixed-size part is the table entry: one pointer per virtual slot. The object usually pays one vptr, while each class contributes a table and its actual method bodies elsewhere in the binary.

Virtual dispatch therefore has several possible costs:

  • one or more dependent loads to find the target;
  • an indirect call that may be mispredicted when object types vary;
  • loss of inlining and the optimizations it would expose;
  • extra object and table storage.

The last two are often more important than the call instruction itself. If speak performs milliseconds of I/O, dispatch is irrelevant. If a virtual method adds two floats inside a loop, it is probably the entire bottleneck.

Compilers can devirtualize a call when they prove the dynamic type—for example, when a class is final, construction is visible, or whole-program analysis finds only one target. Profile-guided optimization can also specialize a common type and retain a fallback for the rest.

#Data Layout Still Wins

A heterogeneous array of pointers creates two independent problems: indirect control flow and pointer chasing. Even perfect branch prediction cannot make scattered objects contiguous in cache.

For data-oriented workloads, it is often better to group objects by type and process each group with a direct loop. This converts many per-object decisions into one outer decision and usually improves both instruction and data locality. The representation is less flexible for frequent type changes, which is the trade-off the virtual interface was designed to avoid.

Indirect branching is a powerful tool, not a performance defect. Use it at coarse boundaries where flexibility matters, and try not to hide two arithmetic instructions behind it a billion times per second.
