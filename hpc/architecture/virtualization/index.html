Virtualization

An operating system kernel is written under the reasonable assumption that it controls the machine. A virtual machine lets several kernels maintain this belief at the same time.

The software making this possible is a virtual-machine monitor, more commonly called a hypervisor. It presents each guest with virtual CPUs, memory, interrupts, and devices while retaining control of the physical versions. The difficult part is not imitating add: ordinary arithmetic already has exactly the behavior the guest expects. The difficult part is executing privileged operations without letting a guest reconfigure or escape the host.

#A Privilege Level for Kernels

Running a guest kernel as an ordinary user process is not sufficient. If every sensitive instruction simply faulted, the hypervisor could emulate it, but historically some x86 instructions behaved differently without reliably trapping. Binary translation and paravirtualized guest kernels worked around this, at considerable complexity.

Modern x86 processors provide hardware virtualization: Intel calls its extension VMX, and AMD calls the corresponding facility SVM. We will use Intel terminology, but the high-level design is shared.

VMX adds root and non-root operation. Both have the familiar rings, so a guest kernel can run in ring 0 while remaining in VMX non-root operation. It has enough privilege to manage its own applications but not enough to take control from the hypervisor, which runs in root operation.

The hypervisor prepares a control structure describing guest state, host state, and which events should be intercepted. A VM entry starts or resumes the guest. Most guest instructions then execute directly on the physical CPU. An intercepted event causes a VM exit: hardware saves guest state, restores host state, and transfers control to the hypervisor. After handling the event, the hypervisor may resume the guest with another VM entry.

Possible exit causes include selected control-register accesses, I/O instructions, interrupts, and instructions such as cpuid, depending on the configured controls. A VM exit is not required for every privileged-looking action: virtualization hardware implements many common cases without leaving the guest. Intel specifies these controls and transitions in the VMX chapters of its system-programming manual.

This is the central performance fact about CPU virtualization: ordinary computation can run directly, while exits add exceptional control transfers and hypervisor work. A compute-heavy guest with few exits can therefore behave much like a native process; an exit-heavy workload can spend substantial time crossing the boundary.

#Virtual Memory for Virtual Memory

A process normally translates a virtual address through page tables into a physical address. Inside a virtual machine, “physical” memory is itself an abstraction:

$$ \text{guest virtual} \longrightarrow \text{guest physical} \longrightarrow \text{host physical}. $$

Early hypervisors maintained shadow page tables that combined the two mappings and trapped guest page-table updates. Current processors support nested translation in hardware. Intel calls it Extended Page Tables (EPT); AMD calls it Nested Page Tables (NPT). The guest manages its own virtual-to-guest-physical tables, while the hypervisor separately controls guest-physical-to-host-physical mappings.

Walking two sets of page tables can require more memory accesses than native translation. Translation lookaside buffers cache the resulting mappings, making page size, locality, and translation invalidations important. The guest and host can each make locally sensible paging decisions that interact badly when composed; abstraction is excellent at hiding responsibility, including from the people trying to diagnose a latency spike.

Nested translation also enforces isolation. A guest can write any guest page-table entry it is permitted to write, but the second translation still prevents it from addressing host memory outside the regions assigned by the hypervisor.

#Virtual Devices

CPUs and memory are only part of a machine. A guest expects disks, network adapters, timers, interrupt controllers, and firmware interfaces. There are three broad implementation strategies.

Emulation. The hypervisor or a user-space device model imitates an existing hardware device. This supports unmodified guests, but register accesses and interrupts may require exits, and emulating a complicated historical device is not a hobby one would invent voluntarily.

Paravirtualization. The guest uses a driver designed for virtual machines. Interfaces such as virtio exchange batches of descriptors through shared-memory queues, reducing emulated device interactions. The guest knows that the device is virtual, while applications above the driver need not know.

Direct assignment. A physical device or hardware-supported virtual function is assigned to a guest. An IOMMU translates and restricts the device’s direct memory accesses, serving a role for devices similar to the nested page tables used by CPUs. This can reduce software overhead but complicates migration, sharing, and device management.

The choice moves work among exits, memory sharing, device emulation, and physical hardware. “Virtualization overhead” is therefore not one number; it is a description missing its workload and device model.

#KVM as an Example

On Linux, KVM exposes hardware virtualization through /dev/kvm. A user-space virtual-machine monitor creates a VM, registers regions of its address space as guest physical memory, creates virtual CPUs, and invokes KVM_RUN to enter them. When an exit requires user-space handling, KVM_RUN returns with a structure describing the reason. The exact interface is documented by the kernel’s KVM API.

This division is pragmatic:

  • the kernel component handles privileged CPU state, scheduling, and memory integration;
  • user-space software can provide device models, firmware, image formats, and management policy;
  • in-kernel or assigned devices can accelerate paths where returning to user space would be too costly.

A virtual CPU is also a schedulable host entity. If there are more runnable vCPUs than physical CPUs, the host scheduler time-slices them. A guest may observe steal time: time during which its virtual CPU was ready but the host ran something else. NUMA placement, vCPU pinning, and oversubscription can matter as much as instruction execution itself.

#Virtual Machines and Containers

Containers virtualize a different boundary. Processes in containers share the host kernel and are isolated using facilities such as namespaces, control groups, capabilities, and filtered system calls. There is no guest kernel and normally no VM entry or exit for an ordinary container operation.

Virtual machines can run a different kernel and provide a hardware-shaped isolation boundary. Containers are lighter because they reuse the host kernel, but this also makes that kernel part of their shared trusted base. The two techniques are frequently combined: a virtual machine provides the tenant boundary, and containers organize applications inside it.

For performance work, the useful question is not whether virtualization is “slow.” Ask which boundary the workload crosses:

  • Does it cause frequent VM exits?
  • Does it miss in nested address translation?
  • Is device I/O emulated, paravirtualized, or assigned?
  • Is the vCPU waiting for a physical CPU?
  • Are guest memory and host memory placed on the expected NUMA node?

Once the responsible resource is named, the usual tools of batching, locality, profiling, and reducing unnecessary work apply again. Virtualization adds another layer, but fortunately it does not repeal causality.
