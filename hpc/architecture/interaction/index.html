Interrupts and System Calls

Our assembly programs have so far lived in an unusually peaceful universe. They read and write memory, perform arithmetic, and eventually return. Real programs also need to open files, allocate pages, receive network packets, and occasionally discover that the user has pressed a key.

The CPU cannot let an arbitrary program control these facilities directly. A process that could rewrite page tables or talk to a storage controller could inspect or destroy every other process on the machine. Instead, the operating-system kernel runs with privileges that applications do not have, and provides a narrow interface for requesting privileged work.

#Protection Rings

x86 associates code with a privilege level. Operating systems conventionally run applications in ring 3 and the kernel in ring 0. Instructions that change address translation, interrupt handling, or other global machine state are privileged: executing them from user mode raises an exception rather than quietly handing the process the computer.

Memory is protected as well. Page-table entries specify whether a page is accessible from user mode, so a normal load from a kernel-only address faults before it can reveal anything. This division is the foundation of process isolation.

Applications still need kernel services, so the architecture provides controlled entry points. On 64-bit x86, the usual one is the syscall instruction. It does not mean “call whichever kernel address is in this register.” The kernel configures the entry address and processor state in advance. syscall transfers control there, changes privilege level, and saves enough user state for a later sysret or equivalent return path. Linux’s entry code then establishes a kernel stack and saves the remaining state before ordinary kernel code handles the request.

A system call is therefore a protected procedure call across an abstraction boundary.

#The Linux System-Call ABI

System calls have their own calling convention. For the x86-64 Linux ABI:

ValueRegister
system-call numberrax
arguments 1–3rdi, rsi, rdx
arguments 4–6r10, r8, r9
return valuerax

The fourth argument uses r10, not rcx, because the syscall instruction itself clobbers rcx; it also clobbers r11. The complete per-architecture table is maintained in the Linux syscall(2) documentation.

Here is a complete NASM program that writes a string and exits without using a C library:

global _start

section .rodata
    msg:    db "Hello, world!", 10
    msglen: equ $ - msg

section .text
_start:
    mov eax, 1          ; __NR_write
    mov edi, 1          ; STDOUT_FILENO
    lea rsi, [rel msg]  ; buffer
    mov edx, msglen     ; byte count
    syscall

    mov eax, 60         ; __NR_exit
    xor edi, edi        ; status = 0
    syscall
    ud2                 ; exit does not return

It can be assembled and linked with:

nasm -f elf64 hello.asm -o hello.o
ld -o hello hello.o

This example intentionally ignores the return value of write. Production code must handle errors, interruptions, and partial writes. More importantly, it should normally call the standard library instead of embedding system-call numbers and ABI details. The GNU C Library explains why its system-call wrappers are more portable and may provide compatibility or thread-cancellation behavior in addition to the raw transition.

At the raw Linux interface, failures are returned as negative error numbers in rax. A libc wrapper normally converts this to -1 and stores the positive error number in errno. This is another small example of why “one C function call” and “one machine-level operation” are not interchangeable concepts.

#What the Transition Costs

Calling the kernel is more expensive than an ordinary function call. The processor crosses a protection boundary, application state must be preserved, arguments and pointers must be validated, and mitigations or tracing may add work. The requested service can then cost anything from a short table lookup to waiting for a disk.

A system call is a mode switch, but it is not necessarily a context switch. If the kernel can satisfy the request immediately, it returns to the same thread. A blocking read may instead put the thread to sleep and let the scheduler run another one. Conflating these two events makes system-call costs seem even more mysterious than they are.

The main optimization is usually to request useful work in larger units:

  • buffered output combines many small writes;
  • batched interfaces submit several operations together;
  • memory allocators serve small requests from user-space arenas and ask the kernel for larger regions less often;
  • asynchronous and non-blocking interfaces reduce the need to dedicate a blocked thread to each request.

Batching is not free. It may increase latency, retain more memory, or complicate error handling. As always, the right unit is determined by the workload rather than by a moral objection to system calls.

Some library operations avoid kernel entry entirely. Linux maps a small kernel-provided shared object, the vDSO, into each process. Functions such as clock queries can sometimes read kernel-maintained data and return in user mode; the library falls back to a real system call when necessary. The interface and its versioning rules are described in vdso(7). This is why tracing system calls is not always the same as tracing library calls.

#Interrupts, Exceptions, and Traps

Several events can redirect the CPU to privileged code, but they have different causes:

  • An interrupt is asynchronous with respect to the current instruction stream. A device or timer asks the CPU for attention.
  • An exception is caused synchronously by an instruction, such as a page fault, division by zero, or invalid opcode.
  • A system call is a deliberate synchronous transition requested by the program.

Architecture manuals sometimes use trap as a more specific exception category, while operating-system literature also uses it informally for controlled transitions in general. It is safer to describe the cause than to rely on the overloaded word.

Interrupt and exception handlers preserve an architectural state, identify the cause, and eventually either resume execution, deliver a signal, schedule another thread, or terminate the process. They are not categorically “off the normal path”: page faults, timer interrupts, and system calls are essential parts of normal operation. What matters for performance is their frequency, the work they trigger, and whether they disturb caches, translation state, or the currently running thread.

The same protected-transition idea appears one level lower when an entire operating system runs under another piece of privileged software. That is the subject of virtualization.
