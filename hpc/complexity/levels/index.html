When to Optimize

Suppose a request spends most of its time waiting for a database. Replacing an integer division in the response formatter with a shift may produce magnificent assembly and an entirely invisible product improvement.

Performance engineering begins one step before optimization: deciding what is worth making faster.

#Choose the Objective

“Fast” is not a complete requirement. Depending on the application, the quantity we care about may be:

  • latency: how long one operation takes;
  • throughput: how many operations finish per unit of time;
  • tail latency: how long an unusually slow operation takes;
  • resource efficiency: CPU time, memory, energy, or money per operation;
  • scalability: how performance changes with input size or load.

These objectives can conflict. Batching requests often improves throughput while delaying the first request in the batch. A lookup table spends memory to save computation. Parallel execution may reduce latency while consuming more total CPU time. Before touching the implementation, write down the workload, the metric, and the constraint that is currently being violated.

Correctness is part of that definition. An optimization measured on convenient inputs but wrong on an edge case is not a faster implementation of the same program; it is a benchmark for a different program.

#Estimate the Ceiling

Assume a fraction $f$ of the current running time belongs to a component we can speed up by a factor of $s$. After optimization, the normalized running time is

$$ T' = (1-f) + \frac{f}{s}, $$ so the total speedup is $$ S = \frac{1}{(1-f) + f/s}. $$

This is commonly known as Amdahl’s law. Its most useful feature is not the formula but the disappointment it calculates in advance. If the target occupies 10% of execution time, making it infinitely fast can improve the whole program by at most $1/0.9 \approx 1.11$ times. If the target occupies 90%, even a modest local improvement may matter.

The fraction must be measured on a representative workload. Optimizing the startup path using a profile of a week-long server process is as misguided as optimizing steady-state throughput using only startup measurements.

#Move Up Before Moving Down

Optimization opportunities form a rough hierarchy. Changes near the top tend to be more powerful and more invasive:

  1. Avoid the work. Cache a result, remove an unnecessary conversion, or stop requesting data that will be discarded.
  2. Change the contract or representation. A binary format can be cheaper to parse than JSON; a flat array can be cheaper to traverse than a graph of tiny allocations.
  3. Choose a better algorithm. Improve asymptotic work, expected work, or the model that matches the bottleneck, such as I/O complexity.
  4. Expose information to the compiler. Use suitable types, remove accidental aliasing, select the target architecture, and enable optimization.
  5. Improve the data path. Arrange accesses for locality, remove unpredictable branches, shorten dependency chains, and use SIMD.
  6. Tune individual instructions. Only now do instruction selection and hand-written assembly become likely candidates.

This is not a law that forbids working from the bottom. Sometimes the interface is fixed, the algorithm is already optimal, and one instruction really is the bottleneck. The hierarchy is a search order: check high-leverage explanations before spending an afternoon polishing a loop that should not exist.

#Measure, Explain, Change

A productive optimization cycle is short:

  1. Establish a correct baseline and a reproducible benchmark.
  2. Use profiling to locate where the relevant resource is spent.
  3. Form a mechanism-level hypothesis: cache misses, dependency latency, branch misprediction, excessive work, or something else.
  4. Change one important variable.
  5. Measure again, including correctness and secondary metrics.

The explanation matters. A faster result without a causal account may be a change in CPU frequency, input distribution, code alignment, or compiler behavior that will disappear in production. Conversely, a good explanation predicts when the optimization should stop helping. A cache-blocking transformation should lose importance when the working set already fits in cache; branch removal should lose to a cheap, predictable branch.

For small kernels, it is useful to compare the measurement with a physical bound. If the loop already consumes nearly all available memory bandwidth, replacing additions with cheaper additions cannot help much. If a dependency chain determines latency, adding execution units does not shorten it. The performance-limits chapter develops this style of accounting.

#Include the Engineering Cost

Runtime is not the only scarce resource. An optimization may also cost:

  • development and review time;
  • portability across compilers and architectures;
  • readability and future modification speed;
  • test surface and risk of rare failures;
  • binary size or memory;
  • additional operational complexity.

These costs do not imply that low-level code is bad. They imply that it should earn its keep. Isolate architecture-specific kernels behind small interfaces, retain a simple reference implementation for testing, and document the assumptions that make the fast path correct.

The expected value of an optimization is roughly its benefit over the lifetime and scale of the program, discounted by implementation risk. Saving a fraction of a microsecond in a function called trillions of times can justify heroic work. Saving a second in a tool run once during installation may not justify making the installer mysterious.

#Know When to Stop

Stop when one of the following becomes true:

  • the original performance requirement is met with adequate margin;
  • the optimized region is no longer a meaningful part of the profile;
  • another resource has become the bottleneck;
  • expected benefit is smaller than measurement noise or engineering cost;
  • further changes would violate a more important objective.

For important performance properties, turn the stopping point into a regression test. Record the workload and metric, track distributions rather than only the best run, and allow enough tolerance for real machine noise. Performance then becomes a maintained property of the system instead of folklore about a benchmark somebody ran on a laptop three years ago.

Premature optimization is not the act of caring about efficiency early. Choosing compact data structures and avoiding needless work during design is usually cheap. Premature optimization is committing to a complicated solution before establishing that its resource is important. The cure is not indifference; it is measurement and a model.
