Models of Computation

Consider two procedures that both read every element of an array exactly once. The first reads the elements from left to right. The second follows a permutation stored in the array and uses the value it has just read to find the next element.

In the usual operation-counting model, these procedures are almost identical: both perform $n$ reads and $O(n)$ integer operations. On an actual computer, they can behave very differently. The sequential scan gives the memory system a long stream of predictable requests. The pointer-chasing version creates a dependency chain: the address of the next request is not known until the current one completes.

The model did not make an arithmetic mistake. It simply declined to represent the property that matters.

#Useful Lies

A model of computation defines the resources an algorithm is charged for using. The classical unit-cost model charges roughly one step for an arithmetic operation, comparison, or memory access. This is deliberately unrealistic, just as a map is deliberately not the same size as the country it depicts.

A useful model has two properties:

  1. It is simple enough that we can design and analyze algorithms with it.
  2. It preserves the differences that decide performance for the problem at hand.

Asymptotic complexity remains exceptionally useful. If one implementation does $n^2$ work and another does $n \log n$, no amount of instruction scheduling is likely to rescue the first on sufficiently large inputs. The trouble begins when we treat $O(n)$ as a complete performance prediction rather than one coordinate of it.

Modern processors make several resources partly independent. Arithmetic can overlap with arithmetic, multiple memory requests can be in flight, and cached data has a different cost from data in main memory. Consequently, there is no single replacement for Big O. We use several small models, each exposing one possible bottleneck.

#Word RAM

The word RAM model is the closest formal relative of ordinary systems programming. It assumes a machine word of $w$ bits and charges constant time for operations such as addition, comparison, bitwise logic, shifts, and random access to a word in memory. Usually $w = \Theta(\log n)$, so an index or pointer into the input fits in one word.

This distinction already matters. A bitset can process $w$ Boolean values with one word operation, while an arbitrary-precision integer spanning $k$ words cannot honestly be added in constant time. The model explains why replacing a loop over individual bits with a loop over machine words can be an algorithmic improvement rather than merely a clever implementation trick.

The word RAM still pretends that every memory location costs the same and that operations happen one after another. Those assumptions are convenient for data structures and bit manipulation, but inadequate for studying caches or instruction-level parallelism.

#The External-Memory Model

When data movement dominates computation, we can invert the accounting. The external-memory model gives the machine a fast memory of $M$ words and transfers data to it in blocks of $B$ consecutive words. Computation on resident data is free; the cost is the number of block transfers.

This model was introduced to analyze disks, but the same idea applies recursively to cache hierarchies. A linear scan of $n$ words costs $\Theta(n/B)$ transfers. Reading the same words in an adversarial order may require $\Theta(n)$ transfers. The two scans have equal work and radically different I/O complexity.

The parameters $M$ and $B$ are abstractions, not promises about a particular cache. Real caches have associativity, replacement policies, prefetchers, shared capacity, and several levels. We will first develop the clean model in the external-memory chapter and then examine which parts survive contact with CPU caches.

#Work and Span

Operation counting also fails to say which operations may overlap. Represent a computation as a directed acyclic graph: vertices are operations and edges are dependencies. Two quantities immediately appear:

  • Work $W$ is the total number of operations, or the time on one ideal processor.
  • Span $D$ is the length of the longest dependency path, or the time on infinitely many ideal processors.

On $p$ processors, execution time cannot be smaller than either $W/p$ or $D$:

$$ T_p \ge \max\left(\frac{W}{p}, D\right). $$

This is normally presented as a model of multicore algorithms, but the same dependency graph is useful inside one superscalar core. Execution units provide a small amount of parallel capacity, while the critical path limits how much of it can be used. Four additions that all update one accumulator form a chain; four additions into independent accumulators do not.

The analogy is not exact. A CPU schedules instructions through finite buffers, and different instructions need different execution units. Still, work and span give us the right first question: are we short of resources, or short of independent work? We will make this concrete when discussing instruction scheduling and throughput computing.

#Arithmetic Intensity

For streaming numerical code, a particularly useful summary is arithmetic intensity:

$$ I = \frac{\text{operations performed}}{\text{bytes transferred}}. $$ Suppose a machine can perform at most $C$ relevant operations per second and move at most $B$ bytes per second across the memory boundary we care about. Then attainable performance $P$ is bounded by $$ P \le \min(C, B \cdot I). $$

Low-intensity algorithms hit the bandwidth bound first. High-intensity algorithms may reuse each loaded byte enough times to reach the compute bound. This is the core of the Roofline model, although a serious Roofline analysis must specify which operations and which level of memory are being counted.

Arithmetic intensity is not an intrinsic property of a mathematical problem. Matrix multiplication can repeatedly fetch the same values from memory, or it can operate on cache-sized blocks and reuse them. The formula therefore evaluates an implementation on a memory boundary, not just an algorithm name.

#Models Compose

These models answer different questions:

ModelCharged resourceUseful for
Asymptotic workelementary operationsscalability and algorithm selection
Word RAMword operationsbit tricks and integer data structures
External memoryblock transferslocality, caching, and storage
Work and spanwork and dependency depthparallelism and latency
Rooflineoperations and bytescompute-vs-bandwidth limits

They are not competing theories from which we must select a winner. A fast hash table may need good expected work, compact word-level metadata, few cache-line transfers, and enough independent probes to overlap memory latency. Removing one bottleneck merely grants us the privilege of discovering the next one.

There is also a boundary beyond which analytical models become cumbersome. Branch predictors depend on history, cache behavior depends on neighboring code, and compiler transformations may remove the operation we intended to count. At that point, the right model is an experiment: specify the machine and workload, measure the relevant events, and try to falsify the explanation. That is why profiling is part of algorithm design rather than an activity reserved for when design has failed.

The practical rule is to use the cheapest model that can still distinguish the alternatives. Start with asymptotic work. Add word size, data movement, dependencies, or measured machine limits only when the simpler model stops answering the question.
