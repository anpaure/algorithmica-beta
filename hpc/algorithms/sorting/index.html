Algorithmica βSorting

Sorting

“How fast can we sort?” is not one question. It is a suitcase full of them.

Are the keys arbitrary objects or fixed-width integers? Are comparisons cheap? Must equal keys retain their input order? May the algorithm allocate another array? Is the input random, nearly sorted, reverse sorted, or mostly duplicates? A sorting benchmark that omits these details measures a workload no one can reproduce.

This case study develops two deliberately different algorithms:

  • an unstable comparison sort with $O(n\log n)$ worst-case complexity;
  • a stable four-pass radix sort specialized for 32-bit unsigned keys.

The point is not to replace a mature standard library with two pages of code. It is to expose the choices a production implementation has to make—and to build references sturdy enough for honest experiments.

#The Ordering Contract

A comparison function used for sorting must define a strict weak ordering. Informally:

  • nothing is less than itself;
  • if $a<b$ and $b<c$, then $a<c$;
  • if neither of two values is less than the other, they are equivalent, and this equivalence behaves transitively.

a <= b is not a valid comparator. Neither is an ordinary floating-point < over a domain containing NaNs: the induced “equivalence” is not transitive. A broken comparator does not merely choose a strange order; it violates the sorting algorithm’s precondition.

Two equivalent elements need not be equal. Records can compare only by surname, timestamp, or bucket number while carrying different payloads. This is where stability matters:

input:   (key 2, Alice), (key 1, Bob), (key 2, Carol)
stable:  (key 1, Bob),   (key 2, Alice), (key 2, Carol)

An unstable sort may exchange Alice and Carol. std::sort is unstable; std::stable_sort preserves their relative order. Stability is a semantic requirement, not a performance adjective.

#Comparison Sorting Has a Floor

A comparison gives at most two outcomes. Distinguishing all $n!$ possible input permutations therefore requires a decision tree of height at least

$$ \lceil\log_2(n!)\rceil=n\log_2n-O(n) $$

in the worst case. Clever instructions can reduce time per comparison, but no comparison sort escapes the $\Omega(n\log n)$ bound on arbitrary distinct keys.

Quicksort is attractive because partitioning is sequential and cache-friendly. Its unprotected worst case is quadratic. Heapsort guarantees $O(n\log n)$ and uses constant auxiliary storage, but its access pattern and comparison count are often less friendly. Insertion sort is quadratic, yet excellent on tiny ranges because its loop is small and nearby elements are already hot.

Introsort combines all three: partition like quicksort, switch to heapsort if partitioning becomes suspiciously deep, and finish small ranges with insertion sort.

#An Executable Introsort

The implementation below is intentionally conventional rather than record-seeking. It accepts random-access iterators, a strict weak comparator, and copy-constructible values. The copy requirement keeps the pivot independent while elements are exchanged; industrial implementations do more work to support move-only types efficiently.

#include <algorithm>
#include <concepts>
#include <cstddef>
#include <functional>
#include <iterator>
#include <utility>

template<std::random_access_iterator Iterator, class Compare>
void insertion_sort(Iterator first, Iterator last, Compare &compare) {
    for (Iterator current = first; current != last; ++current) {
        std::iter_value_t<Iterator> value(std::move(*current));
        Iterator hole = current;

        while (hole != first && compare(value, *(hole - 1))) {
            *hole = std::move(*(hole - 1));
            --hole;
        }
        *hole = std::move(value);
    }
}

template<std::random_access_iterator Iterator, class Compare>
std::pair<Iterator, Iterator>
partition_three_way(Iterator first, Iterator last, Compare &compare) {
    using value_type = std::iter_value_t<Iterator>;
    const value_type pivot = *(first + (last - first) / 2);

    Iterator lower = first;
    Iterator current = first;
    Iterator upper = last;

    while (current != upper) {
        if (compare(*current, pivot)) {
            std::iter_swap(lower, current);
            ++lower;
            ++current;
        } else if (compare(pivot, *current)) {
            --upper;
            std::iter_swap(current, upper);
        } else {
            ++current;
        }
    }

    return {lower, upper}; // [lower, upper) is equivalent to pivot
}

template<std::random_access_iterator Iterator, class Compare>
void introsort_loop(Iterator first, Iterator last,
                    unsigned depth, Compare &compare) {
    constexpr std::iter_difference_t<Iterator> insertion_cutoff = 24;

    while (last - first > insertion_cutoff) {
        if (depth == 0) {
            std::make_heap(first, last, compare);
            std::sort_heap(first, last, compare);
            return;
        }
        --depth;

        auto [lower, upper] =
            partition_three_way(first, last, compare);

        // Recurse into the smaller side and loop over the larger one.
        // This bounds stack depth independently of pivot quality.
        if (lower - first < last - upper) {
            introsort_loop(first, lower, depth, compare);
            first = upper;
        } else {
            introsort_loop(upper, last, depth, compare);
            last = lower;
        }
    }

    insertion_sort(first, last, compare);
}

template<std::random_access_iterator Iterator,
         class Compare = std::less<>>
requires std::sortable<Iterator, Compare> &&
         std::copy_constructible<std::iter_value_t<Iterator>>
void introsort(Iterator first, Iterator last, Compare compare = {}) {
    const std::size_t length =
        static_cast<std::size_t>(last - first);
    if (length < 2)
        return;

    unsigned floor_log2 = 0;
    for (std::size_t x = length; x > 1; x >>= 1)
        ++floor_log2;

    introsort_loop(first, last, 2 * floor_log2, compare);
}

The three-way partition establishes

[ first, lower )  < pivot
[ lower, upper ) == pivot under the comparator
[ upper, last )   > pivot

and is especially important for duplicate-heavy input. A two-way partition can repeatedly recurse over values equal to the pivot; this one removes the entire equal region at once.

After twice the floor of $\log_2 n$ partition levels, the routine stops trusting its pivots and heap-sorts the remaining range. That gives the $O(n\log n)$ worst-case bound. Recursing only into the smaller outer partition keeps stack usage $O(\log n)$; the larger partition is processed by the surrounding loop.

This sort is not stable. The partition swaps equivalent records without preserving their order. Making the insertion-sort base case stable does not repair the swaps that happened above it.

#What this implementation does not claim

The middle element is a simple pivot, not necessarily the best pivot. Production sorts use sampling, pattern detection, carefully tuned partition loops, and type-specific optimizations. The cutoff 24 is a parameter, not a constant of nature. std::sort should remain the first baseline, and the C++ standard specifies its complexity and result—not one mandatory internal algorithm.

#Branches, Moves, and Representations

Partitioning has at least three potential costs:

  • comparisons, which may be a single integer instruction or an expensive function;
  • unpredictable branches, especially on mixed random keys;
  • moving records, which may copy four bytes or relocate a large object.

Optimizing one can worsen another. A branchless partition often writes every element to temporary buffers; that is attractive for small keys and less attractive for large records. Sorting pointers or compact indices reduces movement, but the later indirection can destroy locality. Caching an expensive derived key may save comparisons while increasing memory traffic.

This is why “comparisons per second” and “elements per second” are both incomplete metrics. Record the number and size of moves, key extraction cost, allocated bytes, and where the sorted representation will be consumed next.

#Escaping the Comparison Bound

Fixed-width integer keys reveal more information than one comparison bit. A radix sort can inspect one digit of every key, group equal digits, and repeat. For 32-bit keys and 8-bit digits, there are exactly four passes and 256 counters per pass.

The following least-significant-digit (LSD) sort is stable and accepts every span length. It uses one auxiliary array of $n$ words.

#include <algorithm>
#include <array>
#include <cstddef>
#include <cstdint>
#include <span>
#include <utility>
#include <vector>

void radix_sort_u32(std::span<std::uint32_t> values) {
    if (values.size() < 2)
        return;

    std::vector<std::uint32_t> scratch(values.size());
    std::uint32_t *source = values.data();
    std::uint32_t *destination = scratch.data();

    for (unsigned shift = 0; shift < 32; shift += 8) {
        std::array<std::size_t, 256> count{};
        for (std::size_t i = 0; i < values.size(); ++i)
            ++count[(source[i] >> shift) & 0xffu];

        std::array<std::size_t, 256> position{};
        std::size_t total = 0;
        for (std::size_t digit = 0; digit < count.size(); ++digit) {
            position[digit] = total;
            total += count[digit];
        }

        // Forward traversal plus monotonically increasing positions makes
        // this distribution stable.
        for (std::size_t i = 0; i < values.size(); ++i) {
            const unsigned digit = (source[i] >> shift) & 0xffu;
            destination[position[digit]++] = source[i];
        }

        std::swap(source, destination);
    }

    // Four passes are even, so source normally points back to values.
    // Keep the copy for robustness if the digit schedule is later changed.
    if (source != values.data())
        std::copy_n(source, values.size(), values.data());
}

Why must every pass be stable? After the first pass, values are ordered by bits 0–7. The second pass groups by bits 8–15 while retaining the earlier order inside each group, so they are ordered by bits 0–15. Induction extends this argument through all 32 bits. An unstable counting pass would discard the work of the lower digits.

For signed two’s-complement int32_t, use the transformed key

$$ k(x)=\operatorname{bits}(x)\mathbin{\mathtt{xor}}\mathtt{0x80000000}. $$

Flipping the sign bit maps INT_MIN to zero and preserves signed order over the remaining bit patterns. Apply this transformation only when selecting digits; keep the original record as the payload.

For records, distribute the entire record—or an index into a record array—according to its 32-bit key. The forward traversal preserves the input order of equal keys, so the same code structure gives a genuinely observable stable sort. Moving large records four times may dominate the key work, which is another reason to consider sorting indices.

#The Radix Cost Model

The four-pass routine performs $O(4n+4\cdot256)$ work, but asymptotic notation hides its main cost. Each pass reads and writes the entire array, for about 32 bytes of traffic per 32-bit value over four passes, before cache effects and write allocation. It also allocates another $4n$ bytes.

Comparison sorting is often better for tiny arrays, expensive-to-move records, generic comparators, or when allocation is forbidden. Radix sorting becomes attractive when keys are cheap fixed-width integers, arrays are large enough to amortize the histograms, and bandwidth can sustain the passes. Wider digits reduce passes but enlarge histograms; narrower digits do the opposite.

Signed integers are easy. Floating-point keys require a more careful monotone bit transform, including a policy for negative zero and NaNs. Strings need variable-length digit handling and have a cost proportional to inspected characters, not merely record count. “Radix sort” names a family, not one drop-in replacement for std::sort.

#Stable Comparison Sorting

When keys are generic and equal records must retain order, use a stable comparison algorithm. Merge sort is the usual starting point: merge adjacent sorted runs into an auxiliary buffer, alternating source and destination until one run remains. It has predictable $O(n\log n)$ comparisons and sequential memory access, at the price of auxiliary storage and repeated record movement.

Adaptive stable sorts can exploit runs already present in the input. A production decision should compare against std::stable_sort on actual record types; reusing the unstable introsort above with a tie-breaking original index changes the key and movement cost, and is not equivalent to obtaining stability for free.

#There Is No Historical Sorting Record Here

The original book contained only an empty sorting page. Its companion repository has an unfinished partition experiment: the scalar partition exists, while the advertised AVX path is a placeholder, and no complete sorting benchmark or validation harness is present. There is therefore no defensible “faster than std::sort” number to preserve.

This absence is useful. A partition microbenchmark does not measure pivot selection, recursion, equal-key handling, small-range cleanup, fallback behavior, or end-to-end movement. Publishing its best number as a sorting result would compare a part with a whole.

#Benchmarking a Sort

Generate input outside the timed region and restore it before every repetition. Sorting the same buffer repeatedly mostly measures the already-sorted case. Retain a checksum or consume the result so the optimizer cannot discard the call.

At minimum, test:

  • uniform random keys over a wide domain;
  • already sorted and reverse-sorted inputs;
  • constant, binary, and few-unique keys;
  • organ-pipe, sawtooth, and long-run patterns;
  • nearly sorted data with controlled local disturbances;
  • real key and record distributions from the application.

Sweep sizes across cache and memory boundaries. Report the compiler, flags, library, processor, record layout, key extractor, stability requirement, allocation policy, and whether input copying is included. Use time per element as the primary result, but also inspect comparisons, branches, cache misses, and bytes moved to explain it.

#Correctness Before Timing

For scalar keys, differential testing is straightforward:

auto expected = input;
auto actual = input;

std::sort(expected.begin(), expected.end());
introsort(actual.begin(), actual.end());

assert(actual == expected);
assert(std::is_sorted(actual.begin(), actual.end()));

Run the same oracle for radix_sort_u32, including empty arrays, lengths around small-sort and radix boundaries, all bit patterns at the signed edges, duplicate-heavy inputs, and random full-width values. For custom comparators, verify permutation preservation separately because equivalent records may appear in different valid orders.

To test stability, attach each record’s original position, sort by key alone, and assert that positions increase within every equal-key group. To test generic introsort, include move-counting values, stateful comparators, and types whose values are much larger than their keys. Address and undefined-behavior sanitizers should be part of the differential suite.

Sorting rewards specialized engineering, but it punishes vague specifications. Decide what “ordered” and “equal” mean, decide whether equal records may move, and decide which key representation the algorithm is allowed to inspect. Only then does it make sense to count cycles.
