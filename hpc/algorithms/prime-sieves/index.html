Prime Number Sieves

There are two superficially similar prime-number problems. To decide whether one 64-bit integer is prime, we use algorithms such as Miller–Rabin. To enumerate every prime up to a limit $N$, testing the numbers independently repeats almost all of the work. A sieve wins by turning divisibility into a streaming memory problem.

This makes prime generation an unusually clear performance case study. The arithmetic is elementary; the important decisions are which candidates we store, where each crossing-off pass starts, whether the working set fits in cache, and whether an expression such as p * p is even defined for the requested limit.

We will build two implementations:

  • an odd-only in-memory sieve, useful when the whole range fits comfortably in memory;
  • a segmented sieve that keeps only a small interval hot and can stream its output.

Both enumerate primes in the inclusive interval $[2,N]$ and use unsigned 64-bit limits.

#From Trial Division to Sieving

Trial division tests a candidate $x$ against possible divisors up to $\sqrt{x}$. Repeating it for every $x\le N$ performs many divisions and revisits the same factors.

The sieve of Eratosthenes reverses the loops. For each prime $p$, it marks all multiples of $p$ as composite. Marking may begin at $p^2$, because every smaller composite multiple $kp$, with $k<p$, was already handled when processing $k$’s prime factor.

std::vector<std::uint8_t> composite(limit + 1, 0);

for (std::uint64_t p = 2; p <= limit / p; ++p)
    if (!composite[p])
        for (std::uint64_t x = p * p; x <= limit; x += p)
            composite[x] = 1;

The condition p <= limit / p is the overflow-safe form of p * p <= limit. The inner loop still needs care: after marking a value near UINT64_MAX, x += p can wrap to a small number and continue forever. We will use a subtraction-based termination check in the complete implementations.

The classical running time is $O(N\log\log N)$. For performance engineering, the more immediate fact is that it performs a large number of tiny stores spread over an array of size $N$.

#Do Not Store Even Candidates

After reporting 2, every prime is odd. Represent candidate

$$ x_i = 2i+3 $$ by slot $i$. Multiples of an odd prime that are themselves odd are separated by $2p$ in value and therefore by $p$ slots: $$ p^2,\ p^2+2p,\ p^2+4p,\ldots $$

This halves both the main array and the crossing work associated with the prime 2. Here is a complete byte-per-odd-candidate implementation:

#include <cstddef>
#include <cstdint>
#include <limits>
#include <stdexcept>
#include <vector>

std::vector<std::uint32_t> odd_primes(std::uint64_t limit) {
    if (limit > std::numeric_limits<std::uint32_t>::max())
        throw std::invalid_argument("dense sieve limit exceeds uint32 output");

    std::vector<std::uint32_t> primes;
    if (limit >= 2)
        primes.push_back(2);
    if (limit < 3)
        return primes;

    // Slots represent 3, 5, ..., the largest odd number <= limit.
    std::uint64_t count64 = (limit - 1) / 2;
    if (count64 > std::numeric_limits<std::size_t>::max())
        throw std::length_error("sieve does not fit address space");

    std::size_t count = static_cast<std::size_t>(count64);
    std::vector<std::uint8_t> composite(count, 0);

    for (std::size_t i = 0; i != count; ++i) {
        std::uint64_t p = 2 * std::uint64_t(i) + 3;
        if (p > limit / p)
            break;
        if (composite[i])
            continue;

        std::size_t first = static_cast<std::size_t>((p * p - 3) / 2);
        std::size_t step = static_cast<std::size_t>(p);
        std::size_t last = count - 1;

        for (std::size_t j = first;;) {
            composite[j] = 1;
            if (step > last - j)
                break;
            j += step;
        }
    }

    for (std::size_t i = 0; i != count; ++i)
        if (!composite[i])
            primes.push_back(static_cast<std::uint32_t>(2 * i + 3));

    return primes;
}

There are several contracts hidden in this small function:

  • limit is inclusive, so odd_primes(3) returns {2, 3};
  • $p^2$ is evaluated only after p <= limit / p proves that it fits;
  • the final increment is guarded as step > last - j, so an unsigned wrap cannot restart the loop;
  • limits above UINT32_MAX are rejected because the output element type cannot represent them.

The last condition is naturally satisfied when the helper generates base primes up to the square root of a 64-bit segmented limit. For a standalone dense sieve with a larger limit, change the output type to uint64_t; memory will become the practical limit much earlier.

#Bytes or bits?

A byte array spends eight bits to store one answer, but every update is a simple byte store. A packed bitmap reduces the footprint eightfold and can keep a larger range in cache, at the cost of read-modify-write operations and more address arithmetic. There is no context-free winner.

The comparison must include the transition between cache levels. A byte sieve can win while both representations fit in a nearby cache and lose abruptly when only the packed version still fits. A wheel that omits multiples of 3 and 5 reduces traffic further but complicates the mapping from numbers to slots and changes the regular stride pattern.

#Segmentation

For a large $N$, the full candidate array is not only large; it is revisited once for every base prime. A segmented sieve first computes the primes up to $\lfloor\sqrt N\rfloor$, then crosses off a small interval at a time:

base primes: 2, 3, 5, 7, 11, ... <= sqrt(N)

[low ........ high]    mark multiples of every base prime
                      emit the survivors
                      advance to the next segment

The segment should be small enough to remain in a chosen cache and large enough that initialization, loop setup, and output do not dominate. It also lets us stream primes through a callback instead of storing $\pi(N)$ output values.

First we need an integer square root. Converting through floating point is useful for an initial estimate, but the result is corrected with division so rounding cannot omit a necessary base prime:

#include <cmath>

std::uint64_t floor_sqrt(std::uint64_t n) {
    std::uint64_t r = static_cast<std::uint64_t>(std::sqrt((long double)n));

    while (r != 0 && r > n / r)
        --r;
    while (r + 1 <= n / (r + 1))
        ++r;

    return r;
}

For a 64-bit input, the true result is at most $2^{32}-1$, so r + 1 cannot overflow during the correction. The segmented core can now reuse the odd-number mapping:

#include <algorithm>
#include <cstddef>
#include <cstdint>
#include <stdexcept>
#include <vector>

template <class Emit>
void segmented_primes(std::uint64_t limit,
                      std::size_t block_odds,
                      Emit emit) {
    if (block_odds == 0)
        throw std::invalid_argument("empty sieve segment");
    if (limit < 2)
        return;

    emit(std::uint64_t(2));
    if (limit < 3)
        return;

    auto base = odd_primes(floor_sqrt(limit));
    std::vector<std::uint8_t> composite;

    for (std::uint64_t low = 3;;) {
        // `low` is odd. Count the odd values from low through limit.
        std::uint64_t remaining = (limit - low) / 2 + 1;
        std::uint64_t count64 =
            std::min<std::uint64_t>(remaining, block_odds);
        std::uint64_t high = low + 2 * (count64 - 1);

        composite.assign(static_cast<std::size_t>(count64), 0);

        for (std::uint32_t p32 : base) {
            if (p32 == 2)
                continue;

            std::uint64_t p = p32;
            std::uint64_t square = p * p; // p <= floor_sqrt(limit)
            if (square > high)
                break;

            std::uint64_t first = square;
            if (first < low) {
                std::uint64_t remainder = low % p;
                std::uint64_t delta = remainder == 0 ? 0 : p - remainder;
                if (delta > high - low)
                    continue;
                first = low + delta;
            }

            if ((first & 1) == 0) {
                if (p > high - first)
                    continue;
                first += p;
            }

            std::uint64_t step = 2 * p;
            for (std::uint64_t x = first;;) {
                composite[static_cast<std::size_t>((x - low) / 2)] = 1;
                if (step > high - x)
                    break;
                x += step;
            }
        }

        for (std::size_t i = 0; i != composite.size(); ++i)
            if (!composite[i])
                emit(low + 2 * std::uint64_t(i));

        if (count64 == remaining)
            break;
        low = high + 2; // another odd value exists, so this cannot overflow
    }
}

The first multiple of $p$ in a segment is

$$ \max\left(p^2,\left\lceil\frac{low}{p}\right\rceil p\right), $$

rounded up once more when it is even. Starting at $p^2$ is still necessary: otherwise a segment containing the prime $p$ would mark the prime itself as composite.

The implementation allocates one byte per odd value in the segment and $O(\sqrt N)$ bytes for its dense base sieve. More advanced large-interval sieves retain the next hit for each prime or bucket hits by destination segment, avoiding repeated quotient/remainder work and out-of-cache state. The locality problem and bucketed approach are studied in the primary work on a cache-optimized sieve; a detailed production example appears in the cache-efficient segmented sieve used for the Goldbach verification.

#Mapping the Work to Hardware

Small primes generate dense, regular stores and are friendly to hardware prefetching. Large base primes produce only a few stores per segment, with little spatial locality. This suggests several independent tuning dimensions:

  • candidate encoding: byte, bit, or a small wheel;
  • segment size and alignment;
  • crossing primes one at a time versus bucketing future hits;
  • clearing a segment versus using generation counters;
  • collecting primes versus counting or streaming them.

SIMD is not automatically useful for composite[x] = 1 because successive addresses for one prime are strided. It is more natural for clearing blocks, scanning bytes for survivors, expanding packed masks, or processing several small-prime patterns. As usual, vectorizing the visible line of arithmetic is less important than arranging the data stream.

Parallelization is comparatively simple after the base primes are known: different segments can be crossed independently. Static scheduling works when segments are similar; ordered output needs either per-segment buffers or a later merge. Sharing one output vector with a lock can erase much of the benefit.

#Reproducible Evaluation

A useful sieve benchmark states:

  • inclusive limit and whether primes are counted, stored, or printed;
  • byte, bit, and wheel encoding;
  • segment size and cache level it is intended to fit;
  • cost of generating base primes;
  • cold versus warm allocation and page state;
  • compiler, flags, ISA target, CPU, and frequency policy.

Test boundary limits 0, 1, 2, 3, every square around a prime, the last partial segment, and limits near the chosen integer type’s endpoints. Differential tests can compare both sieves against trial division for small ranges; larger tests can compare their complete outputs and known prime-count values.

Do not time printing unless formatted output is the subject of the benchmark. A sieve that writes decimal text is usually an integer-formatting benchmark with some prime generation attached.

The central optimization is segmentation, not because it changes $O(N\log\log N)$, but because it changes repeated main-memory traffic into repeated cache traffic. The asymptotic algorithm stays ancient; the useful machine model does not.
