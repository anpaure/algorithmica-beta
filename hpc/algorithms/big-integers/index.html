Big Integers and Karatsuba Multiplication

Machine integers have a useful property: their cost does not depend on their value. Arbitrary-precision integers give up that abstraction. Adding a thousand-limb number touches a thousand limbs; multiplying two of them creates a small algorithm-selection problem.

This chapter builds a nonnegative big integer from first principles. We begin with a normalized limb representation and schoolbook multiplication, derive Karatsuba’s three-product identity, and add a crossover that preserves the fast base case for small and strongly unbalanced operands.

The implementation is educational rather than a replacement for GMP. It nevertheless has a precise domain, checked size arithmetic, defined carry bounds, canonical zero, and a differential-testable C++20 core.

#Limbs and Invariants

Choose a base $B$ that fits one limb and store

$$ x = x_0 + x_1B + x_2B^2 + \cdots + x_{n-1}B^{n-1} $$ in little-endian order. We use uint32_t limbs and $B=10^9$. Decimal conversion is convenient, and a limb product plus two carry-sized terms fits in uint64_t: $$ (B-1)^2+(B-1)+(B-1)<10^{18}+2\cdot10^9<2^{64}. $$

Every object maintains three invariants:

  1. each limb is smaller than $B$;
  2. the most significant stored limb is nonzero;
  3. zero is represented by an empty limb vector.

The last two make equality, comparisons, and recursion boundaries unambiguous. Every arithmetic helper normalizes before returning; “we will remove leading zeros later” is how noncanonical zeros escape into the rest of a library.

#include <algorithm>
#include <cstddef>
#include <cstdint>
#include <iomanip>
#include <limits>
#include <sstream>
#include <span>
#include <stdexcept>
#include <string>
#include <utility>
#include <vector>

class big_uint {
    static constexpr std::uint64_t base = 1'000'000'000ULL;
    std::vector<std::uint32_t> limb_; // least significant first

    void normalize() {
        while (!limb_.empty() && limb_.back() == 0)
            limb_.pop_back();
    }

    static int compare(const big_uint &a, const big_uint &b) {
        if (a.limb_.size() != b.limb_.size())
            return a.limb_.size() < b.limb_.size() ? -1 : 1;
        for (std::size_t i = a.limb_.size(); i != 0; --i)
            if (a.limb_[i - 1] != b.limb_[i - 1])
                return a.limb_[i - 1] < b.limb_[i - 1] ? -1 : 1;
        return 0;
    }

    static big_uint add(const big_uint &a, const big_uint &b) {
        big_uint result;
        std::size_t n = std::max(a.limb_.size(), b.limb_.size());
        if (n == result.limb_.max_size())
            throw std::length_error("big integer is too large");
        result.limb_.reserve(n + 1);

        std::uint64_t carry = 0;
        for (std::size_t i = 0; i != n; ++i) {
            std::uint64_t current = carry;
            if (i < a.limb_.size()) current += a.limb_[i];
            if (i < b.limb_.size()) current += b.limb_[i];
            result.limb_.push_back(std::uint32_t(current % base));
            carry = current / base;
        }
        if (carry != 0)
            result.limb_.push_back(std::uint32_t(carry));
        return result;
    }

    // Precondition: a >= b.
    static big_uint subtract(const big_uint &a, const big_uint &b) {
        if (compare(a, b) < 0)
            throw std::logic_error("negative big_uint subtraction");

        big_uint result;
        result.limb_.resize(a.limb_.size());
        std::int64_t borrow = 0;
        for (std::size_t i = 0; i != a.limb_.size(); ++i) {
            std::int64_t current = std::int64_t(a.limb_[i]) - borrow;
            if (i < b.limb_.size())
                current -= b.limb_[i];
            if (current < 0) {
                current += std::int64_t(base);
                borrow = 1;
            } else {
                borrow = 0;
            }
            result.limb_[i] = std::uint32_t(current);
        }
        result.normalize();
        return result;
    }

    static big_uint slice(const big_uint &x,
                          std::size_t first,
                          std::size_t last) {
        big_uint result;
        if (first >= x.limb_.size())
            return result;
        last = std::min(last, x.limb_.size());
        result.limb_.assign(x.limb_.begin() + first,
                            x.limb_.begin() + last);
        result.normalize();
        return result;
    }

    static big_uint shifted(const big_uint &x, std::size_t limbs) {
        if (x.limb_.empty())
            return {};
        big_uint result;
        if (limbs > result.limb_.max_size() - x.limb_.size())
            throw std::length_error("big integer shift is too large");
        result.limb_.assign(limbs, 0);
        result.limb_.insert(result.limb_.end(),
                            x.limb_.begin(), x.limb_.end());
        return result;
    }

    static big_uint schoolbook(const big_uint &a, const big_uint &b) {
        if (a.limb_.empty() || b.limb_.empty())
            return {};

        big_uint result;
        if (b.limb_.size() >= result.limb_.max_size() ||
            a.limb_.size() >
            result.limb_.max_size() - b.limb_.size() - 1)
            throw std::length_error("big integer product is too large");
        result.limb_.assign(a.limb_.size() + b.limb_.size() + 1, 0);

        for (std::size_t i = 0; i != a.limb_.size(); ++i) {
            std::uint64_t carry = 0;
            for (std::size_t j = 0; j != b.limb_.size(); ++j) {
                std::uint64_t current = result.limb_[i + j]
                    + std::uint64_t(a.limb_[i]) * b.limb_[j] + carry;
                result.limb_[i + j] = std::uint32_t(current % base);
                carry = current / base;
            }

            std::size_t k = i + b.limb_.size();
            while (carry != 0) {
                std::uint64_t current = result.limb_[k] + carry;
                result.limb_[k] = std::uint32_t(current % base);
                carry = current / base;
                ++k;
            }
        }

        result.normalize();
        return result;
    }

    static big_uint karatsuba(const big_uint &a,
                              const big_uint &b,
                              std::size_t crossover) {
        if (a.limb_.empty() || b.limb_.empty())
            return {};

        std::size_t small = std::min(a.limb_.size(), b.limb_.size());
        std::size_t large = std::max(a.limb_.size(), b.limb_.size());

        // Karatsuba's additions and allocations lose on small operands.
        // A balanced split also matters: use the base case when one side is
        // more than twice as long as the other.
        if (small < crossover || large - small > small)
            return schoolbook(a, b);

        std::size_t split = large / 2;
        big_uint a0 = slice(a, 0, split);
        big_uint a1 = slice(a, split, a.limb_.size());
        big_uint b0 = slice(b, 0, split);
        big_uint b1 = slice(b, split, b.limb_.size());

        big_uint z0 = karatsuba(a0, b0, crossover);
        big_uint z2 = karatsuba(a1, b1, crossover);
        big_uint z1 = karatsuba(add(a0, a1), add(b0, b1), crossover);
        z1 = subtract(subtract(z1, z0), z2);

        big_uint low_and_middle = add(z0, shifted(z1, split));
        return add(low_and_middle, shifted(z2, 2 * split));
    }

public:
    big_uint() = default;

    explicit big_uint(std::uint64_t value) {
        while (value != 0) {
            limb_.push_back(std::uint32_t(value % base));
            value /= base;
        }
    }

    static big_uint from_limbs(std::span<const std::uint32_t> limbs) {
        big_uint result;
        for (std::uint32_t limb : limbs)
            if (limb >= base)
                throw std::invalid_argument("limb exceeds representation base");
        result.limb_.assign(limbs.begin(), limbs.end());
        result.normalize();
        return result;
    }

    std::string to_string() const {
        if (limb_.empty())
            return "0";
        std::ostringstream out;
        out << limb_.back();
        for (std::size_t i = limb_.size() - 1; i != 0; --i)
            out << std::setw(9) << std::setfill('0') << limb_[i - 1];
        return out.str();
    }

    static big_uint multiply(const big_uint &a,
                             const big_uint &b,
                             std::size_t crossover = 32) {
        if (crossover < 2)
            throw std::invalid_argument("Karatsuba crossover is too small");
        return karatsuba(a, b, crossover);
    }

    friend bool operator==(const big_uint &, const big_uint &) = default;
};

The code supports nonnegative integers only. from_limbs validates every limb and canonicalizes any high zero limbs, which is useful for binary deserialization and tests. A signed big integer should store sign separately, keep zero signless, and multiply magnitudes before combining signs. Mixing sign into the top limb makes normalization and comparison considerably harder.

#Schoolbook Multiplication

For limb arrays $a$ and $b$, schoolbook multiplication evaluates

$$ c_{i+j}\mathrel{+}=a_i b_j $$

for every pair of limbs, propagating the base-$B$ carry after each inner iteration. Its $nm$ limb products give $O(nm)$ running time and a wonderfully compact hot loop.

The accumulator bound is part of the representation choice. With $B=10^9$, current is safely below $2^{64}$. If we changed to base $2^{32}$ and kept the same expression, the limb product alone could require all 64 bits, leaving no room for an existing result and carry. Such a representation normally uses a 128-bit intermediate or a multiply instruction that exposes high and low halves.

Schoolbook multiplication has strong locality and little control overhead. For small inputs it beats asymptotically faster methods because the compiler can keep the carry chain and several limbs in registers. It is not a temporary “slow implementation”; it remains the leaf kernel of a fast big-integer library.

#Karatsuba’s Identity

Split balanced operands after $k$ limbs:

$$ x=x_0+B^k x_1,\qquad y=y_0+B^k y_1. $$ Expanding directly requires four half-size products. Karatsuba observes that the middle coefficient can be recovered with one product: $$ \begin{aligned} z_0 &= x_0y_0,\\ z_2 &= x_1y_1,\\ z_1 &= (x_0+x_1)(y_0+y_1)-z_0-z_2,\\ xy &= z_0+B^kz_1+B^{2k}z_2. \end{aligned} $$ The recurrence $$ T(n)=3T(n/2)+O(n) $$

solves to $O(n^{\log_2 3})\approx O(n^{1.585})$. The original result was published by Karatsuba and Ofman in Multiplication of Many-Digital Numbers by Automatic Computers.

Our implementation uses nonnegative sums. Mathematically, z1 is the sum of the two cross products, so both checked subtractions are valid. Normalizing each recursive result is essential: split positions count limbs, and a stray high zero would change balance decisions and termination.

#The crossover is empirical

Karatsuba replaces one recursive multiplication with several additions, slices, shifts, and temporary allocations. It wins only above a machine- and implementation-specific size. The default of 32 limbs in the example is a policy value, not a published constant.

Benchmark a range of balanced operand sizes, locate a stable crossover, and retune after changing the base-case kernel, allocator, limb width, or CPU. The official GNU MP multiplication documentation uses tuned thresholds between schoolbook, Karatsuba, Toom variants, and FFT multiplication; its Karatsuba notes explain why optimizing the base case can move the threshold upward.

Unbalanced operands need separate treatment. Splitting a 32-limb value against a 10,000-limb value creates many zero high halves and temporary work. The code deliberately returns to schoolbook multiplication when one operand is more than twice as long as the other. Production libraries use blocked base cases or specialized unbalanced Toom algorithms.

#Mapping Multiplication to Hardware

The base-case inner loop has two dependency chains: the carry and repeated updates to the destination. Useful optimizations include:

  • accumulating several output diagonals independently;
  • unrolling to overlap multiply latency;
  • using the target’s full-width multiply-high/low operations;
  • separating allocation from arithmetic and reusing scratch buffers;
  • specializing squaring, where cross products occur in symmetric pairs.

Naively vectorizing limb products does not solve carry propagation. SIMD can generate several partial products, but those products still need exact column accumulation. Wider vector lanes are most useful when paired with a redundant representation, delayed normalization, or an instruction set designed for multi-precision arithmetic.

Karatsuba is more sensitive to memory management than its recurrence suggests. The self-contained code allocates at every slice and addition so the invariants are obvious. A performance implementation passes preallocated scratch space through the recursion and writes shifted results directly into the destination. That changes constants, not the algebra.

#Conversion and Other Operations

Base $10^9$ makes decimal output simple: print the high limb normally and every lower limb as exactly nine digits. Parsing can consume groups of nine decimal digits with

$$ x\leftarrow 10^9x+g, $$

using a multiply-by-one-limb and add-one-limb primitive. Binary bases make shifts, bit operations, and division normalization easier. The right base follows the surrounding workload.

Addition, subtraction, comparison, and multiplication are not a complete integer type. Division, modular reduction, parsing errors, allocation limits, signed semantics, and exception guarantees need equally explicit contracts. Cryptographic code additionally needs constant-time control flow and memory access; this teaching implementation does not provide it.

#Validation and Benchmarking

Differential-test the complete decimal result against a mature arbitrary-precision implementation. Include zero, one, values exactly at limb boundaries, long runs of base - 1, unequal sizes, leading-zero-producing subtractions inside Karatsuba, and sizes immediately around the crossover. Random testing should vary both values and limb counts.

Useful algebraic properties include

$$ x(y+z)=xy+xz,\qquad xy=yx,\qquad x\cdot0=0, $$

although a shared bug in addition can make the first property less independent than it looks. Sanitizers are valuable for size and indexing errors; a big-integer oracle is still needed for arithmetic truth.

For performance, report operand limb counts and balance, representation base, crossover, allocation policy, whether operands are equal, and whether conversion is timed. Benchmark cold one-shot products separately from repeated products with reusable scratch storage. Plot schoolbook and Karatsuba across the crossover instead of timing one conveniently large input.

The important transition is not “quadratic bad, Karatsuba good.” It is a hierarchy: canonical limbs make the arithmetic trustworthy, a tight schoolbook kernel wins the small regime, and Karatsuba earns its extra machinery only where three recursive products finally cost less than four.
