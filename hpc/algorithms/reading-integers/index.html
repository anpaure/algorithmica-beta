Reading Decimal Integers

Reading an integer is easy when it happens once. Reading a few gigabytes of them is a small systems problem disguised as elementary arithmetic.

There are really three different jobs involved:

  1. obtaining bytes from a file or a socket,
  2. finding the boundaries of the next token,
  3. converting the digits inside that token to an integer.

Formatted input functions do all three, together with locale handling and a fairly generous grammar. This is exactly what we want for a configuration file and often much more than we want for a machine-generated stream of decimal integers. In this chapter, we will separate these jobs, define a deliberately narrow grammar, and then optimize the hot part without quietly changing what the parser accepts.

The distinction is important. Replacing scanf with mmap does not make digit conversion free, and replacing a scalar digit loop with SIMD does not make one system call per byte acceptable. Optimizing the wrong layer is a surprisingly effective way to produce a very sophisticated slow program.

#The Contract

We will parse a signed 64-bit integer from a half-open byte range [first, last). The token has the following grammar:

integer := [ '+' | '-' ] digit+
digit   := '0' ... '9'

There is no leading whitespace in this low-level function: tokenization is the caller’s job. On success, the parser returns a pointer to the first non-digit. On failure, it distinguishes an invalid token from a value outside the range $[-2^{63}, 2^{63}-1]$, and it leaves the output unchanged.

This is close to std::from_chars, with one intentional difference: the standard function does not accept a leading + for integers. If its exact grammar is suitable, use it first. It is non-allocating, locale-independent, and already has the right range-based interface.

Here is a complete scalar implementation of our slightly different contract:

#include <charconv>
#include <cstdint>
#include <limits>

struct parse_result {
    const char *next;
    std::errc error;
};

parse_result parse_i64(const char *first, const char *last,
                       std::int64_t &output) {
    const char *p = first;
    bool negative = false;

    if (p != last && (*p == '+' || *p == '-')) {
        negative = (*p == '-');
        ++p;
    }

    if (p == last || *p < '0' || *p > '9')
        return {first, std::errc::invalid_argument};

    const std::uint64_t positive_limit =
        std::uint64_t(std::numeric_limits<std::int64_t>::max());
    const std::uint64_t limit = positive_limit + std::uint64_t(negative);

    std::uint64_t magnitude = 0;
    bool overflow = false;

    do {
        unsigned digit = unsigned(*p - '0');
        if (!overflow) {
            if (magnitude > (limit - digit) / 10)
                overflow = true;
            else
                magnitude = magnitude * 10 + digit;
        }
        ++p;
    } while (p != last && *p >= '0' && *p <= '9');

    if (overflow)
        return {p, std::errc::result_out_of_range};

    std::int64_t value;
    if (!negative) {
        value = std::int64_t(magnitude);
    } else if (magnitude == positive_limit + 1) {
        value = std::numeric_limits<std::int64_t>::min();
    } else {
        value = -std::int64_t(magnitude);
    }

    output = value;
    return {p, {}};
}

The apparently fussy limit calculation is what makes -9223372036854775808 work. Its magnitude does not fit in an int64_t, so negating a signed intermediate would overflow. We accumulate into an unsigned type and handle that one endpoint explicitly.

The check is written as

$$ x \le \left\lfloor\frac{L-d}{10}\right\rfloor $$

before evaluating $10x+d$. Therefore the multiplication itself never overflows. The parser also continues to the end of an oversized digit sequence after detecting overflow. This makes next useful for recovery and prevents malformed input from being reinterpreted as a second number.

#Getting the Bytes

The slowest imaginable input loop calls a library function for every character. The next-slowest merely hides that call behind a nicer interface. The first important optimization is to operate on blocks.

fread, a buffered stream, and a hand-written read loop can all provide blocks. The exact choice is usually less important than obeying two rules:

  • process only the number of bytes that were actually returned;
  • preserve the unfinished token at the end of a block and prepend it to the next one.

The second rule is easy to miss because benchmark generators often end every line with a newline and happen to align favorably. Real files are under no obligation to cooperate.

A block reader can be organized like this:

#include <array>
#include <cstdio>
#include <string>

std::string carry;
std::array<char, 64 * 1024> buffer;

while (std::size_t n = std::fread(buffer.data(), 1, buffer.size(), stdin)) {
    // Append bytes until the last complete token, parse complete tokens,
    // and keep the unfinished suffix in `carry` for the next iteration.
}

// At EOF, parse `carry` as a final token even if there is no delimiter.

Production code normally avoids appending every block to a std::string: it parses the complete prefix in place and copies only the short suffix. The logical structure stays the same. If a token can be arbitrarily long, the carry buffer must be growable or the parser must impose and report a maximum token length.

Memory mapping can remove an extra copy for regular files, but it is not a drop-in replacement for input. Pipes are not seekable, empty files need special handling, mapping can fail, and the mapped region still has an exact end that vector loads may not cross. See system calls and memory mapping for the underlying mechanisms.

#Formatted input and synchronization

The usual progression in a C++ benchmark is:

  1. std::cin with its default configuration;
  2. std::ios::sync_with_stdio(false) and an untied input stream;
  3. scanf or another formatted C interface;
  4. block input plus a specialized converter.

Disabling synchronization can remove coordination with C streams, but it does not turn operator>> into a narrow decimal parser. Formatted input still has a wider contract and more state. Conversely, a custom converter fed one byte at a time is still dominated by input overhead. Benchmarking the layers separately tells us which change helped.

#The Scalar Loop

For a positive token, conversion is Horner’s rule:

$$ x = (((d_0) \cdot 10 + d_1) \cdot 10 + d_2) \cdots 10 + d_{k-1}. $$

It performs one dependent multiply-add per digit. On modern out-of-order processors, different tokens can overlap, but the digits of one token form a dependency chain. This is the first real computational bottleneck after buffering.

There is also a branch deciding whether the current byte is a digit. It is predictable for a regular file such as one positive integer per line, and much less predictable for mixed token lengths and separators. A branchless rewrite is not automatically better: it often adds instructions to every digit merely to avoid one correctly predicted branch. This is a case for measurement, not aesthetic preference.

Before reaching for intrinsics, try std::from_chars and inspect the generated code. Library implementations are allowed to specialize common bases and widths, and unlike a benchmark sketch they already specify invalid input and overflow behavior.

#Eight Digits at Once

When there are at least eight known digits available, we can shorten the dependency chain with SWAR—SIMD within a register. Load eight bytes, turn them into numerical digits, and combine neighboring fields in a tree:

1 2 3 4 5 6 7 8
 \_/   \_/   \_/   \_/       12, 34, 56, 78
   \___/       \___/           1234, 5678
       \_______/                12345678

The following x86-oriented routine is safe for unaligned input because memcpy is used for the load. It succeeds only when all eight bytes are decimal digits:

#include <cstdint>
#include <cstring>

bool parse_8_digits(const char *p, std::uint32_t &output) {
    std::uint64_t x;
    std::memcpy(&x, p, sizeof x);  // exactly eight accessible bytes

    // This test works byte-wise on little-endian machines. For a decimal
    // byte, both expressions leave the high bit clear; an out-of-range byte
    // sets at least one high bit.
    constexpr std::uint64_t high_bits = 0x8080808080808080ULL;
    if (((x + 0x4646464646464646ULL) |
         (x - 0x3030303030303030ULL)) & high_bits)
        return false;

    x -= 0x3030303030303030ULL;
    x = (x * 10 + (x >> 8)) & 0x00ff00ff00ff00ffULL;
    x = (x * 100 + (x >> 16)) & 0x0000ffff0000ffffULL;
    x = (x * 10000 + (x >> 32)) & 0x00000000ffffffffULL;

    output = std::uint32_t(x);
    return true;
}

This is not a replacement for the scalar parser. It is a fast path. The caller must first know that eight bytes are accessible, incorporate the chunk into the current magnitude with the same overflow check, and fall back for the remaining zero to seven digits. The constants also assume little-endian byte order; portable code needs an endian-specific load or a byte swap.

The tree has logarithmic depth instead of eight serial multiply-adds, which is the useful part. The arithmetic itself is cheap enough that validation, token boundaries, and the cost of moving data can easily become dominant.

#SIMD Is Usually a Tokenizer First

Variable-length integers are an inconvenient SIMD workload. A 256-bit register may contain three complete tokens, half of a fourth, and several delimiters. The lanes do not know where one integer ends and the next begins.

SIMD is still excellent at classifying bytes. For ASCII input, compare a vector against '0' and '9', combine the results, and extract a bit mask. The set bits identify digits—or, after inversion, token boundaries. We can then:

  • skip long spans without examining every byte individually;
  • locate delimiters with ctz on the mask;
  • dispatch fixed-size digit runs to routines such as parse_8_digits;
  • process the final partial vector with a scalar tail.

Two safety details matter more than the particular intrinsic:

  1. A full-width load is allowed only when that many bytes remain. For the tail, copy the remaining bytes into a padded local array or use a masked load whose architectural contract permits it.
  2. Classification is not validation of the whole token. Signs, empty fields, overflow, and unexpected punctuation still need defined behavior.

An alternative is to transpose several independent byte streams and update several integer accumulators in parallel. This exposes instruction-level parallelism, and it was the most interesting idea in the historical companion experiments for this chapter. It also creates partition-boundary repair work and assumes a very regular format. For a fixed-width data feed that may be a fine trade; for a general integer parser it is usually too much machinery.

The broader lesson is that SIMD need not perform the entire algorithm to be useful. Separating structural scanning from semantic conversion is also the central idea behind high-throughput parsers such as the primary research on SIMD JSON parsing.

#Benchmarking the Parser

Integer parsing results are unusually easy to overstate. A useful benchmark records at least:

  • the distribution of token lengths and signs;
  • the delimiter grammar;
  • whether the input is already resident in memory;
  • whether validation and overflow detection are enabled;
  • whether the checksum or consumer work prevents dead-code elimination;
  • whether bytes, integers, or both are used as the denominator;
  • compiler, flags, ISA target, CPU, and frequency policy.

A parser specialized for eight unsigned digits followed by a newline solves a different problem from scanf("%lld"). Comparing them can illuminate the price of the wider contract, but it does not make them interchangeable.

The repository’s original experiments were run around 2022 on a Zen 2 processor with Clang 13 and included buffered, memory-mapped, branchless, SIMD, and transposed variants. They are useful experimental archaeology, not portable performance promises: several variants assume newline-delimited non-negative integers, complete buffers, or convenient padding. This chapter therefore keeps the optimization ideas while giving the boundary conditions first-class status.

#Checklist

For a high-throughput integer reader, the winning order is usually:

  1. freeze the accepted grammar and error semantics;
  2. read blocks and handle short reads and final tokens correctly;
  3. use from_chars or a checked scalar loop as the reference implementation;
  4. profile tokenization and digit conversion separately;
  5. add fixed-width SWAR fast paths for common lengths;
  6. use SIMD to classify bytes when structural scanning is still expensive;
  7. differential-test every optimized path against the reference on boundaries and random input.

The last point is essential. Test 0, -0, both signed endpoints, one-past-each-endpoint, every token length around the fast-path width, all split positions at a buffer boundary, invalid signs, empty tokens, embedded punctuation, and an EOF immediately after the last digit. Fast input code tends to be correct on ten million random numbers and wrong on the eleventh byte of a carefully chosen file.
