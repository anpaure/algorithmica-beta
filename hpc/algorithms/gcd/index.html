Binary GCD

Euclid’s algorithm is almost two and a half millennia old. The instruction that limits it is much younger.

For nonnegative integers $a$ and $b$, the greatest common divisor satisfies

$$ \gcd(a,b)= \begin{cases} a, & b=0,\\ \gcd(b,a\bmod b), & b>0. \end{cases} $$ The remainder does not change the common divisors because $$ a\bmod b=a-\left\lfloor\frac ab\right\rfloor b. $$

This gives the familiar loop:

#include <cstdint>
#include <utility>

uint64_t euclid(uint64_t a, uint64_t b) {
    while (b != 0) {
        a %= b;
        std::swap(a, b);
    }
    return a;
}

Its number of iterations is logarithmic; consecutive Fibonacci numbers produce the worst remainder sequence. On a word-RAM model, the algorithm is excellent. On a real core, every iteration depends on an integer division from the preceding one. A 64-bit divide can have latency in the tens of cycles and limited throughput, leaving little independent work to overlap.

The first optimization question is therefore not “how do we unroll Euclid?” It is “can we preserve the invariant without division?”

#Stein’s Identities

The binary GCD algorithm, often called Stein’s algorithm, uses shifts and subtraction. It follows from four identities:

$$ \begin{aligned} \gcd(0,b)&=b,\\ \gcd(2a,2b)&=2\gcd(a,b),\\ \gcd(2a,b)&=\gcd(a,b) && \text{when $b$ is odd},\\ \gcd(a,b)&=\gcd(a,b-a) && \text{when $0The last identity is Euclid with a deliberately small quotient. By itself that would be slow, but after removing powers of two, both values are odd. Their difference is even, so the next shift makes substantial progress.

Factor out all powers of two shared by the original inputs. Then keep one operand odd, strip every factor of two from the other, subtract the smaller odd value from the larger, and repeat.

#Counting Zeros in One Instruction

Dividing an unsigned integer by its largest power-of-two factor means shifting by the number of trailing zero bits. C++20 exposes this operation as std::countr_zero; x86 commonly implements it with tzcnt when BMI1 is available or an equivalent sequence on older targets.

Unlike compiler built-ins such as __builtin_ctz, the standard function has a defined result for zero. Shifting a word by its full width is still undefined, however, so the algorithm checks for zero before using the count as a shift amount.

#include <algorithm>
#include <bit>
#include <concepts>

template<std::unsigned_integral T>
T binary_gcd(T a, T b) {
    if (a == 0)
        return b;
    if (b == 0)
        return a;

    // a | b is nonzero. These are exactly the factors of two
    // present in both original operands.
    const unsigned common = unsigned(std::countr_zero(a | b));

    // Keep a odd throughout the loop.
    a >>= std::countr_zero(a);

    while (b != 0) {
        b >>= std::countr_zero(b);

        const T lo = std::min(a, b);
        const T hi = std::max(a, b);
        a = lo;
        b = hi - lo;
    }

    return a << common;
}

The subtraction cannot underflow because hi >= lo. When the values are equal it produces zero, and the loop terminates before asking for another shift. The final left shift reconstructs the common power of two; the mathematical gcd fits in T, and unsigned shifting has defined modulo semantics in any case.

Restricting the template to unsigned types avoids three unrelated hazards:

  • std::abs(INT_MIN) is not representable as a signed int;
  • signed overflow is undefined in C++;
  • the meaning of a right shift of a negative value is not the arithmetic operation used in the proof.

An interface accepting signed integers can convert their magnitudes carefully, as std::gcd does. That conversion is part of the interface, not part of the binary algorithm.

#The Invariant

Let $s$ be the saved common power of two. At loop entry, a is odd and

$$ 2^s\gcd(a,b) $$

equals the gcd of the original inputs.

Removing trailing zeros from b is valid because a is odd: no factor of two can be common. Afterward both values are odd. Replacing them with

$$ \min(a,b) \quad\text{and}\quad |a-b| $$

preserves every common divisor, and the difference is even unless it is zero. Assigning the minimum to a keeps a odd for the next iteration. When b reaches zero, a is the remaining odd gcd; multiplying by $2^s$ restores the answer.

This proof also explains every precondition in the code. Moving countr_zero(b) below the subtraction without checking equality would call a compiler built-in on zero in many older versions of this routine—a tiny ordering change that converts a correct algorithm into undefined behavior.

#What the Core Executes

The hot loop contains:

  • a trailing-zero count and variable shift;
  • a comparison with a min/max selection;
  • one subtraction;
  • the loop branch.

The iterations still form a dependency chain, but no general division remains. Compilers often lower min and max to conditional moves, although instruction selection depends on the target and surrounding code. Inspect the generated assembly before reasoning from source operators.

Binary GCD is not automatically faster everywhere. Some standard libraries already use it; small operand widths may have cheaper division; and a processor can execute division differently from the machine used in an old benchmark. The input distribution also changes the iteration count. Measure the implementation you will deploy.

#Inputs Matter

A useful benchmark includes several families:

  • uniformly distributed word-sized pairs;
  • pairs with large shared powers of two;
  • equal values and zeros;
  • coprime consecutive Fibonacci numbers for Euclid;
  • pairs with a deliberately large gcd;
  • small values embedded in a wider type.

Generate inputs outside the timed region, retain a checksum so calls cannot be deleted, and compare every result with std::gcd. If one fixed pair is repeated, the branch predictor and compiler may learn a workload unlike the intended one.

For a stronger correctness test, exhaust all pairs of 12-bit values and fuzz full-width pairs. Boundary cases are disproportionately valuable: zero, equality, and the top bit are exactly where unsafe bit operations tend to fail.

#Related Problems

The extended Euclidean algorithm also computes Bézout coefficients. A binary extended GCD exists, but tracking coefficients while avoiding overflow is more involved; replacing division there is not a drop-in change.

For multiprecision integers, the balance changes again. Subtracting nearly equal numbers one limb at a time can require many iterations, while Lehmer’s and half-GCD algorithms use leading limbs to batch several Euclidean quotients. Optimizing a word-sized primitive and optimizing a thousand-bit integer are different problems even when both functions are named gcd.

Binary GCD is a compact demonstration of performance engineering at its best: an expensive instruction is not replaced by a clever encoding of the same instruction, but by a different mathematical decomposition whose primitives match the hardware.
