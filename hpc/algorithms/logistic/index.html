Optimizing Logistic Regression

Logistic regression is a small model with an honest performance lesson. Its mathematics fits on a page, but the program contains several distinct kernels: a dot product or matrix multiplication, a nonlinear probability conversion, a loss reduction, and—during training—an optimizer that decides how many times those kernels run.

Combining them into one benchmark makes it easy to optimize the wrong thing. For class prediction, the exponential may be unnecessary. For probability output, it is required and must be evaluated stably. For training, a faster gradient kernel can still lose end to end if a different optimizer needs many more iterations.

We will first make the numerical contract correct, then map the linear algebra to the machine, and finally discuss quantization without assuming that “machine learning tolerates error” is an overflow proof.

#Binary Logistic Regression

For a feature vector $x\in\mathbb R^d$, weights $w$, and bias $b$, the model computes a logit

$$ z = b + \sum_{j=0}^{d-1} w_jx_j $$ and maps it to a probability with the sigmoid $$ \sigma(z)=\frac{1}{1+e^{-z}}. $$

The predicted class at threshold $1/2$ is simply z >= 0: the sigmoid is monotone and $\sigma(0)=1/2$. If the caller needs only a class label, evaluating an exponential and dividing does not improve the answer.

When a probability is required, the direct formula overflows for a large negative z because it evaluates $e^{-z}$. Use two algebraically equivalent branches:

#include <cmath>

double sigmoid(double z) {
    if (z >= 0) {
        double e = std::exp(-z);
        return 1 / (1 + e);
    } else {
        double e = std::exp(z);
        return e / (1 + e);
    }
}

In each branch the exponential’s argument is nonpositive, so it cannot overflow. Underflow for an extreme logit produces the correct limiting probability, zero or one.

#Loss from logits

For a binary label $y\in{0,1}$, cross entropy is often written

$$ -y\log\sigma(z)-(1-y)\log(1-\sigma(z)). $$ Computing the probability first is a numerical mistake: it may round to exactly zero or one, after which a logarithm produces infinity even when the loss has a finite representable expression. Define $$ \operatorname{softplus}(t)=\log(1+e^t) $$

and evaluate the loss directly from the logit:

double softplus(double x) {
    if (x > 0)
        return x + std::log1p(std::exp(-x));
    return std::log1p(std::exp(x));
}

double binary_log_loss(double logit, bool label) {
    return label ? softplus(-logit) : softplus(logit);
}

This also handles infinite logits in the expected limiting way; NaN propagates. The derivative with respect to the logit is still the compact

$$ \frac{\partial L}{\partial z}=\sigma(z)-y. $$

#Multiclass Logistic Regression

For $C$ classes, each class has a weight vector and bias. The model produces logits $$ z_c=b_c+\sum_j W_{cj}x_j $$ and the softmax distribution $$ p_c=\frac{e^{z_c}}{\sum_k e^{z_k}}. $$ Exponentiating raw logits can overflow. Subtract their maximum $m=\max_c z_c$: $$ p_c=\frac{e^{z_c-m}}{\sum_k e^{z_k-m}}. $$

Every exponent is now at most zero, and at least one term equals one. This shifted evaluation is analyzed in the primary numerical study Accurate Computation of the Log-Sum-Exp and Softmax Functions.

#include <algorithm>
#include <cmath>
#include <cstddef>
#include <span>
#include <stdexcept>
#include <vector>

void require_finite(std::span<const double> values) {
    if (values.empty())
        throw std::invalid_argument("empty logit vector");
    for (double x : values)
        if (!std::isfinite(x))
            throw std::domain_error("softmax requires finite logits");
}

std::vector<double> softmax(std::span<const double> logits) {
    require_finite(logits);
    double shift = *std::max_element(logits.begin(), logits.end());

    std::vector<double> probabilities(logits.size());
    double sum = 0;
    for (std::size_t i = 0; i != logits.size(); ++i) {
        probabilities[i] = std::exp(logits[i] - shift);
        sum += probabilities[i];
    }
    for (double &p : probabilities)
        p /= sum;
    return probabilities;
}

double multiclass_log_loss(std::span<const double> logits,
                           std::size_t label) {
    require_finite(logits);
    if (label >= logits.size())
        throw std::out_of_range("class label");

    double shift = *std::max_element(logits.begin(), logits.end());
    double sum = 0;
    for (double z : logits)
        sum += std::exp(z - shift);

    return std::log(sum) - (logits[label] - shift);
}

The loss uses log-sum-exp directly instead of taking the logarithm of a rounded softmax probability. Its gradient with respect to logit $z_c is $p_c-[c=y].

Again, class prediction does not require softmax:

std::size_t predicted_class(std::span<const double> logits) {
    require_finite(logits);
    return std::size_t(std::max_element(logits.begin(), logits.end())
                       - logits.begin());
}

max_element resolves an exact tie in favor of the first class. If class ordering should not decide ties, specify and implement another policy explicitly.

Subtracting the maximum and exponentiating preserves the order. Skipping softmax is an algorithmic optimization with an exact proof, not an approximation.

#The Linear Kernel

For one sample, inference is a matrix-vector product. The following scalar reference uses class-major weights: every class row is contiguous, arbitrary feature counts are valid, and there is no hidden SIMD-width requirement.

#include <cmath>
#include <limits>
#include <span>
#include <stdexcept>
#include <vector>

std::vector<double> logits(std::span<const double> features,
                           std::span<const double> weights,
                           std::span<const double> bias) {
    std::size_t classes = bias.size();
    std::size_t dimensions = features.size();
    if (classes == 0)
        throw std::invalid_argument("model has no classes");
    if (dimensions != 0 &&
        classes > std::numeric_limits<std::size_t>::max() / dimensions)
        throw std::length_error("model shape overflow");
    if (weights.size() != classes * dimensions)
        throw std::invalid_argument("weight shape mismatch");

    std::vector<double> result(bias.begin(), bias.end());
    for (std::size_t c = 0; c != classes; ++c) {
        double sum = result[c];
        for (std::size_t j = 0; j != dimensions; ++j)
            sum = std::fma(weights[c * dimensions + j], features[j], sum);
        result[c] = sum;
    }
    return result;
}

This loop exposes one dependency chain per class. Several independent class accumulators can execute in parallel, while SIMD can process adjacent features inside a row. A vectorized implementation must still reduce each vector accumulator horizontally and handle the final dimensions % lanes features with a scalar or masked tail.

Class-major storage is natural when processing one sample. With many samples, inference becomes matrix multiplication:

$$ Z=XW^T+b. $$

A tuned GEMM reuses blocks of both samples and weights in cache and amortizes packing. Calling a matrix-vector kernel separately for each row of a large batch leaves much of that reuse on the table. The relevant case study is therefore matrix multiplication, not a more ornate sigmoid.

When the number of classes is small, feature-major weights can instead update several class accumulators from one loaded feature. This may reuse features[j] better and vectorize across padded classes. It also changes the best layout for training and batches. Layout belongs in the benchmark contract.

#Training Is More Than the Kernel

For one labeled sample, multiclass gradient accumulation is

$$ G_{cj} \mathrel{+}= (p_c-[c=y])x_j. $$

Computing logits and this outer product is the training kernel. Stochastic gradient descent, momentum, Adam, L-BFGS, regularization, line search, stopping criteria, and data ordering are optimization algorithms. They determine which parameter updates are made and how many full or partial passes are required.

This distinction prevents a common benchmarking error. Comparing two training programs after the same number of iterations says little if their optimizers reach different objective values. Compare kernel throughput with fixed tensors, and separately compare end-to-end time to a fixed validation metric or loss under a documented optimizer configuration.

Training also has more data movement than inference. It writes gradients, optimizer state, and perhaps per-sample probabilities. Fusing loss and gradient production can avoid materializing a full probability matrix, but the fused code must retain the same reduction order and numerical contract.

#Quantization

Reducing weights and activations from floating point to 8-bit integers can reduce model traffic and let one instruction process more products. It is not valid merely because the input data is noisy. Quantization changes the model and needs calibration or quantization-aware training; the primary integer-only inference work describes scales, zero points, and the co-design with training in detail.

Even the simplest symmetric int8_t dot product needs a proved accumulator range. A product can be as large as $(-128)^2=16384$. Therefore a signed 32-bit sum is safe for at most

$$ \left\lfloor\frac{2^{31}-1}{16384}\right\rfloor=131071 $$

unbiased terms:

#include <cstdint>
#include <limits>
#include <span>
#include <stdexcept>

std::int32_t dot_i8(std::span<const std::int8_t> a,
                    std::span<const std::int8_t> b) {
    if (a.size() != b.size())
        throw std::invalid_argument("dot-product shape mismatch");

    constexpr std::size_t safe_terms =
        std::size_t(std::numeric_limits<std::int32_t>::max()) / (128 * 128);
    if (a.size() > safe_terms)
        throw std::overflow_error("int32 accumulator can overflow");

    std::int32_t sum = 0;
    for (std::size_t i = 0; i != a.size(); ++i)
        sum += std::int32_t(a[i]) * std::int32_t(b[i]);
    return sum;
}

Nonzero quantization zero points introduce correction terms; bias accumulation and batching may require wider intermediates. Production kernels commonly widen partial products, accumulate into 32 or 64 bits, and requantize with a documented rounding rule. Saturating a too-small accumulator does not make the result safe—it merely turns undefined or wrapped behavior into a silent model error.

Integer SIMD instructions often compute several widened dot products at once. The scalar function above remains the reference for arbitrary lengths; an optimized version processes full vectors and sends the tail through the same scalar arithmetic. Accuracy must then be evaluated on the complete calibrated model, not inferred from one dot product.

#Benchmarking the Right Thing

A reproducible evaluation separates at least three levels:

  1. kernel: fixed-shape logits, softmax/loss, or gradient accumulation with data already resident;
  2. model inference: input preparation, batching, all kernels, and required probability or label output;
  3. training: time and resources required to reach a fixed objective or validation target.

Record batch size, classes, features, sparsity, data layout, precision, accumulator width, tail policy, compiler and math flags, ISA target, CPU, and thread count. Fast-math flags may reassociate reductions and change NaN, infinity, and signed-zero behavior; they are part of the numerical method, not merely a speed switch.

Test stable functions on logits around zero, large positive and negative values, and class vectors with wide dynamic range. Check that probabilities are nonnegative and sum close to one, compare losses against a higher-precision reference, and finite-difference-check gradients. For quantized kernels, test the all--128 overflow boundary and compare every vector/tail path with the scalar reference.

The optimization hierarchy is now clear. Remove probability conversion when order alone is required. Make required nonlinear functions stable. Arrange the dot products as matrix-vector or matrix-matrix work with explicit tails. Quantize only with an accumulator proof and an accuracy-validation process. And never report a faster optimizer merely because one iteration became cheaper.
