Reading and Writing Floating-Point Numbers

Integer conversion is mostly arithmetic in base ten. Floating-point conversion is arithmetic plus a proof.

Consider the text 0.1. Its value is exactly $1/10$, but no finite binary fraction equals $1/10$. A parser must choose the nearest representable binary value. A formatter then faces the reverse problem: it should print enough decimal digits to identify that value, but usually no more than necessary. Both directions must make the same choice at boundaries where two floating-point numbers are almost equally close.

This chapter is about optimizing the conversion pipeline without weakening that contract.

#What Does “Correct” Mean?

A floating-point input grammar may contain a sign, integer and fractional digits, a decimal exponent, and special values such as infinity and NaN. The numerical part can be written as

$$ (-1)^s M\cdot10^e, $$

where $M$ is an integer assembled from the digits and $e$ accounts for both the decimal point and the explicit exponent.

Parsing normally promises correct rounding: return the representable value nearest to the exact real number under the specified rounding rule. This includes subnormal values, overflow, underflow, and decimals lying extremely close to a midpoint.

For output, three contracts are common:

  • fixed precision: print a requested number of digits after the decimal point;
  • significant digits: print a requested number of meaningful digits;
  • shortest round trip: print the shortest decimal that parses back to the original binary value.

These are different problems. Six digits after the point is not sufficient for every float, and seventeen significant digits are sufficient to round-trip every double but are often not shortest.

The constants in std::numeric_limits describe the distinction:

#include <limits>

static_assert(std::numeric_limits<float>::max_digits10 == 9);
static_assert(std::numeric_limits<double>::max_digits10 == 17);

max_digits10 is a sufficient number of significant decimal digits for binary-to-decimal-to-binary round trips. It is not a buffer size and not a claim that every shortest representation has that many digits.

#Why the Naive Parser Fails

A tempting parser accumulates a double, divides by a power of ten for the fractional part, and calls pow(10, exponent). It has three problems.

First, it rounds after nearly every digit, so the final error is not necessarily the correctly rounded value of the original decimal. Second, pow is a general transcendental routine doing far more work than a bounded integer exponent requires. Third, long inputs overflow the accumulator or discard digits without tracking whether the discarded suffix changes the rounding direction.

A sound design separates syntax from conversion:

  1. scan characters and record sign, significant digits, and decimal exponent;
  2. keep as many leading digits as fit in a machine integer and remember whether discarded digits were nonzero;
  3. convert the integer significand times a power of ten to binary;
  4. detect ambiguous cases and use an exact fallback.

Most real-world inputs contain at most 19 significant digits and moderate exponents. Fast parsers exploit this common case with precomputed powers of five and wide integer multiplication. Since

$$ 10^e=2^e5^e, $$

the power of two mainly adjusts the binary exponent, while multiplication or division by a cached power of five determines the significand bits. A high-half product provides the leading bits without constructing an arbitrary-precision integer.

The difficult part is not producing a nearby answer; it is proving when those leading bits determine the unique correctly rounded answer. Eisel–Lemire-style algorithms make this fast path explicit and fall back for truncated, extreme, or midpoint-adjacent inputs. The fallback is rare, but deleting it changes the function’s contract.

#Use the Narrowest Standard Interface

For locale-independent conversion in modern C++, std::from_chars avoids allocation and null-terminated strings. It returns both an error code and the first unconsumed character:

#include <charconv>
#include <optional>
#include <string_view>
#include <system_error>

std::optional<double> parse_double(std::string_view text) {
    double value;
    const char* first = text.data();
    const char* last = first + text.size();

    auto [end, error] = std::from_chars(
        first, last, value, std::chars_format::general
    );

    if (error != std::errc{} || end != last)
        return std::nullopt;
    return value;
}

Checking end is essential. Without it, "1.25ms" is accepted as the valid prefix 1.25. Whether whitespace, a leading plus sign, hexadecimal notation, or NaN belongs to the language is a protocol decision; the from_chars grammar is intentionally narrower than some C library functions.

std::to_chars provides the matching allocation-free output path. With no precision argument, the general format chooses a shortest representation that round-trips through the corresponding parser:

#include <array>
#include <charconv>
#include <stdexcept>
#include <string>

std::string format_double(double value) {
    std::array<char, 64> buffer;
    auto [end, error] = std::to_chars(
        buffer.data(), buffer.data() + buffer.size(),
        value, std::chars_format::general
    );

    if (error != std::errc{})
        throw std::runtime_error("floating-point buffer too small");
    return std::string(buffer.data(), end);
}

The 64-byte buffer is an interface bound chosen for the supported format, not max_digits10. Production code should make that bound a documented invariant or retry with a larger buffer.

from_chars and to_chars remove locale state, allocation, and formatted-stream machinery. They do not guarantee that every standard-library implementation uses the same internal algorithm or has the same throughput. Check the library version along with the compiler when benchmarking.

#Finding the Shortest Decimal

Every finite binary value owns an interval of real numbers that round to it. For a normal value $v$, the interval boundaries lie near the midpoints between $v$ and its predecessor and successor. A shortest formatter seeks the decimal with the fewest significant digits that lies inside this interval and resolves inclusivity according to the rounding rule.

Older algorithms generated digits while repeatedly testing these boundaries, sometimes using multiprecision arithmetic. Ryu and Dragonbox changed the cost model by reducing the problem to fixed-width integer arithmetic and tables of powers. They compute scaled interval bounds, generate decimal digits, and stop as soon as one candidate uniquely identifies the original binary value.

This is why “printing the stored mantissa” is the wrong mental model. The stored significand is binary. Decimal output is a search for a short name whose rounding interval contains that binary number.

For a requested fixed precision, the objective changes. The formatter must round to a decimal place even when that representation does not round-trip. Financial code should also ask whether binary floating point is the correct representation at all; a scaled integer or decimal type may express the contract more directly.

#The Batch Is Larger Than the Number

Once the conversion kernel is fast, surrounding work becomes visible:

  • locating token boundaries;
  • validating separators and protocol grammar;
  • copying substrings into temporary buffers;
  • allocating one string per output value;
  • issuing small reads or writes;
  • reporting the position of malformed input.

Keep input in a contiguous buffer and pass pointer ranges or string_views into the converter. Append output into a reusable buffer and flush it in large blocks. Do not copy a token merely to add a terminating zero for an API that accepts a range.

SIMD can help find structural characters and classify bytes across several candidate numbers at once. The numeric conversion itself is harder to vectorize because token lengths, exponents, and fallback conditions diverge. Parsers such as simdjson use SIMD heavily for document structure while retaining carefully designed scalar number conversion. Parallelism should follow the shape of the work rather than the label “parser.”

#Testing the Corners

Random human-readable decimals exercise the common path but barely touch the rounding boundaries. A useful differential suite includes:

  • zero and negative zero;
  • the smallest subnormal, largest subnormal, smallest normal, and largest finite value;
  • neighboring values around powers of two and ten;
  • decimals exactly at and immediately around rounding midpoints;
  • very long digit strings with sticky nonzero suffixes;
  • exponent overflow and underflow;
  • malformed signs, decimal points, exponents, and trailing characters;
  • every special value the chosen grammar claims to support.

For formatting, generate floating-point values by randomizing their bit patterns, format them, parse the result, and compare bits for every finite value. Also compare against a trusted implementation, because a formatter and parser sharing the same bug can round-trip each other’s mistakes.

Benchmark several corpora separately: short telemetry values, fixed-precision financial-like records, uniformly distributed bit patterns, and known hard cases. Average token length and fallback rate belong next to throughput results.

#Choosing an Implementation

Use the standard charconv interface when its performance and platform support meet the requirement. It gives the optimizer a small, locale-independent boundary and keeps application code independent of the conversion algorithm.

When conversion dominates a measured workload, use a reviewed implementation with an explicit correctness claim. Fast_float implements Eisel–Lemire parsing with fallbacks; Ryu and Dragonbox implement shortest formatting. Integrating one of them is safer than reproducing its tables and boundary proof inside an application.

The deeper optimization lesson is the same as in integer conversion: separate the common representable case from the rare case that needs more machinery, but never confuse “rare” with “impossible.” The slow path is part of the proof.
