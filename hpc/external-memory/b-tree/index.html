B-Trees

A balanced binary search tree needs $\Theta(\log_2 N)$ nodes on a root-to-leaf path. That is excellent when nodes are already in cache. If every node is on a different storage page, however, a lookup performs one random I/O per comparison while using only a few bytes of every page it fetches.

A B-tree changes the unit of progress. One node occupies one block and contains many sorted separator keys, so a single I/O chooses among many children. The comparison work inside a fetched page is almost free in the external memory model; the reduction in tree height is what matters.

Bayer and McCreight introduced the structure as a page-oriented ordered index in “Organization and Maintenance of Large Ordered Indexes”. The basic invariant has survived because it matches storage unusually well: keep every page substantially full, split it when it overflows, and keep all leaves at the same depth.

#One Page, Many Children

Assume a page has $P$ bytes, of which $H$ bytes are header and bookkeeping. If an internal page stores $F$ child identifiers of $C$ bytes and $F-1$ separators of $K$ bytes, then

$$ H+FC+(F-1)K\le P, $$ so the maximum fanout in this simplified layout is $$ F_{\max}=\left\lfloor\frac{P-H+K}{C+K}\right\rfloor. $$

For a 4096-byte page with a 16-byte header, 8-byte child identifiers, and 8-byte fixed-size separators, this calculation gives $F_{\max}=255$. Real pages have slot arrays, variable-length keys, checksums, and alignment, so the usable fanout is lower; the point is that it is measured in hundreds rather than two.

The traditional definition uses a minimum degree $t$. Except for the root, a node contains between $t-1$ and $2t-1$ keys; an internal node consequently has between $t$ and $2t$ children. The root may be smaller, and every leaf has the same depth.

Let the height $h$ count edges from the root to a leaf. A minimally occupied nonempty B-tree of height $h$ has at least

$$ N_{\min}=2t^h-1 $$ keys: the root contributes one, it has two children, and every lower internal node branches at least $t$ ways. Therefore $$ h\le \log_t\frac{N+1}{2}. $$ This exact counting argument is for the classical B-tree, where internal keys are records. A B+ tree counts records only at the leaves, which changes constants but not the height’s asymptotic form. When a block holds $\Theta(B)$ entries, $t=\Theta(B)$ and a point lookup needs $$ O(\log_B N) $$

block transfers. This is the same logarithm as for a binary tree, but with a much larger base.

#Searching a Page

An internal page stores separators and child page identifiers, not machine pointers. The buffer manager turns a page identifier into a cached page or an I/O request. Once the page arrives, ordinary binary search selects the next child.

The exact equality rule is part of the on-disk format. In the following convention, separator[i] is the smallest key belonging to children[i + 1], so an equal key goes right:

#include <algorithm>
#include <cstdint>
#include <span>
#include <stdexcept>

std::uint32_t choose_child(std::span<const std::uint64_t> separators,
                           std::span<const std::uint32_t> children,
                           std::uint64_t key) {
    if (children.size() != separators.size() + 1)
        throw std::invalid_argument("malformed internal page");

    const auto it = std::upper_bound(separators.begin(),
                                     separators.end(),
                                     key);
    const auto index = static_cast<std::size_t>(it - separators.begin());
    return children[index];
}

std::size_t leaf_position(std::span<const std::uint64_t> keys,
                          std::uint64_t key) {
    const auto it = std::lower_bound(keys.begin(), keys.end(), key);
    return static_cast<std::size_t>(it - keys.begin());
}

The page decoder must validate counts and offsets before constructing these spans. The search functions assume the keys have already been checked to be sorted. For duplicate user keys, databases normally append a record identifier or another tie-breaker so that index entries still have a total order.

#B-Tree and B+ Tree

The terminology is unfortunately inconsistent: production systems often call every member of the family a “B-tree.” The classical distinction is:

B-treeB+ tree
recordsmay appear in internal nodes and leavesappear only in leaves
internal keysmay be records themselvescopies or shortened separators
point lookupmay finish above the leavesalways reaches a leaf
range scanrequires an in-order traversalwalks linked neighboring leaves
internal fanoutreduced if records are largeusually higher because entries are small

B+ trees are especially convenient for database indexes. Internal pages form a compact routing structure, while leaves hold all key-to-record references in sorted order. After one root-to-leaf search, a range query continues through leaf sibling links and reads mostly sequential pages.

For $K$ returned entries, a packed B+ tree therefore answers a range query in

$$ O\left(\log_B N+\left\lceil\frac{K}{B}\right\rceil\right) $$

I/Os. The first term finds the starting leaf; the second scans the result. PostgreSQL’s B-tree documentation describes a production variant whose levels are doubly linked, while the SQLite file-format specification shows the concrete distinction between interior and leaf pages.

Whether values live in the leaf or in a separate heap is another independent decision. A leaf may store the whole row, a stable record identifier, or a primary key used for a second lookup. Large values are usually kept out of internal pages and may spill to overflow storage even at the leaf.

#Splitting and Merging

Searching is read-only and simple. Updates are where the occupancy invariant earns its keep.

To insert into a B+ tree:

  1. descend to the target leaf;
  2. insert the new entry if the page has room;
  3. otherwise, divide the entries between two leaves and link the new leaf into the chain;
  4. copy a separator for the new right leaf into the parent;
  5. if the parent overflows, repeat upward;
  6. if the root splits, create a new root with two children.

A split can propagate through $O(\log_B N)$ pages, although most insertions only modify one leaf. In a classical B-tree, promoting a separator moves it out of the child; in a B+ tree, the indexed entry remains in the leaf and the parent receives a routing copy.

Deletion reverses the process. After removing an entry, an underfull page first tries to redistribute entries with a sibling. If that is impossible, two siblings merge and one parent separator disappears. A root left with a single child can be replaced by that child, decreasing the height.

The textbook half-full rule guarantees the height bound, but production fill policies are workload decisions. Leaving free space reduces immediate splits under random insertions; densely packed leaves improve scan bandwidth. Monotonically increasing keys concentrate inserts at the right edge, which may be desirable for locality but can create a concurrency hotspot.

Sorted input admits a different construction. Fill leaves from left to right, link them, and build each parent level from the completed child pages. This bulk loading writes $O(N/B)$ pages after the input has been sorted; if it is not sorted, the external sorting cost comes first.

#A Page Is a Small Storage Engine

A C++ struct is rarely a suitable disk-page format. Variable-length keys make objects move, while persisted pointers and ABI padding have no stable meaning. A common solution is a slotted page:

  • a fixed header records page type, entry count, free-space bounds, and sibling or parent metadata;
  • a compact slot array stores offsets to entries;
  • variable-length key and value bytes grow from the other end of the page;
  • deleting or compacting an entry updates slots without changing its logical order.

Internal separators need only distinguish adjacent child ranges. Prefix or suffix truncation can make them shorter than full leaf keys, increasing fanout. Compression improves height and cache use, but comparison must still implement exactly the database’s ordering, including collation, null handling, and descending fields.

The upper levels are requested on almost every lookup, so a buffer pool tends to keep the root and often the next level resident. The theoretical I/O bound remains useful, but the common path may perform only the final leaf read. Conversely, an index whose leaves point to randomly scattered table rows can turn a beautiful leaf scan into many unrelated heap reads; the index layout and record layout must be analyzed together.

#Persistence and Concurrency

An in-memory split can update several pointers and then return. A persistent split must survive a crash between any two writes. The database needs a recovery protocol—commonly write-ahead logging or copy-on-write pages—that makes the new page, sibling links, parent separator, and allocation metadata recover to one consistent state. Merely flushing the pages in an intuitive order is not a proof of atomicity.

Concurrent readers add another constraint. Holding one global tree lock is correct but destroys scalability. Practical implementations use page latches, version checks, or linked-page variants that let a search move right when a concurrent split changed a page’s range. Reclamation must also wait until no reader can still reach an old page.

These mechanisms are why a production B-tree is much more than its insertion pseudocode. The core asymptotic idea is nevertheless compact:

  1. make a storage block the unit of a node;
  2. spend each block read on hundreds of comparisons;
  3. preserve high occupancy so the base of the logarithm stays large;
  4. place ordered records in linked leaves when range access matters.

A binary tree minimizes comparisons. A B-tree minimizes expensive transfers. On a deep memory hierarchy, that is often the more important objective.
