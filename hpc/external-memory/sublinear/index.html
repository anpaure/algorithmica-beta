Sublinear Algorithms

To compute the exact sum of an arbitrary array, we must inspect every element: an unread value could change the answer. The same obstacle applies to an exact maximum, an exact number of distinct keys, or a complete list of frequent items. If even one block may contain decisive information, no clever layout makes an exact algorithm sublinear.

Approximation changes the question. Instead of “return the answer,” we ask for an estimator whose error is at most $\varepsilon$ with probability at least $1-\delta$, or for a deterministic summary with a stated additive error. The improvement comes from weakening the output contract, not from making the unread data disappear.

Two models are often grouped under the word sublinear:

  • A sublinear-time algorithm has random access to a dataset and probes only a sample of it.
  • A streaming algorithm reads every update once but uses memory much smaller than the stream.

A one-pass sketch is linear-time, not sublinear-time. It is useful because its memory, communication, and later query cost are sublinear. Keeping these resources separate prevents many misleading complexity claims.

#Sampling a Bounded Mean

Suppose a fixed dataset contains $N$ values $x_i\in[0,1]$ with mean

$$ \mu=\frac{1}{N}\sum_{i=1}^N x_i. $$ Draw $k$ indices independently and uniformly, with replacement, and let $\hat\mu$ be the sample mean. Hoeffding’s inequality gives $$ \Pr\left[|\hat\mu-\mu|\ge\varepsilon\right] \le 2e^{-2k\varepsilon^2}. $$ Thus it is sufficient to choose $$ k\ge\frac{\ln(2/\delta)}{2\varepsilon^2}. $$

The sample count does not depend on $N$. It depends on the value range, independence, desired absolute error, and failure probability. If values lie in $[a,b]$, rescale them and pay a factor of $(b-a)^2$. If the quantity of interest is a rare event, a small additive error may be useless as a relative guarantee; stratified or importance sampling may be needed.

Uniform sampling also assumes we can reach a random record without scanning the blocks before it. On an unindexed compressed stream, “choose a random index” may itself require linear work.

#Sampling an Unknown-Length Stream

When the stream length is not known in advance, reservoir sampling maintains a uniform sample in one pass. Store the first $k$ items. When item $i$ arrives, choose a uniform integer in $[0,i)$ and keep the item exactly when that integer is below $k$, replacing the selected reservoir entry.

#include <cstddef>
#include <cstdint>
#include <iterator>
#include <limits>
#include <random>
#include <stdexcept>
#include <vector>

template<class InputIt, class Generator>
auto reservoir_sample(InputIt first,
                      InputIt last,
                      std::size_t sample_size,
                      Generator& generator)
    -> std::vector<typename std::iterator_traits<InputIt>::value_type> {
    using value_type = typename std::iterator_traits<InputIt>::value_type;
    std::vector<value_type> sample;

    if (sample_size == 0)
        return sample;
    sample.reserve(sample_size);

    std::uint64_t seen = 0;
    for (; first != last; ++first) {
        if (seen == std::numeric_limits<std::uint64_t>::max())
            throw std::length_error("stream index does not fit");
        ++seen;

        if (sample.size() < sample_size) {
            sample.push_back(*first);
            continue;
        }

        std::uniform_int_distribution<std::uint64_t> pick(0, seen - 1);
        const std::uint64_t index = pick(generator);
        if (index < sample_size)
            sample[static_cast<std::size_t>(index)] = *first;
    }

    return sample;
}

After processing $n\ge k$ items, every item is present with probability $k/n$. The proof is inductive: an old reservoir item survives step $n$ with probability $1-1/n$, while the new item enters with probability $k/n$. Jeffrey Vitter’s reservoir-sampling paper develops faster skipping variants for streams where generating one decision per item is expensive.

Reservoir sampling uses $O(k)$ memory, but it still reads $n$ items. It is the canonical example of a streaming-space improvement rather than a sublinear-time one.

#Deterministic Heavy Hitters

Sampling can miss an item near the frequency threshold. The Misra–Gries algorithm gives a deterministic alternative.

Fix $k\ge2$ and maintain at most $k-1$ item counters. An arriving item increments its counter if present, occupies an empty counter if available, and otherwise decrements every counter, removing zeroes. Here is the direct version for 64-bit item identifiers:

#include <cstddef>
#include <cstdint>
#include <limits>
#include <stdexcept>
#include <unordered_map>

class misra_gries {
public:
    explicit misra_gries(std::size_t k) : k_(k) {
        if (k < 2)
            throw std::invalid_argument("k must be at least two");
        counters_.reserve(k - 1);
    }

    void add(std::uint64_t item) {
        if (auto it = counters_.find(item); it != counters_.end()) {
            if (it->second == std::numeric_limits<std::uint64_t>::max())
                throw std::overflow_error("counter overflow");
            ++it->second;
            return;
        }

        if (counters_.size() < k_ - 1) {
            counters_.emplace(item, 1);
            return;
        }

        for (auto it = counters_.begin(); it != counters_.end(); ) {
            if (--it->second == 0)
                it = counters_.erase(it);
            else
                ++it;
        }
    }

    const std::unordered_map<std::uint64_t, std::uint64_t>&
    candidates() const noexcept {
        return counters_;
    }

private:
    std::size_t k_;
    std::unordered_map<std::uint64_t, std::uint64_t> counters_;
};

Let $f_x$ be the true frequency of item $x$ in a stream of length $n$, and let $c_x$ be its stored counter, taking $c_x=0$ when absent. Then

$$ f_x-\frac{n}{k}\le c_x\le f_x. $$

In particular, every item with $f_x>n/k$ must remain as a candidate. The stored counter is a lower bound, not the exact frequency. If the input can be read again, a second pass counts only the candidates and removes false positives.

Why does the bound hold? Each decrement step accounts for $k$ distinct stream occurrences: the untracked arriving item and one occurrence represented by each of the $k-1$ counters. There can be at most $n/k$ such steps, and each step can reduce the remembered contribution of any one item by at most one.

The original Misra–Gries paper develops the comparison-based algorithm and its bounds. The straightforward hash-table implementation has an $O(k)$ worst-case update when all counters are decremented, although those full decrements are limited by the accounting argument. More elaborate representations can make latency smoother.

#Count–Min Sketch

Misra–Gries keeps candidates but does not directly estimate every item’s frequency. A Count–Min sketch stores a rectangular array of counters. Each of $d$ rows has a hash function chosen independently from a pairwise-independent family mapping keys into $w$ columns. Updating item $x$ increments counter $(j,h_j(x))$ in every row; querying takes the minimum of those $d$ counters.

For an insertion-only stream, let $f_x$ be an item’s frequency and let

$$ m=\sum_x f_x $$ be the total count. Choose $$ w=\left\lceil\frac{e}{\varepsilon}\right\rceil, \qquad d=\left\lceil\ln\frac{1}{\delta}\right\rceil. $$ For any fixed queried item $x$, the estimate $\hat f_x$ satisfies $$ f_x\le\hat f_x\le f_x+\varepsilon m $$

with probability at least $1-\delta$. Collisions can only increase a counter, which gives the lower inequality; Markov’s inequality bounds the collision mass in one row, and taking the minimum makes all rows fail only with probability $\delta$.

The qualifier “fixed” matters. If a program chooses among millions of queries after seeing their estimates, the one-query guarantee is not automatically simultaneous. A union bound or a stronger analysis must account for the number and adaptivity of queries.

The original Count–Min paper describes point, range, and inner-product queries. Its basic array uses $O(\varepsilon^{-1}\log(1/\delta))$ counters, independent of the number of distinct keys. Negative updates require the turnstile-model analysis; the simple insertion-only overestimate guarantee above no longer follows.

#Distinct Values

Counting distinct keys exactly requires remembering a set in the worst case. HyperLogLog instead hashes each key, uses some hash bits to choose a register, and records the longest observed zero prefix in the remaining bits. Long zero prefixes are rare, so their maxima reveal the scale of the unseen set.

With $r$ registers and ideal hash behavior, the original HyperLogLog analysis gives an asymptotic relative standard error of approximately

$$ \frac{1.04}{\sqrt r}. $$

This is a standard deviation under the model, not a deterministic error bound or a universal high-probability interval. Practical implementations also need the paper’s bias and range corrections, a sufficiently wide hash, and a defined treatment of duplicate serialized values.

#Merging and Adversarial Inputs

Many sketches are valuable because summaries can be combined without replaying raw data:

  • Count–Min arrays with identical dimensions and hash functions merge by counter-wise addition.
  • HyperLogLog registers with identical parameters and hash function merge by component-wise maximum.
  • Misra–Gries summaries can be combined by adding candidate weights and reducing back to the counter budget.
  • Reservoirs require a weighted merge that accounts for the number of source items; concatenating two reservoirs is biased when their source streams have different lengths.

The parameter and hash identity are part of the serialized sketch format. Merging summaries with different seeds may produce a plausible-looking but meaningless answer.

Random hashing also defines the adversary model. A proof may assume the stream is fixed independently of secret random choices. If clients can learn a fixed non-cryptographic hash and then choose keys, they may manufacture collisions. Use an appropriate randomized or keyed hash construction, rotate secrets according to the surrounding protocol, and do not present an average-case sketch guarantee as an adversarial security boundary.

Finally, count the whole resource budget. A sketch with few counters may still perform several random cache accesses per update; wide counters may dominate its memory; and a tiny summary does not make the initial stream free to read. Benchmark update throughput and merge cost, but choose parameters from the mathematical error contract first.

Sublinear algorithms are useful because they say exactly what was traded away. The result is not “probably close” in the abstract: it is close under stated bounds, randomness, query patterns, and failure probability. Those qualifiers are the algorithm.
