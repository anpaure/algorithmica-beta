Algorithmica βSpatial and Temporal Locality

Spatial and Temporal Locality

The external memory model counts transfers using precise $M$ and $B$. Early in an optimization, those parameters may be unknown or the real machine may have several relevant levels. Two qualitative ideas remain useful:

  • Spatial locality: after accessing one address, the program soon accesses nearby addresses that may share a transferred block.
  • Temporal locality: after accessing a value, the program reuses it before the cache evicts it.

Neither is a guarantee. Nearby virtual addresses can cross a page boundary, two addresses can conflict in a set-associative cache, and another thread can displace the working set. Locality is nevertheless a better first question than counting source-level array subscripts.

#Depth First, Breadth First, and Blocking

Consider mergesort. A bottom-up implementation can merge runs of length 1, then 2, then 4, scanning the full array at every level. A top-down implementation recursively finishes one subproblem before moving to its sibling.

The recursive order naturally exposes temporal locality: once a subproblem of size at most $M$ is resident, all recursion below it can finish without another external transfer. If the base case sorts an $M$-element run internally, only

$$ \left\lceil\log_2\frac{N}{M}\right\rceil $$ merge levels remain outside memory. Including the initial run pass, the I/O count is $$ \Theta\left( \frac{N}{B} \left[ 1+\left\lceil\log_2\frac{N}{M}\right\rceil \right] \right). $$

A naive bottom-up implementation starting from single elements instead performs $\Theta((N/B)(1+\log_2 N))$ transfers. The ratio is not a mysterious “recursion speedup”; it is the difference between recognizing an in-memory base case and streaming all lower levels through external memory.

An iterative implementation that first forms $M$-sized runs gets the same locality as the recursive one. Likewise, recursion can still perform poorly if it allocates scattered nodes or combines subproblems in a strided order. Traversal order and blocking matter; syntax does not.

The external sorting chapter goes further by merging $\Theta(M/B)$ runs at once, improving the logarithm’s base.

#Dynamic Programming: Dense or Sparse?

For 0/1 knapsack, item $i$ has positive integer weight $a_i$ and nonnegative value $v_i$. The goal is to maximize value with total weight at most $W$. A two-dimensional recurrence is

$$ D_i(w)= \begin{cases} D_{i-1}(w), & a_i>w,\\ \max\{D_{i-1}(w),\,v_i+D_{i-1}(w-a_i)\}, & a_i\le w. \end{cases} $$

Only the previous row is needed. Iterating capacities downward lets one array represent both rows without reusing an item twice:

#include <algorithm>
#include <cstddef>
#include <cstdint>
#include <limits>
#include <optional>
#include <span>
#include <stdexcept>
#include <vector>

struct knapsack_item {
    std::size_t weight;
    std::uint64_t value;
};

std::optional<std::uint64_t>
knapsack_value(std::span<const knapsack_item> items,
               std::size_t capacity) {
    if (capacity == std::numeric_limits<std::size_t>::max())
        throw std::length_error("capacity is too large");

    std::vector<std::uint64_t> best(capacity + 1, 0);

    for (const auto& item : items) {
        if (item.weight == 0)
            throw std::invalid_argument("item weights must be positive");
        if (item.weight > capacity)
            continue;

        for (std::size_t w = capacity + 1; w-- > item.weight;) {
            const std::uint64_t previous = best[w - item.weight];
            if (previous > std::numeric_limits<std::uint64_t>::max()
                               - item.value)
                return std::nullopt;

            best[w] = std::max(best[w], previous + item.value);
        }
    }

    return best[capacity];
}

The loop visits capacity, capacity - 1, …, item.weight. When it reads best[w - item.weight], that entry still belongs to the preceding item, so the current item cannot be selected twice. Reversing the direction would silently turn 0/1 knapsack into its unbounded variant.

The array occupies $\Theta(W)$ words, and each item makes one backward sequential pass over it. When the array is larger than memory, this regular access pattern costs $\Theta(NW/B)$ transfers in the basic model. A memoized recursion may instead win when only a small fraction of the $NW$ states are reachable, but its hash table or pointer graph usually has worse locality per state. “Dense versus sparse” is therefore a property of the reachable state space, not a blanket preference for iteration or recursion.

#Sparse Tables

A sparse table answers static idempotent range queries, such as range minimum, in constant time. For an input array $a$, define

$$ T_k[i] = \min(a_i,\ldots,a_{i+2^k-1}). $$ Two adjacent half-intervals give the next level: $$ T_k[i] = \min\bigl(T_{k-1}[i],T_{k-1}[i+2^{k-1}]\bigr). $$

Storing one level at a time makes construction a sequence of linear scans. The following implementation uses half-open query ranges and checks the two common sources of undefined behavior: empty inputs and invalid endpoints.

#include <algorithm>
#include <bit>
#include <cstddef>
#include <span>
#include <stdexcept>
#include <vector>

class sparse_minimum {
public:
    explicit sparse_minimum(std::span<const int> values)
        : size_(values.size()) {
        if (values.empty())
            throw std::invalid_argument("a sparse table cannot be empty");

        const auto level_count =
            static_cast<std::size_t>(std::bit_width(size_));
        levels_.reserve(level_count);
        levels_.emplace_back(values.begin(), values.end());

        for (std::size_t level = 1; level < level_count; ++level) {
            const std::size_t length = std::size_t{1} << level;
            const std::size_t half = length >> 1;
            const std::size_t count = size_ - length + 1;

            levels_.emplace_back(count);
            for (std::size_t i = 0; i < count; ++i) {
                levels_[level][i] =
                    std::min(levels_[level - 1][i],
                             levels_[level - 1][i + half]);
            }
        }
    }

    int query(std::size_t left, std::size_t right) const {
        if (left >= right || right > size_)
            throw std::out_of_range("invalid half-open query range");

        const std::size_t length = right - left;
        const auto level = static_cast<std::size_t>(
            std::bit_width(length) - 1);
        const std::size_t width = std::size_t{1} << level;

        return std::min(levels_[level][left],
                        levels_[level][right - width]);
    }

private:
    std::size_t size_;
    std::vector<std::vector<int>> levels_;
};

For a query $[l,r)$, choose $k=\lfloor\log_2(r-l)\rfloor$. The intervals $[l,l+2^k)$ and $[r-2^k,r)$ cover the query and may overlap. Overlap is harmless for minimum, which is why two table reads suffice.

The table contains $\Theta(N\log N)$ values and takes the same amount of work to build. With each level contiguous, preprocessing costs $\Theta(N\log N/B)$ block transfers when the table does not fit in memory. A query touches at most two table locations; whether either access misses a real cache depends on the query distribution.

#Array of Structures or Structure of Arrays?

Suppose every particle has position, velocity, mass, and an identifier. There are two basic layouts:

  • An array of structures (AoS) keeps all fields of one particle together.
  • A structure of arrays (SoA) keeps all positions together, all velocities together, and so on.

AoS has good spatial locality when an operation consumes most fields of a few records. SoA avoids transferring unused fields when an operation scans one or two columns, and contiguous homogeneous values are also easier to vectorize and compress. Neither layout wins universally. An array-of-structures-of-arrays (AoSoA), which stores small SoA tiles, often provides a useful compromise between record locality and SIMD-friendly streams.

The same distinction appears in databases as row-oriented and column-oriented storage, although production formats add compression, null maps, dictionaries, and late materialization. The right layout follows the hot access pattern: group values that are consumed together, keep the active working set compact, and measure with realistic queries rather than an isolated field access.

#A Locality Checklist

When an algorithm looks memory-bound, ask:

  1. Are consecutive accesses in consecutive blocks, or do they stride across pages?
  2. How much data is reused before the working set is displaced?
  3. Can a pass be blocked so that one tile is completed while resident?
  4. Does the layout transfer fields that the computation never reads?
  5. Is the access sequence regular enough for hardware or software prefetching?
  6. Does improving one cache level merely move the bottleneck to another?

Spatial and temporal locality are not substitutes for the I/O model. They are the vocabulary for discovering which $M$, which $B$, and which access sequence are actually controlling the program.
