Intrinsics and Vector Types

Assembly is the lowest-level interface to SIMD, but C and C++ programmers usually use intrinsics: compiler-provided functions and types that expose a particular instruction or a small instruction pattern. Intrinsics preserve register types and immediates while still letting the compiler allocate registers, schedule instructions, and fold memory operands.

This chapter uses x86 AVX2 for concrete examples. The algorithms often transfer to Arm NEON/SVE or another SIMD ISA, but the intrinsic names and some capabilities do not.

#ISA and Dispatch

Include <immintrin.h> for the Intel-style SSE, AVX, AVX2, and AVX-512 intrinsic declarations. Declaring an intrinsic does not make it safe to execute. The function containing it must be compiled for the required target, and the function must only run when both the CPU and operating system support the relevant state.

GCC and Clang can place one implementation behind a function-level target attribute and select it at runtime:

using AddFunction = void (*)(const double *, const double *, double *, std::size_t);

void add_scalar(const double *a, const double *b,
                double *out, std::size_t n) {
    for (std::size_t i = 0; i < n; ++i)
        out[i] = a[i] + b[i];
}

__attribute__((target("avx2")))
void add_avx2(const double *a, const double *b,
              double *out, std::size_t n) {
    std::size_t i = 0;
    for (; i + 4 <= n; i += 4) {
        const __m256d x = _mm256_loadu_pd(a + i);
        const __m256d y = _mm256_loadu_pd(b + i);
        _mm256_storeu_pd(out + i, _mm256_add_pd(x, y));
    }
    for (; i < n; ++i)
        out[i] = a[i] + b[i];
}

AddFunction select_add() {
    return __builtin_cpu_supports("avx2") ? add_avx2 : add_scalar;
}

The GCC x86 built-in documentation lists the accepted feature names and function-multiversioning facilities. A resolver used before normal runtime initialization has extra requirements such as __builtin_cpu_init; an ordinary call from main does not.

-march=native is convenient for a private benchmark because it targets the build machine. It is inappropriate for a redistributable binary unless that binary also has a lower baseline and dispatch. AVX-512 code must check every subset it uses—for example, AVX512F does not imply AVX512BW or AVX512VPOPCNTDQ.

#Registers and Types

In 64-bit mode, the architectural register view is:

  • SSE exposes sixteen 128-bit registers, XMM0–XMM15;
  • AVX exposes sixteen 256-bit registers, YMM0–YMM15, whose low halves are the XMM registers;
  • AVX-512 exposes thirty-two 512-bit registers, ZMM0–ZMM31, and eight mask registers, k0–k7. For most masked vector instructions, k0 denotes the unmasked form, leaving k1–k7 as general write masks. The low parts of ZMM0–ZMM15 are the older YMM/XMM registers.

The 32-bit x86 ABI has fewer directly nameable vector registers, so register counts must always include the execution mode. AVX-512 is also a feature family rather than one indivisible extension.

Intrinsic vector types describe how an operation interprets the bits:

  • __m128, __m128d, and __m128i hold 128 bits interpreted as floats, doubles, or integers;
  • __m256, __m256d, and __m256i hold 256 bits;
  • __m512, __m512d, and __m512i hold 512 bits.

An integer register has no persistent “element type”; _mm256_add_epi8 and _mm256_add_epi32 can consume the same 256 bits with different lane boundaries. Use cast intrinsics such as _mm256_castsi256_ps when only the interpretation changes. They generate no instruction. Numeric conversions such as _mm256_cvtepi32_ps do real work and are not casts.

#Intrinsic Names

Most names resemble _mm<size>_<operation>_<element-type>. For example:

  • _mm_add_epi16 adds eight packed 16-bit integers in two 128-bit operands;
  • _mm256_sqrt_pd computes square roots of four packed doubles;
  • _mm256_broadcast_sd broadcasts one double to four lanes;
  • _mm256_ceil_pd rounds four doubles toward positive infinity;
  • _mm256_cmpeq_epi32 compares eight pairs of 32-bit integers and returns all-one or all-zero lanes;
  • _mm256_blendv_ps selects packed floats according to the sign bits of a mask.

There is no _mm256_acos_pd instruction or standard x86 intrinsic. Transcendental functions such as acos come from a vector math library or a compiler’s library-vectorization interface and generally expand to substantial algorithms.

Some operands are immediates encoded in the instruction, so their intrinsic arguments must be compile-time constants. Comparisons and shuffles expose many such modes. The authoritative searchable reference is Intel’s Intrinsics Guide, which also marks intrinsics that expand to more than one instruction.

#What the Compiler May Change

The compiler preserves an intrinsic’s semantics, not a one-to-one textual assembly listing. The add loop above can become three assembly instructions because x86 arithmetic accepts one memory operand:

vmovupd ymm1, YMMWORD PTR [rdi + rax]
vaddpd  ymm0, ymm1, YMMWORD PTR [rsi + rax]
vmovupd YMMWORD PTR [rdx + rax], ymm0

This is not a “fused vector addition.” It is one load instruction, an add with a memory source, and one store. The processor may still decode the memory-form add into separate load and arithmetic micro-operations. True arithmetic fusion is an operation such as fused multiply-add, which changes both the instruction and floating-point rounding behavior.

Likewise, a broadcast or extraction intrinsic may become a short sequence, and two neighboring intrinsics may combine. Always inspect the optimized assembly and measure on the target microarchitecture.

#Bounds and Padding

The vector loop uses i + 4 <= n, then handles the remainder scalarly. It never accesses outside [0,n), including for n < 4.

An alternative is to round the allocation up to four doubles and deliberately execute one final full vector. That is legal only if every load and store has four accessible elements: the input padding must be initialized if it is read, and the output allocation must also include the rounded capacity. Padding one array does not authorize an overread from another, and being on the same mapped page is irrelevant to the C++ object bound.

#Compiler Vector Extensions

GCC and Clang also support fixed-width vector types:

using v4si = int   __attribute__((vector_size(16)));
using v8si = int   __attribute__((vector_size(32)));
using v8sf = float __attribute__((vector_size(32)));

v4si a = {1, 2, 3, 5};
v4si b = {8, 13, 21, 34};
v4si c = (a + b) * 2;

They make elementwise arithmetic concise:

using v4d = double __attribute__((vector_size(32)));

v4d add(v4d a, v4d b) {
    return a + b;
}

The syntax is a compiler extension, the width is fixed, and not every C++ operator has useful vector semantics. It is more readable than a long intrinsic expression but not architecture-independent by itself.

Interoperation requires a defined type on both sides. A same-size representation copy is safe and normally optimized away:

__attribute__((target("avx")))
int sign_mask(v8sf x) {
    __m256 raw;
    std::memcpy(&raw, &x, sizeof(raw));
    return _mm256_movemask_ps(raw);
}

Portable SIMD libraries add ISA dispatch, scalable abstractions, and tested fallbacks. Notable C++ options include Highway, EVE, Vector Class Library, and xsimd. Intrinsics remain useful when an algorithm depends on a specific instruction or when profiling shows the abstraction missed an important lowering.
