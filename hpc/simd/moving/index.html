Moving Data

Elementwise arithmetic is usually the easy part of SIMD. The difficult part is arranging data so that a useful amount arrives in the right lanes without spending more work on loads, conversions, shuffles, and tails than the arithmetic saves.

#Aligned and Unaligned Access

AVX offers aligned load/store intrinsics and unaligned loadu/storeu intrinsics. Their contract is precise:

  • _mm256_load_si256 and _mm256_store_si256 require the memory address itself to be divisible by 32;
  • _mm256_loadu_si256 and _mm256_storeu_si256 accept any address for which all 32 accessed bytes belong to valid objects.

Fitting inside one cache line is not sufficient for an aligned load. An address at offset 4 inside a line is still not 32-byte aligned, and an aligned instruction may fault or the compiler may assume the impossible case never occurs.

Use unaligned operations in a general API:

void add(const std::int32_t *a, const std::int32_t *b,
         std::int32_t *out, std::size_t n) {
    std::size_t i = 0;
    for (; i + 8 <= n; i += 8) {
        const __m256i x = _mm256_loadu_si256(
            reinterpret_cast<const __m256i *>(a + i));
        const __m256i y = _mm256_loadu_si256(
            reinterpret_cast<const __m256i *>(b + i));
        _mm256_storeu_si256(
            reinterpret_cast<__m256i *>(out + i),
            _mm256_add_epi32(x, y));
    }
    for (; i < n; ++i)
        out[i] = a[i] + b[i];
}

The scalar expression can overflow for arbitrary signed inputs; this example assumes the mathematical sums fit in int32_t. Use unsigned lanes for defined modulo arithmetic or widen the result when that is not true.

When an API guarantees alignment, aligned operations document and exploit it:

alignas(32) std::int32_t a[N];

std::size_t i = 0;
for (; i + 8 <= N; i += 8) {
    const __m256i x = _mm256_load_si256(
        reinterpret_cast<const __m256i *>(a + i));
    // ...
}

Because i advances by eight integers, every vector begins 32 bytes after the previous one. Dynamic allocations need the same base guarantee, as described in Alignment and Packing.

On many modern x86 cores, an unaligned instruction whose data lies within one cache line has the same throughput as its aligned counterpart. Crossing a line can require two cache accesses, and crossing a page can be more expensive still; unaligned stores have additional microarchitectural constraints. The exact penalty varies by instruction and processor. The historical Zen 2 benchmark in this book found an offset-three add loop about 30% slower because roughly half its 32-byte accesses crossed 64-byte lines, not because the mnemonic ended in u.

Alignment is therefore a property to measure, not a reason to manufacture undefined behavior. Aligned intrinsics are not “free runtime assertions”: the compiler is entitled to assume their precondition without checking it.

Non-temporal operations have a separate contract. Streaming stores can avoid ordinary write allocation for large, write-only output, but they need suitable alignment, complete streams, and an ordering fence at the relevant boundary. They are covered in Memory Bandwidth; a non-temporal load is not a portable “do not cache” switch.

#Register History and Aliasing

MMX did not introduce a clean independent register file. Its eight 64-bit registers alias the physical x87 floating-point stack registers, and code had to execute EMMS before returning to x87 arithmetic. They were not simply aliases for an 80-bit value’s mantissa.

SSE introduced separate XMM registers. AVX extended them: XMM0 is the low 128 bits of YMM0, and YMM0 is the low 256 bits of ZMM0 when AVX-512 is present. This is architectural naming, not evidence that the registers “live in the FPU”; modern cores rename vector registers internally.

Legacy SSE and VEX/EVEX encodings also differ in what happens to upper bits. A 128-bit VEX instruction normally zeros the upper part of the corresponding YMM register, while many legacy SSE instructions preserve it. Mixing legacy SSE with AVX could trigger transition penalties on some older processors, so compilers insert vzeroupper at suitable call boundaries. Do not add it blindly inside a hot loop; inspect the ABI boundary and target CPU.

#Extract, Insert, and Broadcast

Extracting lane zero is usually cheap:

vmovd eax, xmm0

Extracting a high lane of a 256-bit integer vector may first select the upper 128-bit half:

vextracti128 xmm1, ymm0, 1
vpextrd      eax, xmm1, 3

The index argument to _mm256_extract_epi32 and _mm256_insert_epi32 is an immediate and must be a compile-time constant. Exact sequences vary because the compiler can reuse an already available half or choose a shuffle. Occasional extraction is fine; repeatedly moving every lane to scalar registers usually defeats the point of SIMD.

Constants and broadcasts have direct intrinsics:

const __m256i indices = _mm256_setr_epi32(0, 1, 2, 3, 4, 5, 6, 7);
const __m256i answer = _mm256_set1_epi32(42);
const __m256i zero = _mm256_setzero_si256();

setr lists lanes in increasing memory order; _mm256_set_epi32 lists them in the opposite argument order. A compiler may load a constant pool or synthesize the value. _mm256_broadcast_ss(p) broadcasts one float from memory to eight lanes.

For debugging, store a vector into a real array rather than aliasing the vector object through an unrelated pointer:

void print(__m256i value) {
    alignas(32) std::array<std::uint32_t, 8> lane{};
    _mm256_store_si256(reinterpret_cast<__m256i *>(lane.data()), value);

    for (std::uint32_t x : lane)
        std::cout << std::bitset<32>(x) << ' ';
    std::cout << '\n';
}

#Gather and Scatter

A gather loads elements from addresses formed by a base, vector indices, and a scale. AVX2 provides integer and floating-point gathers; AVX-512 adds scatter forms and masked variants. They require the AVX2 or relevant AVX-512 feature at runtime, and every active index must be in bounds.

This complete AVX2 checksum handles a query tail and uses modulo-$2^{32}$ arithmetic:

std::uint32_t gather_sum(const std::int32_t *data,
                         const std::int32_t *query,
                         std::size_t count) {
    __m256i sum = _mm256_setzero_si256();
    std::size_t i = 0;

    for (; i + 8 <= count; i += 8) {
        const __m256i index = _mm256_loadu_si256(
            reinterpret_cast<const __m256i *>(query + i));
        const __m256i value = _mm256_i32gather_epi32(data, index, 4);
        sum = _mm256_add_epi32(sum, value);
    }

    alignas(32) std::array<std::uint32_t, 8> lane{};
    _mm256_store_si256(reinterpret_cast<__m256i *>(lane.data()), sum);
    std::uint32_t result = std::accumulate(lane.begin(), lane.end(), 0u);

    for (; i < count; ++i)
        result += static_cast<std::uint32_t>(data[query[i]]);
    return result;
}

The precondition is 0 <= query[i] < data_size for every query; the function would need data_size to check it itself. On the original Zen 2 experiment, gather plus one add was not faster than scalar indexed loads except for small working sets. Other cores differ. Gather is most valuable when keeping the values in vector registers enables enough subsequent arithmetic to repay its latency and throughput cost.

Irregular SIMD memory access is still not the same as eight independent scalar threads. Gather/scatter instructions share execution and memory resources and can touch many lines or pages. Data layout that turns a gather into one or two contiguous loads is often the larger optimization.
