Preface

An algorithm does not run on the RAM model. It runs through a compiler, an instruction set, a speculative out-of-order core, several caches, a virtual-memory system, and whatever operating system happened to schedule it. Asymptotic analysis deliberately hides these details; performance engineering begins when the hidden constants become the problem.

This book studies the boundary between algorithms and modern hardware. The first part is about one CPU thread: how to measure it, reason about it, and reshape an algorithm so that the core can execute more useful work in parallel. The recurring subjects are instruction-level parallelism, arithmetic, memory locality, and SIMD. The final chapters put these ideas back together in complete algorithms and data structures.

The goal is not to replace asymptotic complexity. A linear algorithm still loses to a logarithmic one eventually, and no arrangement of intrinsics rescues a fundamentally unsuitable data structure. The goal is to add the missing levels of the model: the input sizes we actually process, the work each operation expands into, and the paths that data follows through the machine.

#Prerequisites

The intended reader is comfortable with elementary algorithms and data structures and can read C or C++. Familiarity with calculus, probability, and modular arithmetic is helpful in a few chapters; the required ideas are introduced where they are used.

No prior assembly or computer-architecture course is required. The architecture chapters build a working model from the instruction-set boundary upward. It is intentionally a programmer’s model: detailed enough to predict many performance effects, but not a substitute for a processor-design text or a vendor manual.

Most examples use C++ on x86-64 with GCC or Clang. These choices make the generated machine code easy to inspect and give us mature SIMD intrinsics and profiling tools. The principles transfer to other compiled languages and architectures, but instruction availability, ABI rules, cache geometry, and compiler behavior do not. Platform-specific examples say which assumptions they need.

#How to Read This Part

The chapters form three broad layers.

Foundations, Chapters 1–5. Complexity models explain why elapsed time cannot be inferred from operation counts alone. Computer architecture follows a program from source-level control flow to instructions and operating-system interaction. Instruction-level parallelism develops the core model of latency, throughput, dependencies, and speculation. Compilation and profiling show how to inspect what actually happened.

Mechanisms, Chapters 6–10. Arithmetic and number theory derive transformations that replace expensive operations or change their representation. External memory and CPU caches study locality at two scales. SIMD turns data-parallel work into explicit vector operations.

Case studies, Chapters 11–12. The algorithm and data-structure chapters start from correct baselines and optimize complete workloads. They are not a bag of independent tricks. Each one combines several earlier ideas and makes their interactions visible.

Reading in order gives the cleanest dependency graph, but it is not mandatory. A reader who already knows assembly can start with instruction-level parallelism. Someone with a concrete vectorization problem can read the SIMD chapter first and follow its links backward. The case studies are most useful after the relevant mechanism chapters, because copying optimized code without its preconditions is an efficient way to copy bugs.

#The Experimental Contract

Performance is an empirical property of a complete program on a particular system. A benchmark result should therefore be read together with:

  • the processor and its enabled instruction-set extensions;
  • the compiler, version, flags, and relevant source code;
  • the input distribution and size;
  • the statistic being reported and the number of repetitions;
  • the state that may affect the result, such as cache warmth, frequency scaling, allocation, and thread placement.

Historical measurements in the case studies are evidence for a mechanism on the named machine, not universal constants. The point of a “five times faster” result is the explanation that survives after the number does not. Re-run the benchmark on the target system before adopting an optimization.

Correctness comes first. Examples avoid undefined behavior where practical, document ranges that prevent overflow or overread, and separate exact transformations from approximations. Short fragments may omit application-level error handling, but omitted handling is not permission to omit it in production. Cryptographic examples in particular are educational mathematics, never a recommendation to implement security protocols from scratch.

#A Useful Optimization Loop

Most successful investigations follow the same cycle:

  1. Define the workload and verify a simple implementation.
  2. Measure enough of the whole program to locate the limiting resource.
  3. Form a hardware-level hypothesis: a dependency chain, branch misses, memory traffic, front-end pressure, or insufficient parallel work.
  4. Change one important thing and preserve a reference implementation for differential testing.
  5. Measure again, inspect the generated code when necessary, and keep the change only if the explanation and evidence agree.

Starting with source-level cleverness reverses this order. It often optimizes cold code, moves cost elsewhere, or exchanges a visible instruction for less visible memory traffic. A profiler is not an oracle, but it is a better opening move than guessing.

#Scope

Part I focuses on single-threaded CPU performance. Operating-system effects, shared caches, and storage appear where they affect one thread, but synchronization, multicore algorithms, GPUs, and distributed systems belong to later parts.

The book emphasizes transferable models rather than a catalog of current processors. Hardware and compilers evolve. Latencies, cache sizes, and favored instruction sequences will change; conservation laws are more durable. Work must enter through a finite front end, dependencies limit overlap, bytes must cross finite-bandwidth links, and representations determine which operations are cheap.

#Code and Contributions

The book source is hosted in the Algorithmica repository, and companion experiments live in the code repository. Examples in the text are kept small enough to explain; the companion programs provide benchmark scaffolding and historical context.

Corrections are welcome, especially when they include a minimal counterexample, a primary reference, or a reproducible measurement. Performance literature improves the same way performance code does: keep a trustworthy baseline, make a falsifiable claim, and test it where the claim is supposed to hold.
