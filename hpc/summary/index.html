A Performance Engineering Checklist

Optimization is the process of discovering which constraint is active and changing the program so that a different constraint becomes active. That is why isolated tricks age badly and models age well.

A loop can be slow because it performs unnecessary work, waits on one dependency chain, misses in cache, exceeds memory bandwidth, feeds an unpredictable branch, saturates an execution port, or simply never appears in the program’s profile. Each cause suggests a different transformation. Applying all transformations indiscriminately produces complicated code that is still limited by the original bottleneck.

This chapter condenses Part I into a repeatable investigation.

#1. Define the Program You Are Optimizing

Write down the workload before timing it:

  • What inputs occur in production, including empty, tiny, adversarial, and malformed cases?
  • Which output differences are acceptable: none, a floating-point tolerance, or a probabilistic error rate?
  • Is the objective throughput, median latency, tail latency, startup time, memory use, energy, or cost?
  • Which processors, operating systems, and compiler targets must the binary support?

These choices are algorithmic constraints. -ffast-math is not an optimization for a program that requires IEEE exception behavior; reading past the end of an array is not an optimization for an interface that does not provide padding; -march=native is not a deployment strategy for a binary distributed to unknown machines.

Keep a simple reference implementation. Test the optimized version against it on boundary cases and randomized inputs. The faster the code becomes, the more valuable an independent definition of “correct” becomes.

#2. Establish a Reproducible Baseline

Build an optimized binary with debug information and the actual deployment configuration. Record the compiler version, flags, processor, input generator, and benchmark command.

Measure enough work that timer overhead is negligible, but preserve the workload’s intended state. A warmed cache measures steady state; a cold cache measures something else. Neither is inherently more honest.

Inspect variation before comparing means. Randomize or interleave competing implementations, collect independent batches where possible, and report the statistic that matches the objective. The probability and measurement appendix develops the underlying assumptions.

#3. Find the Expensive Region

Use instrumentation and sampling to identify where time is spent. Start at the program level: eliminating a function that consumes 20% of the run is more promising than halving an instruction that consumes 0.2%.

Then narrow the question. Hardware counters, annotated assembly, and machine-code analyzers can distinguish several broad limits:

  • front-end stalls or excessive instruction count;
  • a long dependency chain;
  • execution-port pressure;
  • branch mispredictions;
  • cache or TLB misses;
  • exhausted memory bandwidth;
  • system calls, allocation, synchronization, or I/O outside the kernel.

Counters are evidence, not diagnoses. A cache-miss count matters only after relating misses to bytes, latency, overlap, and elapsed time. A model should predict the direction and rough size of the change you are about to make.

#4. Remove Work Before Accelerating It

The largest speedups usually come from changing what is computed.

Use an appropriate algorithm and data structure for the actual input range. Precompute values that are reused. Hoist loop-invariant work. Replace repeated parsing, allocation, hashing, or virtual dispatch with a representation that performs it once. Batch transitions across expensive boundaries such as system calls and storage requests.

Asymptotic complexity still belongs at the top of the checklist. Performance engineering extends algorithm analysis; it does not excuse skipping it.

#5. Choose a Hardware-Friendly Representation

Representation determines which operations become cheap.

  • Fixed-point reciprocals turn division by reused constants into multiplication.
  • Montgomery space turns modular reduction by an odd modulus into low-word cancellation and a shift.
  • Bitmaps replace pointer-heavy sets over dense universes with word operations.
  • Structure-of-arrays layouts let scans load only the fields they use; array-of-structures layouts keep fields of one object together.
  • Flat and blocked trees exchange pointer chasing for predictable cache-line access.

This is often the bridge between an algorithmic idea and an instruction-level speedup. SIMD works well after data has been arranged into homogeneous lanes, not before.

#6. Make Memory Access Deliberate

Count bytes as well as operations. When a kernel is bandwidth-bound, deleting arithmetic may have no measurable effect.

Prefer sequential traversal and compact data. Block computations so reused working sets fit a useful cache level. Separate hot fields from cold fields. Avoid storing materialized intermediates when producing and consuming them in one pass is possible.

For latency-bound pointer chains, seek independent requests that create memory-level parallelism, or replace pointers with indices and packed layouts. Software prefetching is a last-mile technique for a stable access pattern the hardware cannot learn; it spends instructions and bandwidth and must be scheduled far enough ahead without reading invalid addresses.

External-memory algorithms apply the same principle at a larger block size: sort and scan runs, batch random requests, and use branching factors matched to transfer blocks.

#7. Expose Independent Work

An out-of-order core overlaps instructions only when dependencies allow it. If every iteration waits for the preceding result, the reciprocal throughput of an instruction is irrelevant; latency sets the pace.

Break artificial dependencies, use multiple accumulators for associative reductions, and unroll enough to expose independent operations. Stop when code size, register pressure, or memory traffic becomes the new limit. Consult instruction tables and inspect the emitted machine code rather than counting source operators.

Branches are dependencies on control. Keep predictable branches: they are cheap and often clearer. For genuinely unpredictable conditions, consider conditional moves, masks, lookup tables, or partitioning the data—but compare the extra work against the cost of a misprediction. Branchless code is not automatically faster and may perform operations that the branch would have skipped.

#8. Vectorize the Right Loop

SIMD requires the same operation across independent lanes. Before reaching for intrinsics:

  1. make the loop bounds and aliasing contract visible to the compiler;
  2. use a contiguous layout and remove loop-carried dependencies;
  3. check the vectorization report and generated assembly;
  4. handle tails and alignment explicitly;
  5. write intrinsics only when the compiler still lacks information or the algorithm itself must change.

Vector width does not guarantee proportional speedup. Loads, stores, shuffles, conversions, frequency behavior, and horizontal reductions remain. Multi-version a binary or choose a conservative target when the deployment population is heterogeneous.

#9. Transform Arithmetic with Contracts Attached

Strength reduction is powerful precisely because arithmetic operations have unequal costs. It is also a common source of silent errors.

State ranges before changing integer arithmetic. Prove that intermediate values do not overflow—or use unsigned wraparound when modulo-$2^w$ arithmetic is intentionally required. Handle zero before calling count-trailing-zero intrinsics. Remember that signed division rounds toward zero and signed overflow is undefined in C++.

For floating point, decide which identities the application permits. Reassociation changes rounding; reciprocal approximations change error; flushing subnormals changes tiny values; fused multiply-add rounds once rather than twice. Measure numerical error alongside running time.

#10. Re-measure and Simplify

After each material change:

  • rerun correctness tests and sanitizers where applicable;
  • inspect the new profile to confirm the intended bottleneck moved;
  • benchmark on representative machines and input distributions;
  • remove changes that do not earn their complexity;
  • document preconditions and the evidence that justified the remaining ones.

Optimization ends when the objective is met, not when every loop contains an intrinsic. The best final implementation often has a portable baseline, one or two carefully chosen specialized kernels, and a dispatch boundary that keeps the rest of the system ordinary.

#The Short Version

If only one page survives, keep this sequence:

  1. Specify correctness, workload, machine population, and metric.
  2. Preserve a reference implementation and representative tests.
  3. Build and measure the real program.
  4. Profile to locate the limiting region and resource.
  5. Remove unnecessary work and choose a better representation.
  6. Improve locality and expose independent operations.
  7. Vectorize or specialize only where the model predicts a gain.
  8. Re-test, re-measure, and write down the assumptions.

The craft is not knowing a long list of tricks. It is being able to explain, before and after a change, where each cycle and byte had to go.
